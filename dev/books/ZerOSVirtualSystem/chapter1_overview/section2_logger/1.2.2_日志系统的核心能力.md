# 1.2.2 日志系统的核心能力

## 本节导读

本节将介绍日志系统的核心能力，包括日志级别、存储与输出、以及性能与可维护性方面的考虑。这些能力是设计或选用日志组件时的通用要点，ZerOS 的 KernelLogger 也围绕这些能力进行实现。

---

## 日志级别

### 级别的定义

日志系统通常定义多个**日志级别**，用于区分单条日志的重要程度和详细程度。常见级别自低到高可概括为：

- **DEBUG**：调试信息，记录最详细的内部状态、变量值、分支走向等，便于开发时排查问题。在生产环境中通常关闭或仅对部分模块开启，以避免日志量过大。
- **INFO**：一般信息，记录系统正常运行时的关键步骤，如“模块加载完成”“用户登录成功”。适合作为默认级别，既能反映主流程，又不会像 DEBUG 那样刷屏。
- **WARN**：警告信息，表示可能存在问题但尚未导致失败，如“重试中”“降级使用备用方案”。便于运维提前发现潜在风险。
- **ERROR**：错误信息，表示已经发生的错误，如“加载失败”“接口返回异常”。需要重点关注并配合告警或人工排查。
- **FATAL**：致命错误，表示系统无法继续运行，如“关键模块初始化失败”。通常伴随进程退出或不可恢复状态。

不同系统对级别的命名和数量可能略有差异（例如增加 TRACE、减少 FATAL），但“从细到粗、从调试到致命”的层次思想是一致的。

### 级别的作用

级别不仅用于人类阅读时的区分，还会直接影响运行时的行为：

- **过滤**：通过配置“最低输出级别”，可以只输出不低于该级别的日志。例如将最低级别设为 INFO，则 DEBUG 不会写入或显示，从而在保留主流程信息的同时控制日志量。
- **优先级与展示**：在控制台或日志查看器中，可以按级别着色、折叠或排序，让 ERROR/WARN 更容易被注意到。
- **性能**：在日志库实现中，可以在写入前先判断当前配置的级别，若某条日志的级别低于配置则直接跳过格式化与 IO，减少不必要的开销。这对引导阶段尤其重要，因为此时模块多、调用频繁，若每条 DEBUG 都做字符串拼接和输出，会明显拖慢启动。

## 日志的存储与输出

### 输出目标

同一条日志可能被发送到多个目标，以便同时满足“开发时看控制台”和“生产上留痕”的需求：

- **控制台**：浏览器提供的 `console.log` / `console.info` / `console.error` 等。开发时最常用，无需额外存储，但刷新或关闭页面后即丢失，且不适合大量日志。
- **文件**：将日志写入本地文件或通过后端接口落库。便于长期保存和按时间、级别检索，但需要设计轮转与清理策略，避免占满磁盘。
- **网络**：将日志上报到远程日志服务器或日志平台。便于集中管理多实例、多环境，但依赖网络且可能涉及隐私与合规，需谨慎使用。

ZerOS 运行在浏览器中，其“文件”和“网络”能力受浏览器与后端接口限制；KernelLogger 的实现会结合这些约束选择实际可用的输出方式。

### 存储策略

当日志需要持久化时，通常需要考虑以下策略：

- **大小与条数限制**：为单个日志文件或内存缓冲区设置上限，防止日志无限增长导致内存或磁盘占满。超过限制时可触发轮转或丢弃最旧日志。
- **滚动策略**：按时间（如每天一个文件）或按大小（如每 10MB 一个新文件）轮转，旧文件可压缩、归档或按保留天数删除。这样既保留近期详细日志，又控制总占用。
- **格式化**：约定每条日志的格式（如时间戳、级别、模块名、消息、可选堆栈），便于后续用脚本或日志系统解析、检索和统计。统一的格式也有利于跨模块、跨环境对比问题。

## 日志的性能影响

### 性能开销

日志记录会带来可见的开销，在引导阶段若滥用会拖慢启动：

- **IO 开销**：控制台输出、写文件或发网络请求都有 IO 成本。高频率的同步写会阻塞主线程，导致启动变慢或界面卡顿。
- **存储开销**：日志内容占用内存（缓冲区）或磁盘；在浏览器环境中，过大的日志还可能影响标签页或持久化存储的配额。
- **计算开销**：拼接字符串、序列化对象、获取调用栈等都需要 CPU 时间。在热路径上即使“只是 DEBUG”，若每条都做复杂格式化，累计开销也不可忽视。

### 优化策略

常见优化方式包括：

- **分级控制**：在生产或高负载环境下将最低级别设为 INFO 或 WARN，从源头减少日志条数；开发或排查问题时再临时开启 DEBUG。
- **异步写入**：将日志先放入内存队列，由单独的任务或 Worker 负责批量写入控制台/文件/网络，避免阻塞主流程。注意在崩溃或页面关闭时需考虑未刷写的日志是否要尽力写出。
- **批量与采样**：对高频日志（如“每帧渲染”）可做批量汇总或采样（如每 100 条写一条），在保留一定可观测性的同时控制量和性能。

在 ZerOS 的引导流程中，日志系统是第一个被依赖的模块，其实现会尽量做到“默认可用、可配置、对启动时间影响可控”，以便其他模块能安全地打日志而不拖垮整体性能。

---

## 本节小结

本节介绍了日志系统的核心能力：通过**日志级别**区分重要程度并支持过滤与性能优化；通过**多目标输出**和**存储策略**兼顾开发可见性与持久化需求；通过**分级控制、异步写入和批量/采样**在可观测性与性能之间取得平衡。这些能力是理解 KernelLogger 设计与配置的基础。
