# 1.5.3 Starter 实现

## 本节导读

本节将介绍 ZerOS 中模块加载器（Starter）的具体实现要点。Starter 是 BootLoader 的核心逻辑所在，负责按依赖顺序异步加载所有内核与系统模块；详细源码分析见第 2 章，本节仅建立概述级认识。

---

## Starter 核心架构

### 模块定位

Starter 即 BootLoader 中执行“按序加载模块”的那部分逻辑，通常与依赖配置、对象池配合：从 **DependencyConfig** 或内置的 **MODULE_DEPENDENCIES** 读取依赖图，对模块列表做**拓扑排序**得到加载顺序，再逐个（或按层并行）通过动态插入 `<script>` 或调用加载 API 加载脚本，并等待各模块初始化完成。

### MODULE_DEPENDENCIES

**MODULE_DEPENDENCIES** 是一个键值结构：键为模块路径（如 `../kernel/process/processManager.js`），值为该模块所依赖的模块路径数组。Starter 根据此结构构建有向图，进行拓扑排序后得到从“无依赖”到“依赖最多”的加载顺序，保证被依赖者先于依赖者执行，避免未初始化就被访问。

---

## 加载流程

### 步骤概览

1. **读取 MODULE_DEPENDENCIES**：得到完整的依赖关系图（可包含仅被依赖但未在键中的模块）。
2. **拓扑排序**：计算一个合法的加载序列；若存在循环依赖则报错或拒绝启动。
3. **按序加载模块**：按排序结果依次加载脚本；对同一层级无依赖关系的模块可并行加载以缩短启动时间。每加载一个模块后，该模块的初始化代码会执行（通常向 POOL 注册自身或声明就绪），Starter 再继续下一批。

---

## 层级划分

### ZerOS 模块层级

ZerOS 通过依赖关系自然形成**多层结构**：例如枚举/类型池为底层，文件系统、内存、进程等依赖它们，再往上是事件与 GUI，最后是依赖文件系统与用户系统的锁屏、扩展等。Starter 不显式写死“第几层”，而是完全由 MODULE_DEPENDENCIES 与拓扑排序决定顺序，因此新增模块时只需在依赖图中声明依赖即可融入现有流程。

---

## 本节小结

本节概述了 Starter 的职责：基于 MODULE_DEPENDENCIES 构建依赖图、做拓扑排序、按序（或按层并行）加载模块，并与 DependencyConfig、POOL 配合完成引导。具体实现细节（如异步等待、错误处理、与 HTML 中已加载脚本的兼容）见第 2 章。
