# 3.3.1 APPLICATION_SOP 与 Heap/Shed

## 本节导读（阅读目标）

本节使读者能够：**① 完全理解 APPLICATION_SOP 在内存中的结构（Map<pid, Object>）及每个 pid 对应对象的 heaps/sheds/nextHeapId/nextShedId 含义；② 明确 _getApplicationSOP 与 _saveApplicationSOP 的每一段逻辑：_loadingApplicationSOP 防递归、KernelMemory 不可用时的降级、只持久化元数据不持久化 Heap/Shed 的原因；③ 掌握 _canAllocateMemory 与 BIOS 设置的关系；④ 接手维护时能正确扩展 per-pid 元数据、排查“刷新后 nextHeapId 冲突”或“保存时循环/未保存”问题。** 下文给出**带行号与中文注释的完整/关键源码**、**行为流程**与**接手维护要点**。源码文件：`kernel/memory/memoryManager.js`。

## 一、APPLICATION_SOP 的结构（源码注释约 55–65 行）

**APPLICATION_SOP** 在内存中为 **Map<pid, Object>**，每个 pid 对应一个对象，结构如下：

| 字段 | 类型 | 含义 | 是否持久化 |
|------|------|------|------------|
| heaps | Map<heapId, Heap> | 该进程的堆实例 | **否**（运行时对象，可能含函数/DOM 引用） |
| sheds | Map<shedId, Shed> | 该进程的栈实例 | **否**（同上） |
| nextHeapId | number | 下一个可用的堆 ID | **是** |
| nextShedId | number | 下一个可用的栈 ID | **是** |

Heap/Shed 是运行时对象，无法直接 JSON 序列化；因此持久化时**只保存 nextHeapId、nextShedId**，加载时恢复的 info 仅含这两项，heaps/sheds 在运行时由 MemoryManager 按需创建并挂到该 info 上。

## 二、_canAllocateMemory — BIOS 与申请内存开关（约 31–54 行）

```javascript
    static _canAllocateMemory() {
        try {
            let LStorage = null;
            if (typeof POOL !== 'undefined' && typeof POOL.__GET__ === 'function') {
                try {
                    LStorage = POOL.__GET__("KERNEL_GLOBAL_POOL", "LStorage");
                } catch (e) {}
            }
            if (!LStorage && typeof window !== 'undefined' && window.LStorage) {
                LStorage = window.LStorage;
            }
            if (!LStorage || !LStorage._storageData || !LStorage._storageData.system) {
                return true;   // 未初始化或读取失败时默认允许
            }
            const value = LStorage._storageData.system['bios.memoryAllocation'];
            if (value === undefined || value === null) {
                return true;
            }
            return Boolean(value);
        } catch (e) {
            return true;
        }
    }
```

**行为流程**：从 POOL 或 window 取 LStorage；若不存在或无 system 数据则返回 true（允许申请）；否则读 `system['bios.memoryAllocation']`，仅当明确为 false 时返回 false，其余返回 true。**设计原因**：安全策略“未初始化/读取失败时默认允许”，只有明确关闭内存申请时才禁止。

## 三、_getApplicationSOP — 完整源码与注释（约 70–112 行）

```javascript
    static _getApplicationSOP() {
        if (MemoryManager._loadingApplicationSOP) {
            if (!MemoryManager._fallbackApplicationSOP) MemoryManager._fallbackApplicationSOP = new Map();
            return MemoryManager._fallbackApplicationSOP;
        }
        if (typeof KernelMemory === 'undefined') {
            if (!MemoryManager._fallbackApplicationSOP) MemoryManager._fallbackApplicationSOP = new Map();
            return MemoryManager._fallbackApplicationSOP;
        }

        MemoryManager._loadingApplicationSOP = true;
        try {
            const data = KernelMemory.loadData('APPLICATION_SOP');
            if (data) {
                const map = new Map();
                if (Array.isArray(data)) {
                    for (const [pid, info] of data) {
                        map.set(pid, info);  // info 仅含 nextHeapId、nextShedId 等元数据
                    }
                } else if (typeof data === 'object') {
                    for (const [pid, info] of Object.entries(data)) {
                        map.set(parseInt(pid), info);
                    }
                }
                return map;
            }
            const newMap = new Map();
            MemoryManager._saveApplicationSOP(newMap);
            return newMap;
        } finally {
            MemoryManager._loadingApplicationSOP = false;
        }
    }
```

**行为流程**：  
1. 若 _loadingApplicationSOP 为 true（防止递归）→ 返回 _fallbackApplicationSOP。  
2. 若 KernelMemory 未定义 → 返回 _fallbackApplicationSOP。  
3. 置 _loadingApplicationSOP = true；loadData('APPLICATION_SOP')；有数据则按数组或对象恢复为 Map<pid, info>（info 仅含元数据）；无数据则新建 Map 并 _saveApplicationSOP；finally 中置 _loadingApplicationSOP = false。

**设计原因**：_getApplicationSOP 可能在被 KernelMemory 或其它初始化链路上间接调用，若不设 _loadingApplicationSOP，可能形成递归；此时返回 fallback 避免死循环。

## 四、_saveApplicationSOP — 完整源码与注释（约 117–150 行）

```javascript
    static _saveApplicationSOP(sop) {
        if (typeof KernelMemory === 'undefined') return;
        if (KernelMemory._ensuringMemory) return;  // 防止在内存初始化时保存，避免循环

        const array = Array.from(sop.entries()).map(([pid, info]) => {
            return [pid, {
                nextHeapId: info.nextHeapId || 1,
                nextShedId: info.nextShedId || 1
            }];
        });

        if (KernelMemory._memoryCache) {
            KernelMemory.saveData('APPLICATION_SOP', array);
        } else {
            setTimeout(() => {
                if (KernelMemory._memoryCache) {
                    KernelMemory.saveData('APPLICATION_SOP', array);
                }
            }, 100);
        }
    }
```

**行为流程**：  
1. KernelMemory 未定义或 _ensuringMemory 为 true 则 return（静默跳过，避免在内存初始化过程中写回导致循环）。  
2. 将 sop 转为数组，每项只保留 [pid, { nextHeapId, nextShedId }]，不写入 heaps/sheds。  
3. 若 _memoryCache 已存在则立即 saveData；否则延迟 100ms 再尝试保存，避免 KernelMemory 尚未就绪时写入失败。

**设计原因**：Heap/Shed 含运行时引用，不序列化；只持久化 ID 计数器，刷新后每个 pid 能恢复“下一个 ID”，避免 ID 冲突。延迟保存用于兼容“APPLICATION_SOP 首次被创建时 KernelMemory 可能尚未完成 _memoryCache 初始化”的情况。

## 五、APPLICATION_SOP 的 getter 与缓存（约 155–166 行）

```javascript
    static get APPLICATION_SOP() {
        if (MemoryManager._applicationSOPCache) {
            return MemoryManager._applicationSOPCache;
        }
        const sop = MemoryManager._getApplicationSOP();
        MemoryManager._applicationSOPCache = sop;
        return sop;
    }
```

首次访问时从 KernelMemory 加载并写入 _applicationSOPCache；后续直接返回缓存。注意：若别处直接修改了 KernelMemory 中的 APPLICATION_SOP，缓存不会自动失效，需在需要刷新的地方清除 _applicationSOPCache 或通过 MemoryManager 提供的接口更新。

---

## 六、行为流程小结（APPLICATION_SOP 从持久化到运行时）

1. 某处访问 MemoryManager.APPLICATION_SOP 或直接调 _getApplicationSOP()。  
2. 若正在加载或 KernelMemory 不可用 → 返回 fallback Map。  
3. 否则 loadData('APPLICATION_SOP')；有数据则恢复为 Map<pid, info>（info 仅含 nextHeapId、nextShedId）；无数据则新建 Map 并 _saveApplicationSOP。  
4. 运行时为该 pid 分配 Heap/Shed 时，会确保该 pid 在 APPLICATION_SOP 中有条目，并在其 heaps/sheds 上挂载新建的 Heap/Shed，同时递增 nextHeapId/nextShedId。  
5. 保存时 _saveApplicationSOP 只写 pid 与 nextHeapId、nextShedId；_ensuringMemory 为 true 时跳过保存，_memoryCache 未就绪时延迟 100ms 再保存。

---

## 七、接手维护要点

- **扩展 per-pid 元数据**：若需持久化新字段（如某进程的配额），在 _saveApplicationSOP 的 [pid, { ... }] 中增加字段，在 _getApplicationSOP 恢复后若需默认值再补全；运行时专用字段不要写入持久化。  
- **“刷新后 nextHeapId 冲突”**：确认 _saveApplicationSOP 在进程退出或关键路径被调用，且 KernelMemory.saveData 成功；确认反序列化时 nextHeapId/nextShedId 被正确读回（含兼容旧数据无此字段时默认为 1）。  
- **“保存时循环/未保存”**：检查是否在 KernelMemory._ensuringMemory 为 true 的调用栈中触发了 _saveApplicationSOP；若 _memoryCache 未就绪，依赖 100ms 延迟保存，若 100ms 内仍未就绪则可能未写入，可考虑重试或在 KernelMemory 就绪后再写一次。  
- **“刷新后恢复堆内容”**：APPLICATION_SOP 不存堆内容；若需恢复，应在应用层或上层用其他 KernelMemory 键或 LStorage 存业务数据，与 APPLICATION_SOP 的 nextHeapId 等配合使用。
