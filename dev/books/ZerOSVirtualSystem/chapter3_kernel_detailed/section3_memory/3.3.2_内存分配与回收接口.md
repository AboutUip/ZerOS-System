# 3.3.2 内存分配与回收接口

## 本节导读（阅读目标）

本节使读者能够：**① 完全理解 allocateMemory(pid, heapSize, shedSize, ...) 的完整流程：_canAllocateMemory 检查、APPLICATION_SOP 中 per-pid 条目的创建、nextHeapId/nextShedId 的分配与 Heap/Shed 实例的创建；② 明确 _canAllocateMemory 与 LStorage 中 bios.memoryAllocation 的对应关系及默认策略；③ 掌握进程退出时与 ProcessManager 的协作及回收路径；④ 接手维护时能正确在分配前检查 BIOS、排查“内存申请被禁止”或“分配后未回收”问题。** 下文给出**带行号与中文注释的完整/关键源码**、**行为流程**与**接手维护要点**。源码文件：`kernel/memory/memoryManager.js`。

---

## 一、_canAllocateMemory 与 BIOS（约 31–54 行）

（与 3.3.1 中 _canAllocateMemory 一致，此处简述。）

从 POOL 或 window 取 LStorage；若不存在或无 `_storageData.system` 则返回 **true**（默认允许）；否则读 `LStorage._storageData.system['bios.memoryAllocation']`，仅当**明确为 false** 时返回 false，其余（含 undefined/null）返回 true。这样“未配置或读取失败时默认允许”，只有显式关闭内存申请时才禁止，便于教学与安全策略。

## 二、allocateMemory — 完整逻辑与注释（约 363–430 行）

```javascript
    static allocateMemory(pid, heapSize = -1, shedSize = -1, heapId = null, shedId = null) {
        if (!MemoryManager._canAllocateMemory()) {
            const error = new Error('内存申请已被 BIOS 设置禁止');
            MemoryManager._log(1, `拒绝为应用程序 ${pid} 分配内存: ${error.message}`);
            throw error;
        }
        if (pid != null && typeof ProcessManager?.recordKernelModuleCall === 'function') {
            ProcessManager.recordKernelModuleCall(pid, 'Memory.allocateMemory', { heapSize, shedSize });
        }

        const sop = MemoryManager.APPLICATION_SOP;
        if (!sop.has(pid)) {
            sop.set(pid, {
                heaps: new Map(),
                sheds: new Map(),
                nextHeapId: 1,
                nextShedId: 1
            });
            MemoryManager._saveApplicationSOP(sop);
        }

        const appSpace = sop.get(pid);
        let allocatedHeapId = heapId, allocatedShedId = shedId;
        let heap = null, shed = null;

        if (heapSize !== -1 && heapSize > 0) {
            if (allocatedHeapId === null || allocatedHeapId === undefined) {
                allocatedHeapId = appSpace.nextHeapId++;
            }
            if (appSpace.heaps.has(allocatedHeapId)) {
                heap = appSpace.heaps.get(allocatedHeapId);
            } else {
                heap = new Heap(pid, heapSize, allocatedHeapId);
                appSpace.heaps.set(allocatedHeapId, heap);
            }
            // shed 同理：nextShedId、Shed 实例、appSpace.sheds.set
        }

        MemoryManager._saveApplicationSOP(sop);
        return { heapId: allocatedHeapId, shedId: allocatedShedId, heap, shed };
    }
```

**行为流程**：  
1. _canAllocateMemory() 为 false 则抛错并打日志。  
2. 可选记录 ProcessManager.recordKernelModuleCall。  
3. 取 APPLICATION_SOP；若该 pid 无条目则创建 { heaps, sheds, nextHeapId: 1, nextShedId: 1 } 并 _saveApplicationSOP。  
4. 若 heapSize 有效且未指定 heapId，用 appSpace.nextHeapId++ 分配 id；若该 heapId 已存在则复用，否则 new Heap(...) 并放入 appSpace.heaps。  
5. shed 同理（shedSize、nextShedId、Shed）。  
6. 再次 _saveApplicationSOP(sop)，返回 { heapId, shedId, heap, shed }。

**设计原因**：每个 pid 独立 nextHeapId/nextShedId，避免跨进程 ID 冲突；BIOS 禁止时直接抛错，调用方需 catch 并处理“内存申请被禁止”。

---

## 三、回收与 ProcessManager 的协作

进程退出时，ProcessManager 会调用 MemoryManager 的回收接口（具体方法名以源码为准，如 **releaseMemory(pid)** 或清理该 pid 在 APPLICATION_SOP 中的条目）：释放该进程占用的 Heap/Shed 引用、从 APPLICATION_SOP 中移除该 pid 或清空其 heaps/sheds，并 _saveApplicationSOP 持久化更新后的元数据。二者通过 **pid** 关联，保证“一进程一分区、退出即回收”。若进程崩溃未正常退出，需依赖异常处理或定时扫描中调用同一回收路径，否则该 pid 的分区会一直占用直到被某处显式回收或刷新后仅剩元数据（heaps/sheds 为运行时对象，刷新后不会恢复，但 nextHeapId/nextShedId 会保留，见 3.3.1）。

---

## 四、行为流程小结（分配与回收）

1. **分配**：调用 allocateMemory(pid, heapSize, shedSize, ...) → _canAllocateMemory 检查 → 确保 APPLICATION_SOP 中有 pid 条目 → 按需分配 nextHeapId/nextShedId 并创建 Heap/Shed → _saveApplicationSOP。  
2. **回收**：ProcessManager 在进程退出路径调用 MemoryManager 回收接口 → 释放该 pid 的 heaps/sheds 引用并从 APPLICATION_SOP 移除或清空 → _saveApplicationSOP。

---

## 五、接手维护要点

- **bios.memoryAllocation 为 false**：所有通过 allocateMemory 的路径都会在入口处检查 _canAllocateMemory；分配失败时当前实现为 **throw**，调用方需 try/catch 并向上返回“内存申请被禁止”或友好提示。  
- **“分配后未回收”**：确认进程退出路径（正常退出、杀进程、异常处理）中调用了 MemoryManager 的回收接口；若新增退出方式，需补上回收调用。  
- **进程崩溃**：若未走正常退出，需在 ExceptionHandler 或类似统一出口中根据 pid 调用回收接口，或提供“按 pid 强制回收”的维护接口。
