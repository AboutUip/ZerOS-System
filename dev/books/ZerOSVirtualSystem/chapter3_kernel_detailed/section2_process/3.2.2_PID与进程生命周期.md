# 3.2.2 PID 与进程生命周期

## 本节导读（阅读目标）

本节使读者能够：**① 完全理解 PID 的分配策略（_allocatePid、_getUsedPids、_generateRandomPid）及 EXPLOIT_PID 的保留；② 明确进程状态 loading/running/exited 在 ProcessInfo 中的体现及变更时机；③ 掌握 _createProtectedProcessTable 与 _createProtectedProcessInfo 的完整 Proxy 逻辑，以及为何禁止直接 set/delete/clear 与直接修改 isExploit；④ 接手维护时能正确扩展状态、排查“PID 冲突”或“安全警告：尝试直接修改进程表”问题。** 下文给出**带行号与中文注释的完整/关键源码**、**行为流程**与**接手维护要点**。源码文件：`kernel/process/processManager.js`。

## 一、PID 与分配策略

ProcessManager 使用数字类型的 **pid** 唯一标识进程。特殊常量：

- **EXPLOIT_PID = 10000**：Exploit 程序固定 PID；D/server 服务调用内核 API 时也使用该 PID（SERVER_SERVICE_PID 同值），内核对该 PID 放行。
- **PID_MIN / PID_MAX**：随机 PID 生成范围（见 _generateRandomPid）。

普通进程的 PID 由 **_allocatePid()** 分配，保证不与已用 PID 及 EXPLOIT_PID 冲突；进程表 Map 的键即 pid，同一时刻两进程不会共用一个 pid。

## 二、_allocatePid — 完整逻辑与注释（约 1160–1208 行）

```javascript
    static _allocatePid() {
        const usedPids = ProcessManager._getUsedPids();
        const maxAttempts = 1000;
        let attempts = 0;
        let pid;

        if (usedPids.size >= (ProcessManager.PID_MAX - ProcessManager.PID_MIN + 1) * 0.9) {
            ProcessManager._log(1, `警告: 已使用的PID数量接近可用范围上限`);
        }

        do {
            pid = ProcessManager._generateRandomPid();
            attempts++;
            if (pid === ProcessManager.EXPLOIT_PID) continue;
            if (!usedPids.has(pid)) {
                usedPids.add(pid);
                return pid;
            }
            if (attempts >= maxAttempts) {
                // 降级：顺序递增寻找空位
                for (let fallbackPid = ProcessManager.PID_MIN; fallbackPid <= ProcessManager.PID_MAX; fallbackPid++) {
                    if (fallbackPid !== ProcessManager.EXPLOIT_PID && !usedPids.has(fallbackPid)) {
                        usedPids.add(fallbackPid);
                        return fallbackPid;
                    }
                }
                throw new Error(`无法分配PID：所有可用的PID都已已被使用`);
            }
        } while (attempts < maxAttempts);

        throw new Error(`PID分配失败：达到最大尝试次数 ${maxAttempts}`);
    }
```

**行为流程**：获取当前已用 PID 集合；在 maxAttempts 次内随机生成 pid；若等于 EXPLOIT_PID 则跳过；若未使用则加入 usedPids 并返回；超次后改为顺序扫描 PID_MIN~PID_MAX 找空位；若仍满则抛错。**设计原因**：随机分配降低可预测性；保留 EXPLOIT_PID 避免与 Exploit 冲突；降级保证在高占用下仍能分配。

## 三、进程状态：loading / running / exited

ProcessInfo 的 **status** 字段表示当前状态：

| 状态 | 含义 | 典型变更时机 |
|------|------|--------------|
| loading | 进程正在加载（脚本已开始执行但尚未完成初始化） | 启动时创建 ProcessInfo 后设为 loading；脚本或框架完成初始化后改为 running。 |
| running | 进程已就绪或在运行 | 初始化完成或用户恢复窗口等。 |
| exited | 进程已退出，资源待回收 | 正常退出、杀进程或异常清理时；后续可由内核回收该 pid 对应的进程表项与内存。 |

状态变更应通过 ProcessManager 的 **updateProcessInfo** 等 API 内部更新 ProcessInfo，并视需要调用 _saveProcessTable 持久化，以便刷新后能区分已退出进程与活跃进程；外部不应直接改表。

## 四、_createProtectedProcessTable — 完整源码与注释（约 239–290 行）

```javascript
    static _createProtectedProcessTable(table) {
        const protectedTable = new Map();
        for (const [pid, info] of table) {
            protectedTable.set(pid, ProcessManager._createProtectedProcessInfo(pid, info));
        }
        return new Proxy(protectedTable, {
            get(target, prop) {
                if (prop === 'get' || prop === 'has' || prop === 'entries' ||
                    prop === 'keys' || prop === 'values' || prop === 'forEach' ||
                    prop === Symbol.iterator) {
                    const method = target[prop];
                    if (typeof method === 'function') return method.bind(target);
                    return method;
                }
                if (prop === 'size') return target.size;
                if (prop === 'set' || prop === 'delete' || prop === 'clear') {
                    KernelLogger.warn("ProcessManager", `安全警告: 尝试直接修改进程表 (操作: ${prop})。请使用 ProcessManager.updateProcessInfo() 方法。`);
                    return () => { throw new Error(`安全错误: 不能直接修改进程表。请使用 ProcessManager.updateProcessInfo() 方法。`); };
                }
                return target[prop];
            },
            set(target, prop, value) {
                KernelLogger.warn("ProcessManager", `安全警告: 尝试直接设置进程表属性 (属性: ${prop})。`);
                return false;
            }
        });
    }
```

**行为流程**：复制 table 中每项，将 value 换为 _createProtectedProcessInfo(pid, info)；对复制后的 Map 做 Proxy：允许 get、has、entries、keys、values、forEach、Symbol.iterator、size；对 set/delete/clear 返回会抛错的函数并打警告；对 set trap 禁止设置属性。这样对外暴露的“进程表”为只读视图，修改必须通过 ProcessManager API。

## 五、_createProtectedProcessInfo — 完整源码与注释（约 299–336 行）

```javascript
    static _createProtectedProcessInfo(pid, info) {
        const protectedInfo = { ...info };
        return new Proxy(protectedInfo, {
            set(target, prop, value) {
                if (prop === 'isExploit') {
                    if (pid !== ProcessManager.EXPLOIT_PID) {
                        KernelLogger.error("ProcessManager", `安全错误: 进程 ${pid} 尝试修改 isExploit 标志。只有 EXPLOIT_PID 可以设置此标志。`);
                        ProcessManager._logSecurityViolation(pid, 'attempt_modify_isExploit', { ... });
                        return false;
                    }
                    if (value !== true) {
                        KernelLogger.warn("ProcessManager", `安全警告: EXPLOIT_PID 尝试将 isExploit 设置为 ${value}，已拒绝。`);
                        return false;
                    }
                }
                target[prop] = value;
                return true;
            },
            get(target, prop) {
                return target[prop];
            }
        });
    }
```

**行为流程**：对 ProcessInfo 做浅拷贝后包一层 Proxy；set 时若 prop === 'isExploit'：仅 EXPLOIT_PID 可设置且只能设为 true，否则拒绝并记录安全违规；其他字段允许写入。这样关键字段 isExploit 只能由内核逻辑对 EXPLOIT_PID 设置，防止伪造特权进程。

## 六、与 MemoryManager 的协作

进程创建时，MemoryManager 会为该 pid 在 APPLICATION_SOP 中建立或获取分区元数据（heaps/sheds、nextHeapId、nextShedId），并可按需创建 Heap/Shed（见 3.3.2）；进程退出时，ProcessManager 会协同 MemoryManager 回收该 pid 对应的内存分区，并视需要 _saveProcessTable 与 _saveApplicationSOP。进程表与 APPLICATION_SOP 通过 pid 关联，形成“进程 ↔ 内存分区”的一致视图。

---

## 七、行为流程小结（从启动到退出）

1. 启动程序时：_allocatePid() 得到 pid；创建 ProcessInfo（status 为 loading），加入进程表并 _saveProcessTable；MemoryManager.allocateMemory(pid, ...) 为该 pid 建立分区。  
2. 初始化完成后：updateProcessInfo(pid, { status: 'running' })（或等价 API），并 _saveProcessTable。  
3. 退出时：updateProcessInfo(pid, { status: 'exited', ... })；协同 MemoryManager 回收该 pid 分区；_saveProcessTable。  
4. 对外暴露的进程表为 _createProtectedProcessTable(table)，只读；ProcessInfo 为 _createProtectedProcessInfo 包装，isExploit 受保护。

---

## 八、接手维护要点

- **“PID 冲突”**：确认 _getUsedPids 正确反映当前进程表中的 pid 与持久化中的 pid；若持久化未正确加载，usedPids 可能漏掉已存在 pid。  
- **“安全警告：尝试直接修改进程表”**：调用方使用了 table.set/delete/clear 或直接改表；应改为 ProcessManager.updateProcessInfo 等官方 API。  
- **扩展状态**：若增加新状态（如 suspended），在 ProcessInfo 中增加字段并在状态变更处统一通过 updateProcessInfo 更新并 _saveProcessTable。  
- **受保护进程表与 forEach**：当前 Proxy 允许 forEach 遍历；若在回调中修改 ProcessInfo 的某个属性，由 _createProtectedProcessInfo 的 set 约束（仅 isExploit 被严格限制）；其他字段可写，若需只读可再对 protectedInfo 的更多属性做 set 拦截。
