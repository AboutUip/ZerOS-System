# 3.2.4 进程退出与资源回收

## 本节导读（阅读目标）

本节让读者**完完全全参透**进程**退出**时的**完整回收链**：谁触发退出（正常退出、杀进程、异常）、ProcessManager 如何更新进程表（status=exited）、如何通知 GUIManager 与 EventManager 清理该 pid 的窗口与事件、以及 MemoryManager 是否/如何释放该 pid 的内存分区。学完后能说出“进程退出后哪些资源必须被回收、在代码中由谁负责”，并能排查“退出后窗口仍存在”或“事件仍触发”。源码：`kernel/process/processManager.js`、`system/ui/guiManager.js`、`system/ui/eventManager.js`。

---

## 一、退出的触发点

- **正常退出**：应用脚本或框架调用“退出”API（如 ProcessManager 暴露的 exit 或 kill 接口），或窗口关闭时由 onClose 回调触发退出逻辑。
- **杀进程**：用户或系统调用 **ProcessManager.killProcess(pid)**（或等价），强制将进程标记为退出并执行回收。
- **异常**：未捕获异常可能导致进程被标记为异常退出，由 ExceptionHandler 或统一出口触发回收。

---

## 二、回收链（按顺序）

1. **ProcessManager**：将 ProcessInfo.status 置为 'exited'，可选记录 exitTime；**_saveProcessTable(table)**；从进程表或内部列表中移除该 pid 的“活跃”引用（具体以源码为准）。
2. **GUIManager**：调用 **GUIManager.unregisterAllWindowsByPid(pid)**，移除该 pid 下所有窗口（从 _windows 与 _pidToWindows 删除，并从 DOM 移除元素）；**unregisterTaskbarPreviewProvider(pid)**（若存在）。
3. **EventManager**：调用 **EventManager.unregisterAllByPid(pid)**，移除该 pid 注册的所有事件处理程序（从 _eventHandlers 与 _pidToHandlers 清理）。
4. **MemoryManager**：该 pid 在 APPLICATION_SOP 中的分区（heaps、sheds）可保留元数据（nextHeapId、nextShedId）供 _saveApplicationSOP 持久化，**运行时 Heap/Shed 对象**可被 GC 回收（若不再被引用）；若内核提供 **releaseMemory(pid)** 或等价接口，应在此处调用以显式从 APPLICATION_SOP 移除该 pid 或清空其 heaps/sheds，并 _saveApplicationSOP。

**关键**：回收必须由**同一处**（如 ProcessManager 的 exit/kill 路径）**依次**调用 GUIManager、EventManager、MemoryManager 的清理接口，否则会出现“进程已死但窗口仍在”或“事件仍触发”。

---

## 三、本节小结与维护要点

- 退出时：ProcessManager 更新表并持久化 → GUIManager 移除窗口与预览 → EventManager 移除事件 → MemoryManager 释放或标记该 pid 分区。
- 排查“退出后窗口仍在”：确认退出路径是否调用了 unregisterAllWindowsByPid(pid)。
- 排查“退出后事件仍触发”：确认是否调用了 unregisterAllByPid(pid)。
