# 3.2.1 进程表与 KernelMemory

## 本节导读（阅读目标）

## 一、进程表的数据结构（源码注释约 74–96 行）

进程表在内存中为 **Map<number, ProcessInfo>**，键为 **pid**（数字），值为 **ProcessInfo** 普通对象。ProcessInfo 字段含义与序列化约定如下：

| 字段 | 类型 | 含义 | 序列化/恢复说明 |
|------|------|------|-----------------|
| pid | number | 进程 ID | 直接序列化。 |
| programName / programNameUpper | string | 程序名及大写形式（用于 __init__/__exit__ 等调用） | 直接序列化。 |
| scriptPath | string | 脚本路径 | 直接序列化。 |
| status | string | 'loading' \| 'running' \| 'exited' | 直接序列化。 |
| startTime / exitTime | number \| null | 启动/退出时间戳 | 直接序列化。 |
| memoryRefs | Map<string, any> | 该进程占用的内存引用 | 序列化为 `Array.from(map.entries())`；恢复时 `new Map(info.memoryRefs)`。 |
| domElements | Set<Element> | 该进程创建的 DOM 元素 | **不序列化**；保存时只存 domElementsCount；恢复时置为 `new Set()`。 |
| mutationObserver | MutationObserver \| null | DOM 观察器 | **不序列化**；恢复时为 null。 |
| requestedModules | Set<string> | 该进程请求的动态模块 | 序列化为 `Array.from(set)`；恢复时 `new Set(info.requestedModules)`。 |
| isBackground | boolean | 是否后台进程 | 直接序列化；旧数据无此时默认为 false。 |
| windowState / isMinimized 等 | 见源码 | UI 相关状态 | 直接序列化（若为简单类型）。 |

## 二、_getProcessTable — 完整源码与注释（约 103–184 行）

```javascript
    static _getProcessTable() {
        // 【降级】KernelMemory 未定义（如引导期尚未加载）时使用内存内 fallback Map，避免抛错
        if (typeof KernelMemory === 'undefined') {
            if (!ProcessManager._fallbackProcessTable) {
                ProcessManager._fallbackProcessTable = new Map();
            }
            return ProcessManager._fallbackProcessTable;
        }

        const data = KernelMemory.loadData('PROCESS_TABLE');
        if (data) {
            const map = new Map();
            if (Array.isArray(data)) {
                for (const [pid, info] of data) {
                    const deserializedInfo = { ...info };
                    if (deserializedInfo.isBackground === undefined) deserializedInfo.isBackground = false;

                    if (Array.isArray(info.memoryRefs)) {
                        deserializedInfo.memoryRefs = new Map(info.memoryRefs);
                    } else if (!(info.memoryRefs instanceof Map)) {
                        deserializedInfo.memoryRefs = new Map();
                    }
                    deserializedInfo.domElements = new Set();
                    deserializedInfo.mutationObserver = null;
                    if (Array.isArray(info.requestedModules)) {
                        deserializedInfo.requestedModules = new Set(info.requestedModules);
                    } else if (!(info.requestedModules instanceof Set)) {
                        deserializedInfo.requestedModules = new Set();
                    }
                    map.set(pid, deserializedInfo);
                }
            } else if (typeof data === 'object') {
                for (const [pid, info] of Object.entries(data)) {
                    const deserializedInfo = { ...info };
                    if (deserializedInfo.isBackground === undefined) deserializedInfo.isBackground = false;
                    // memoryRefs / domElements / mutationObserver / requestedModules 同上
                    map.set(parseInt(pid), deserializedInfo);
                }
            }
            return map;
        }

        // 无数据时创建新 Map 并立即持久化，保证下次可读
        const newMap = new Map();
        ProcessManager._saveProcessTable(newMap);
        return newMap;
    }
```

**行为流程**：  
1. KernelMemory 未定义 → 返回 _fallbackProcessTable（单例空 Map）。  
2. data = KernelMemory.loadData('PROCESS_TABLE')。  
3. 若 data 存在：按数组或对象格式遍历，对每条 [pid, info] 做浅拷贝后：恢复 memoryRefs 为 Map、requestedModules 为 Set；domElements 置空 Set、mutationObserver 置 null；isBackground 默认 false；写入 map 并返回。  
4. 若 data 不存在：new Map()，_saveProcessTable(newMap)，返回 newMap。

**设计原因**：DOM 与 MutationObserver 无法跨会话恢复，故只恢复“可序列化”的元数据；requestedModules 与 memoryRefs 需保持集合/映射结构，故用数组形式存盘再恢复为 Map/Set。

## 三、_saveProcessTable — 完整源码与注释（约 190–231 行）

```javascript
    static _saveProcessTable(table) {
        if (typeof KernelMemory === 'undefined') return;

        const array = Array.from(table.entries()).map(([pid, info]) => {
            const serializedInfo = { ...info };
            if (info.memoryRefs instanceof Map) {
                serializedInfo.memoryRefs = Array.from(info.memoryRefs.entries());
            }
            if (info.domElements instanceof Set) {
                serializedInfo.domElementsCount = info.domElements.size;
                serializedInfo.domElements = [];
            }
            if (info.mutationObserver) serializedInfo.mutationObserver = null;
            if (info.requestedModules instanceof Set) {
                serializedInfo.requestedModules = Array.from(info.requestedModules);
            } else if (!Array.isArray(info.requestedModules)) {
                serializedInfo.requestedModules = [];
            }
            return [pid, serializedInfo];
        });

        KernelMemory.saveData('PROCESS_TABLE', array);
        ProcessManager._processTableCache = table;
    }
```

**行为流程**：  
1. KernelMemory 未定义则直接 return。  
2. 将 table 转为数组：每项 [pid, info]，info 浅拷贝后：memoryRefs 转为 entries 数组；domElements 只存 size（domElementsCount），domElements 置 []；mutationObserver 置 null；requestedModules 转为数组。  
3. KernelMemory.saveData('PROCESS_TABLE', array)；更新 _processTableCache = table。

**注意**：domElements 与 mutationObserver 不写入持久化，刷新后无法恢复；若需“刷新后恢复窗口”，需在应用层或 KernelMemory 层另存窗口元数据（如位置、大小），见课后思考。

---

## 四、行为流程小结（进程表从持久化到内存）

1. 某处（如 getProcessTable 或启动进程）调用 _getProcessTable()。  
2. 若 KernelMemory 不可用 → 返回 fallback Map。  
3. 否则 loadData('PROCESS_TABLE')；有数据则反序列化为 Map（含 Map/Set 恢复与不可序列化字段的占位）；无数据则新建 Map 并 _saveProcessTable。  
4. 进程创建/退出/状态变更时，内部会更新该 Map 并调用 _saveProcessTable(table)，将当前表序列化后写入 KernelMemory，并更新 _processTableCache。

---

## 五、接手维护要点

- **扩展 ProcessInfo 字段**：若为简单类型（number/string/boolean），直接加入序列化对象即可；若为 Map/Set，需在 _saveProcessTable 中转为数组、在 _getProcessTable 中从数组恢复；若为 DOM/函数等不可序列化，与 domElements 一样只做占位恢复（如空 Set/null）。  
- **“刷新后进程丢失”**：检查是否在关键路径调用了 _saveProcessTable（如进程退出、状态变更后）；检查 KernelMemory.saveData 是否成功、键名是否为 'PROCESS_TABLE'。  
- **“刷新后状态错乱”**：检查反序列化是否兼容旧数据（如 isBackground、requestedModules 从对象格式恢复）；若曾改过 ProcessInfo 结构，需兼容旧字段或做迁移。  
- **多线程/并发**：ZerOS 当前为单线程；若未来多 Worker，对同一 table 的读写在同一次事件循环内完成，避免交叉写；若需加锁，应在 KernelMemory 或 ProcessManager 层统一加。
