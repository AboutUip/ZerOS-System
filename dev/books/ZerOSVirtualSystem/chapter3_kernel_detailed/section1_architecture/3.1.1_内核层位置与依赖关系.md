# 3.1.1 内核层的位置与依赖关系

## 本节导读

内核层在 ZerOS 中对应“阶段三：模块加载”里、在类型池与文件系统基础模块之后、在进程管理（ProcessManager）及后续事件与 GUI 之前（或与之交错）的那一段。本节结合第 2 章 MODULE_DEPENDENCIES 与拓扑排序的结果，说明**内核层主要模块的加载顺序**及其对 KernelMemory、POOL 的依赖关系，为后续 3.2–3.4 节的代码解析建立上下文。

---

## 一、从 MODULE_DEPENDENCIES 看内核层顺序

在 starter.js 的 MODULE_DEPENDENCIES 中，与内核层直接相关的模块及其依赖可概括为（按“层”从前到后）：

1. **类型池 / 枚举**：enumManager、logLevel、addressType、fileType 等，无依赖或仅依赖 enumManager，最先加载。
2. **文件系统基础**：fileFramework、disk、nodeTree 依赖 fileType；filesystem/init.js 依赖 disk、nodeTree、fileFramework，完成文件系统挂接。
3. **内存管理**：heap、shed、memoryManager 依赖 logLevel、addressType 及 heap/shed；kernelMemory、memoryUtils 依赖 memoryManager 等。KernelMemory 提供 loadData/saveData，是进程表、内存分区元数据、磁盘分区列表等持久化的入口。
4. **进程管理**：applicationAssets、applicationAssetManager、programCategories、**processManager** 依赖 memoryManager、kernelMemory、applicationAssetManager。ProcessManager 依赖 MemoryManager 与 KernelMemory，用于进程表与内存分区管理。
5. **事件与系统层**：eventManager 依赖 processManager；其后 guiManager、contextMenuManager 等依赖 processManager 与 eventManager，进入系统层。

因此“内核层”在本书中主要指：**类型池 → 文件系统（fileFramework、disk、nodeTree、init）→ 内存（heap、shed、memoryManager、kernelMemory）→ 进程（processManager）** 这一段；事件与 GUI 虽也依赖进程，但归入系统层更符合第 1 章的分层。

---

## 二、内核层对 KernelMemory 与 POOL 的依赖

- **KernelMemory**：由 memory 相关模块提供，对外暴露 loadData(key)、saveData(key, value)。ProcessManager 用其存储 PROCESS_TABLE（进程表序列化）；MemoryManager 用其存储 APPLICATION_SOP（各 pid 的堆/栈元数据）、PROGRAM_NAMES 等；Disk 用其存储 DISK_SEPARATE_MAP（分区名列表）等。因此 KernelMemory 必须在 ProcessManager、MemoryManager、Disk 使用前就绪，对应依赖图中 kernelMemory 在 processManager 与 disk 之前。
- **POOL**：各模块在初始化时向 POOL 注册自身或子组件（如 Dependency、ProcessManager、LStorage、各分区 NodeTreeCollection），供其他模块通过 __GET__ 获取。Disk 的分区对象（NodeTreeCollection）存在 POOL 中，Disk 自身只在 KernelMemory 中存分区名列表，避免将不可序列化的复杂对象写入 KernelMemory。

这样，**KernelMemory = 可序列化状态与元数据的存储，POOL = 运行时单例与复杂对象的注册表**，二者配合完成内核层的状态持久化与模块发现。

---

## 三、行为流程小结（内核层加载顺序）

1. BootLoader 按 MODULE_DEPENDENCIES 拓扑排序后，先加载类型池/枚举（enumManager、logLevel、addressType、fileType 等）。  
2. 再加载文件系统基础（fileFramework、disk、nodeTree、filesystem/init）；init 完成文件系统挂接，分区可在此阶段注册到 POOL。  
3. 再加载内存相关（heap、shed、memoryManager、kernelMemory、memoryUtils）；KernelMemory 提供 loadData/saveData，此后 ProcessManager、MemoryManager、Disk 才可依赖其做持久化。  
4. 再加载进程管理（applicationAssets、applicationAssetManager、programCategories、processManager）；ProcessManager 依赖 MemoryManager 与 KernelMemory。  
5. 最后加载事件与系统层（eventManager、guiManager 等）。因此若 KernelMemory 在 ProcessManager 之后加载，ProcessManager 在访问 KernelMemory.loadData('PROCESS_TABLE') 时会得到 undefined 或需降级到 fallback。

## 四、接手维护要点

- **调整内核模块顺序**：修改 starter.js 的 MODULE_DEPENDENCIES 时，保持 kernelMemory 在 processManager、memoryManager、disk 之前；保持 memoryManager 在 processManager 之前。  
- **新增依赖 KernelMemory 的模块**：在 MODULE_DEPENDENCIES 中为该模块添加对 kernelMemory 的依赖，并避免循环依赖。

## 五、本节小结

内核层在引导顺序上位于类型池与文件系统基础之后、进程管理及事件/系统层之前；其核心模块（ProcessManager、MemoryManager、Disk）依赖 KernelMemory 做持久化、依赖 POOL 做注册与发现；KernelMemory 由 memory 子模块提供，是进程表、内存分区、磁盘分区元数据等的存储中心。
