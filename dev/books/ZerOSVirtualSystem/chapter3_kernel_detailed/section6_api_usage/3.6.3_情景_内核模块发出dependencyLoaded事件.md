# 3.6.3 情景：内核模块发出 dependencyLoaded 事件

## 情景描述

在 ZerOS 中，模块加载往往是**有依赖顺序的**：例如，某些系统扩展需要在内核和基础服务就绪后再执行。为此，内核和系统层使用类似 `dependencyLoaded` 的事件作为“就绪信号”，通知其它模块“某依赖已经准备好，可以继续初始化”。

本节以简化示例说明：某内核模块在完成自身初始化后，通过事件系统发出“已就绪”的信号。

---

## 前置条件

- 事件系统（如 `EventManager` 或内核级事件总线）已初始化，并注册到 `POOL` 中。
- 其它模块在启动时会订阅对应的 `dependencyLoaded:XXX` 事件。

---

## 核心代码：发出 dependencyLoaded 事件

```js
// 位于某内核模块（例如 KernelMemory 或 Disk）初始化逻辑末尾
function _onModuleReady() {
    const EventBus = POOL.get('KernelEventBus'); // 名称示意，实际以源码为准
    if (!EventBus) {
        throw new Error('KernelEventBus 未就绪，无法发送 dependencyLoaded 事件');
    }

    EventBus.emit('dependencyLoaded', {
        name: 'KernelMemory',
        timestamp: Date.now()
    });
}
```

要点：

- 这里使用了一个抽象的 `KernelEventBus`，在真实代码中可能是 `EventManager` 或专门的内核信号模块。
- 事件名统一用 `'dependencyLoaded'`，通过 payload 中的 `name` 字段区分具体哪个模块就绪。

---

## 订阅方（概念示例）

```js
// 某依赖 KernelMemory 的模块
function _waitForKernelMemory() {
    const EventBus = POOL.get('KernelEventBus');
    if (!EventBus) return;

    EventBus.on('dependencyLoaded', (payload) => {
        if (payload.name === 'KernelMemory') {
            // 知道 KernelMemory 已就绪，可以继续自己的初始化
            continueInitWithKernelMemory();
        }
    });
}
```

---

## 行为小结

| 步骤 | 行为 |
|------|------|
| 模块 A 初始化完成 | 通过事件总线 `emit('dependencyLoaded', { name: 'KernelMemory' })` 发出就绪信号 |
| 模块 B 等待依赖 | 在启动时订阅 `dependencyLoaded`，在 payload.name 匹配时继续初始化 |

通过这个情景，读者可以把 `dependencyLoaded` 看作内核内部的“生命周期事件”，用于在模块间传递“初始化阶段进度”，而不必写死初始化顺序。
