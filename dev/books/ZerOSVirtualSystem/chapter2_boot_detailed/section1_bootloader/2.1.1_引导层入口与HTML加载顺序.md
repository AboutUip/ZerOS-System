# 2.1.1 引导层入口与 HTML 加载顺序

## 本节导读（阅读目标）

本节使读者能够：**① 完全理解 ZerOS 引导层“入口”从何开始（HTML 解析与脚本执行顺序）；② 明确 HTML 中四个脚本的先后顺序及每一顺序的设计原因；③ 知道 starter.js 以 IIFE 形式执行、何时注册 DOMContentLoaded 与何时调用 start_init；④ 接手维护时能正确调整入口页脚本、排查“KernelLogger/DependencyConfig/POOL 未定义”问题。** 下文给出**与源码对应的脚本顺序说明**、**starter.js 末尾入口逻辑的带注释代码**、**行为流程**与**接手维护要点**。源码文件：入口 HTML（如 `test/index.html`）、`bootloader/starter.js`。

---

## 一、入口：页面加载

ZerOS 的引导层**入口**是承载系统的 HTML 页面（如项目中的 `test/index.html`）。浏览器解析到 `<script src="...">` 时会按出现顺序依次加载并**同步执行**脚本（未使用 `async`/`defer` 时，会阻塞后续 DOM 解析直到该脚本执行完毕）。因此，**脚本在 HTML 中的书写顺序即执行顺序**，引导层通过控制该顺序保证 KernelLogger、DependencyConfig、POOL 在 BootLoader 逻辑（starter.js 内的 start_init）之前就绪。

---

## 二、HTML 中的四个脚本顺序（与第 1 章对应）

在典型入口 HTML 中，与引导层直接相关的脚本通常为以下四个（路径以项目为准）：

| 顺序 | 脚本 | 作用 | 为何必须此顺序 |
|------|------|------|----------------|
| 1 | **KernelLogger**（如 `../kernel/core/logger/kernelLogger.js`） | 日志系统，无依赖 | 最先加载，后续所有模块都依赖 `KernelLogger.info` 等；若放后面，执行到 DependencyConfig/POOL 时可能报错。 |
| 2 | **DependencyConfig**（如 `../kernel/core/signal/dependencyConfig.js`） | 依赖配置类，提供 dependencyMap、waitLoaded、publishSignal | 其源码会使用 KernelLogger；且 BootLoader 的 waitForCoreModules 会 `new DependencyConfig()`，必须在此脚本之后。 |
| 3 | **POOL**（如 `../kernel/core/signal/pool.js`） | 全局对象池 | 内部使用 KernelLogger；且会调用 `DependencyConfig.publishSignal(...)` 发布自身路径，故需在 DependencyConfig 之后。start_init 中会 `POOL.__INIT__("KERNEL_GLOBAL_POOL")` 并 __ADD__ Dependency，故必须在 starter.js 之前。 |
| 4 | **BootLoader**（如 `../bootloader/starter.js`） | 启动器本体 | 依赖上述三者；执行后完成安全校验、依赖图构建与按序加载所有模块（见 2.1.2）。 |

顺序可概括为：**KernelLogger → DependencyConfig → POOL → starter.js**。前三个对应第 1 章图中的“阶段一：HTML 加载”；starter.js 执行后进入“阶段二：BootLoader 初始化”与“阶段三：模块加载”。

## 三、starter.js 的 IIFE 与入口注册（starter.js 约 1699–1732 行）

starter.js 整体包裹在**立即执行函数（IIFE）**中，执行到末尾时完成两件事：**① 决定何时调用 start_init；② 将 start_init 暴露给 window 或 POOL。**

```javascript
    // 自动启动：根据 DOM 是否已就绪选择监听或立即执行
    if (document.readyState === 'loading') {
        document.addEventListener('DOMContentLoaded', start_init);
    } else {
        // DOM 已就绪，立即启动（避免重复监听）
        start_init().catch(error => {
            if (typeof KernelLogger !== 'undefined') {
                KernelLogger.error("BootLoader", "启动失败", error);
            } else {
                console.error("[内核][BootLoader] 启动失败", error);
            }
        });
    }

    // 导出启动函数：优先通过 POOL 管理，POOL 不可用时降级到 window
    if (typeof window !== 'undefined') {
        if (typeof POOL !== 'undefined' && typeof POOL.__ADD__ === 'function') {
            try {
                if (!POOL.__HAS__("KERNEL_GLOBAL_POOL")) {
                    POOL.__INIT__("KERNEL_GLOBAL_POOL");
                }
                POOL.__ADD__("KERNEL_GLOBAL_POOL", "startKernel", start_init);
            } catch (e) {
                window.startKernel = start_init;
            }
        } else {
            window.startKernel = start_init;
        }
        window.BootLoader = {
            loadScript: loadScript,
            waitForCoreModules: waitForCoreModules,
            start: start_init,
            performKernelSelfCheck: performKernelSelfCheck,
        };
    }
```

**行为流程**：  
1. 若 `document.readyState === 'loading'`，则只注册 `DOMContentLoaded` 监听，**不立即执行** start_init；等 DOM 解析完毕再触发 start_init。  
2. 否则认为 DOM 已就绪，**立即**执行 `start_init().catch(...)`，避免重复监听。  
3. 随后将 start_init 写入 POOL（"startKernel"）或 window.startKernel，并挂载 BootLoader 对象（loadScript、waitForCoreModules、start、performKernelSelfCheck）。

**为何等 DOMContentLoaded**：保证 DOM 可用后再做后续 UI 相关初始化（如挂载根节点、绑定事件），避免脚本在 DOM 未就绪时访问 document 导致异常。

---

## 四、为何不把更多模块写在 HTML 里？

若把所有模块都写成静态 `<script>`，则：依赖关系难以维护、无法按拓扑序并行加载、循环依赖难以检测。因此只有**无循环且必须最先就绪**的少数模块放在 HTML 中，其余由 BootLoader 根据 MODULE_DEPENDENCIES 动态 loadScript，既保证顺序又便于扩展（见 2.3.1、2.3.2）。

---

## 五、行为流程小结（从打开页面到 start_init 被调用）

1. 浏览器解析 HTML，按顺序加载并执行：KernelLogger → DependencyConfig → POOL → starter.js。  
2. starter.js（IIFE）执行：定义 loadScript、topologicalSort、loadModules、waitForCoreModules、start_init 等；执行到末尾。  
3. 若 document.readyState === 'loading'，注册 DOMContentLoaded → 用户无操作则随后触发 → 调用 start_init()。  
4. 若 document.readyState 已非 loading，直接 start_init().catch(...)。  
5. start_init 内部先检查 KernelLogger、再 waitForCoreModules（见 2.1.2），然后创建 Dependency、初始化 POOL、设置系统加载标志等。

---

## 六、接手维护要点

- **“KernelLogger/DependencyConfig/POOL 未定义”**：检查 HTML 中脚本顺序是否严格为 KernelLogger → DependencyConfig → POOL → starter.js；检查路径是否正确、是否被缓存或部署遗漏。  
- **调整入口页**：新增或移动脚本时，保持上述四者顺序；其他业务脚本建议由 BootLoader 通过 MODULE_DEPENDENCIES 加载，不要插在这四者之间破坏依赖。  
- **手动触发启动**：可调用 `window.startKernel()` 或 `POOL.__GET__("KERNEL_GLOBAL_POOL", "startKernel")()`（需在 POOL 与 start_init 注册之后）。
