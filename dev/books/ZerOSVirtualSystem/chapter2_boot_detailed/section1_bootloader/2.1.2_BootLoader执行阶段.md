# 2.1.2 BootLoader 执行阶段

## 本节导读（阅读目标）

本节使读者能够：**① 完全理解 start_init 从第一行到 loadModules 的每一步在源码中的位置与作用；② 明确 waitForCoreModules 的完整逻辑（markAsLoaded、waitLoaded、超时 catch）；③ 明确“阶段一：依赖与对象池准备”“阶段二：SystemInformation + RandomSecurity”“阶段三：loadModules”的边界与对应行号；④ 接手维护时能正确在 start_init 中插入步骤或排查“卡在等待核心模块/RandomSecurity”问题。** 下文给出**带行号与中文注释的 start_init 与 waitForCoreModules 关键代码**、**行为流程**与**接手维护要点**。源码文件：`bootloader/starter.js`。

---

## 一、何时真正“启动”

starter.js 加载后以 IIFE 形式执行，**真正开始引导**的逻辑在 **DOMContentLoaded** 触发时（或若 `document.readyState !== 'loading'` 则立即）调用的 **start_init**。入口逻辑在 starter.js 末尾（约 1699–1710 行），见 2.1.1。

## 二、waitForCoreModules — 完整逻辑与注释（约 1017–1109 行）

```javascript
    async function waitForCoreModules() {
        KernelLogger.info("BootLoader", "等待核心模块初始化");

        // 【硬性检查】三者任一未定义则抛错，保证 HTML 顺序正确
        if (typeof KernelLogger === 'undefined') {
            throw new Error("KernelLogger 未加载，请确保在 HTML 中加载 kernelLogger.js");
        }
        if (typeof DependencyConfig === 'undefined') {
            throw new Error("DependencyConfig 未加载，请确保在 HTML 中加载 dependencyConfig.js");
        }
        if (typeof POOL === 'undefined') {
            throw new Error("POOL 未加载，请确保在 HTML 中加载 pool.js");
        }

        // 临时实例，仅用于“等待信号”；与 start_init 内正式注册的 Dependency 不是同一个
        const Dependency = new DependencyConfig();

        // 若核心模块已在 HTML 中执行并 publishSignal，dependencyMap 中可能已有条目；
        // 若未发布或路径不一致，则需先确保有条目再根据“全局是否存在”标记 loaded
        const markAsLoaded = (moduleName) => {
            if (!Dependency.dependencyMap.has(moduleName)) {
                Dependency.dependencyMap.set(moduleName, DependencyConfig.generate(moduleName));
                Dependency.dependencyMap.get(moduleName).linked = true;
            }
            const entry = Dependency.dependencyMap.get(moduleName);
            if (moduleName === "../kernel/core/signal/dependencyConfig.js" && typeof DependencyConfig !== 'undefined') {
                entry.inited = true;
                entry.loaded = true;
                return true;
            }
            if (moduleName === "../kernel/core/signal/pool.js" && typeof POOL !== 'undefined') {
                entry.inited = true;
                entry.loaded = true;
                return true;
            }
            return entry.loaded;
        };

        const dependencyConfigLoaded = markAsLoaded("../kernel/core/signal/dependencyConfig.js");
        const poolLoaded = markAsLoaded("../kernel/core/signal/pool.js");

        if (dependencyConfigLoaded && poolLoaded) {
            KernelLogger.info("BootLoader", "核心模块已初始化完成");
            return;
        }

        // 未完全就绪则等待；超时后 catch 并尝试再次 markAsLoaded，避免因信号路径不一致永久阻塞
        const waitPromises = [];
        if (!dependencyConfigLoaded) {
            waitPromises.push(
                Dependency.waitLoaded("../kernel/core/signal/dependencyConfig.js", { interval: 10, timeout: 500 })
                    .catch(() => {
                        if (markAsLoaded("../kernel/core/signal/dependencyConfig.js")) {
                            KernelLogger.debug("BootLoader", "dependencyConfig.js 已加载");
                        } else {
                            KernelLogger.warn("BootLoader", "dependencyConfig.js 初始化信号未收到，继续执行");
                        }
                    })
            );
        }
        if (!poolLoaded) {
            waitPromises.push(
                Dependency.waitLoaded("../kernel/core/signal/pool.js", { interval: 10, timeout: 500 })
                    .catch(() => { /* 同上逻辑 */ })
            );
        }
        if (waitPromises.length > 0) {
            await Promise.all(waitPromises);
        }
        KernelLogger.info("BootLoader", "核心模块初始化完成");
    }
```

**行为流程**：  
1. 检查 KernelLogger、DependencyConfig、POOL 全局存在，否则 throw。  
2. 新建临时 Dependency，用 markAsLoaded 为 dependencyConfig.js / pool.js 在 dependencyMap 中确保条目，并根据“全局是否已有对应对象”直接设 loaded。  
3. 若两者都已 loaded，直接 return。  
4. 否则对未就绪的模块 waitLoaded(..., { interval: 10, timeout: 500 })；超时 catch 后再次 markAsLoaded，若仍能通过“全局存在”判定则视为就绪，打 warn 后继续。  
5. await Promise.all(waitPromises) 后结束。

**设计原因**：HTML 中已加载的脚本可能已执行完 publishSignal，但 publishSignal 使用的路径可能与 waitLoaded 的 moduleName 不一致；markAsLoaded 用“全局对象是否存在”做兜底，避免因路径字符串差异导致永远等不到 loaded。

## 三、阶段一：依赖与对象池准备（start_init 约 1114–1154 行）

在 **start_init** 内依次执行：

| 步骤 | 行号 | 代码要点 | 作用 |
|------|------|----------|------|
| 1 | 1116–1119 | `if (typeof KernelLogger === 'undefined') throw ...` | 再次保证 KernelLogger 存在。 |
| 2 | 1125 | `await waitForCoreModules();` | 等待核心模块（DependencyConfig、POOL）初始化信号或超时兜底。 |
| 3 | 1127 | `const Dependency = new DependencyConfig();` | 创建**正式**依赖管理实例，供后续 addDependency、waitLoaded 使用。 |
| 4 | 1131–1134 | `if (!POOL.__HAS__("KERNEL_GLOBAL_POOL")) POOL.__INIT__("KERNEL_GLOBAL_POOL");` | 确保 KERNEL_GLOBAL_POOL 类别存在。 |
| 5 | 1136–1140 | `if (!POOL.__IS_SYSTEM_LOADING__()) POOL.__ADD__(..., POOL.__SYSTEM_LOADING_FLAG__, true);` | 设置系统加载标志，供 LStorage 等在引导期做权限判断。 |
| 6 | 1142–1148 | `POOL.__ADD__("KERNEL_GLOBAL_POOL", "Dependency", Dependency);` 与 WORK_SPACE "C:" | 注册 Dependency 与工作区根路径。 |
| 7 | 1150–1153 | `Object.keys(MODULE_DEPENDENCIES).forEach(module => Dependency.addDependency(module));` | 将依赖图所有键加入 Dependency，供拓扑与 waitLoaded 使用。 |

对应第 1 章“阶段二：BootLoader 初始化”中的“构建依赖图”与“对象池就绪”。

## 四、阶段二：强制先加载 SystemInformation 与 RandomSecurity（约 1155–1176 行）

在进入 MODULE_DEPENDENCIES 的拓扑加载之前，**强制**先做两件事：

```javascript
            // 强制先加载 SystemInformation（多后端服务 URL 等，安全脚本依赖）
            await loadScript(SYSTEM_INFORMATION_MODULE);

            Dependency.addDependency(RANDOM_SECURITY_MODULE);
            await loadScript(RANDOM_SECURITY_MODULE);
            try {
                await Dependency.waitLoaded(RANDOM_SECURITY_MODULE, { interval: 50, timeout: 15000 });
                // ...
            } catch (e) {
                KernelLogger.error("BootLoader", `RandomSecurity 等待超时或失败: ${e.message}`, e);
                throw e;  // 安全校验失败则终止引导
            }
```

- **SystemInformation**：提供系统/内核版本及多后端服务 URL，安全脚本依赖其获取服务地址，必须在 RandomSecurity 之前加载。  
- **RandomSecurity**：引导前安全校验（如 JWT）。loadScript 后**必须** waitLoaded(15000ms)，确保模块完全执行并 publishSignal 后再继续；超时则 throw，终止引导。

这两步不在 MODULE_DEPENDENCIES 的拓扑序中单独列出，但在代码中显式优先执行。

---

## 五、阶段三：loadModules(MODULE_DEPENDENCIES)（约 1178–1180 行）

RandomSecurity 就绪后，调用 **loadModules(MODULE_DEPENDENCIES)**，进入第 1 章图中的“阶段三：模块加载”。loadModules 内部会：  
1. 对 MODULE_DEPENDENCIES 做**拓扑排序**（见 2.3.1）；  
2. 按**层级**分组，同层**并行** loadScript（见 2.3.2）；  
3. 每加载一个脚本后，通过 POOL 取 Dependency，将当前模块在 dependencyMap 中标记为 linked，并可选 waitLoaded(module) 等待该模块初始化完成再继续。

---

## 六、行为流程小结（start_init 主流程）

1. 检查 KernelLogger → await waitForCoreModules()。  
2. new DependencyConfig()；POOL.__INIT__("KERNEL_GLOBAL_POOL")（若尚未）；设置系统加载标志；注册 Dependency、WORK_SPACE；addDependency(MODULE_DEPENDENCIES 所有键)。  
3. await loadScript(SYSTEM_INFORMATION_MODULE)；await loadScript(RANDOM_SECURITY_MODULE)；await Dependency.waitLoaded(RANDOM_SECURITY_MODULE, { timeout: 15000 })（失败则 throw）。  
4. await loadModules(MODULE_DEPENDENCIES)。  
5. 后续：LanguagesExpansion._ready、SystemExpansion._ready、ExceptionHandler 等（见 starter.js 1182 行起）。

---

## 七、接手维护要点

- **“卡在等待核心模块”**：检查 HTML 顺序与路径；检查 dependencyConfig.js / pool.js 是否在文件末尾调用了 `DependencyConfig.publishSignal("...")` 且路径与 waitForCoreModules 中的字符串一致；若不一致可改 waitForCoreModules 的 moduleName 或改模块内 publishSignal 的路径。  
- **“RandomSecurity 超时”**：检查 randomSecurity.js 是否在就绪后调用了 publishSignal(RANDOM_SECURITY_MODULE)；网络或 JWT 过慢时可适当增大 timeout（当前 15000ms）。  
- **在 start_init 中插入步骤**：在 loadModules 之前插入时注意不要破坏“SystemInformation → RandomSecurity（并等待）→ loadModules”的顺序；在 loadModules 之后插入则属“系统扩展就绪”阶段，可参考现有 LanguagesExpansion._ready 的写法。
