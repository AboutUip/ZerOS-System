# 2.1.3 HTML 脚本阻塞语义与 async/defer

## 本节导读（阅读目标）

本节让读者**完完全全参透**浏览器对 `<script src="...">` 的**解析与执行语义**：默认（无 async/defer）时如何阻塞 DOM 解析、脚本执行顺序如何保证、以及 ZerOS 为何**不在**入口脚本上使用 async/defer，从而保证 KernelLogger → DependencyConfig → POOL → starter.js 的严格顺序。学完后能解释“脚本顺序即执行顺序”的底层原因，并能判断在何种场景下可安全使用 async/defer。参考：HTML 规范与 `bootloader/starter.js`、入口 HTML。

---

## 一、默认 script 的阻塞与顺序语义

当浏览器解析到 `<script src="url"></script>`（无 **async**、无 **defer**）时：

1. **停止 DOM 解析**：暂停对后续 HTML 的解析，直到该脚本**下载完成并执行完毕**。
2. **执行顺序**：多个此类 script 按**在文档中的出现顺序**依次下载并执行；前一个脚本执行完后才下载/执行下一个。
3. **与 DOM 的关系**：脚本执行时，其**之前的** DOM 已解析完成；其之后的 DOM 尚未解析。因此若脚本中有 `document.querySelector(...)`，只能访问到该 script 标签之前的节点。

因此，**“HTML 中书写顺序 = 执行顺序”** 在无 async/defer 时由规范保证。ZerOS 入口 HTML 中 KernelLogger → DependencyConfig → POOL → starter.js 的四个脚本均为默认阻塞脚本，故执行顺序严格按此顺序。

---

## 二、async 与 defer 的语义差异（简要）

- **async**：脚本**异步下载**，下载完成后**立即执行**（可能在 DOM 解析完成前）。多个 async 脚本之间**执行顺序不确定**，谁先下载完谁先执行。
- **defer**：脚本异步下载，但执行推迟到 **DOM 解析完成后、DOMContentLoaded 前**；多个 defer 脚本按**文档中的顺序**执行。

若对 KernelLogger 或 DependencyConfig 使用 async，则可能 POOL 或 starter.js 先执行，此时 KernelLogger 未定义，会报错。故**引导层关键脚本必须为默认阻塞**，不能 async/defer。

---

## 三、loadScript 中动态插入的 script.async = false（starter.js）

在 loadScript 中（约 221 行）：`script.async = false;`。动态插入的 script 默认行为在某些浏览器中可能等价于 async；显式设为 false 可保证该脚本**按“加载完成”顺序执行**，与“先插入先执行”的预期一致，避免同层多模块执行顺序错乱。详见 2.3.2。

---

## 四、本节小结与维护要点

- 入口 HTML 中引导层脚本不使用 async/defer，依赖默认阻塞保证顺序。
- loadScript 动态插入时 `async = false`，保证依赖顺序；新增入口脚本时勿为关键依赖加 async/defer。
- 若某脚本与引导无依赖关系、可延后执行，可单独使用 defer 或放在 body 末尾，但不改变 KernelLogger/DependencyConfig/POOL/starter 四者顺序。
