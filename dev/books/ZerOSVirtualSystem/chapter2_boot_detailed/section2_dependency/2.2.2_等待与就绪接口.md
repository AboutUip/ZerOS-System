# 2.2.2 等待与就绪接口

## 本节导读（阅读目标）

本节使读者能够：**① 完全理解 waitLoaded 与 waitLoadedSync 的每一行代码作用、轮询与超时逻辑；② 明确 BootLoader 在何处调用、为何 RandomSecurity 用长超时而普通模块用短超时；③ 在新增“等待某模块”或排查“一直不 resolve/一直阻塞”时，能准确判断是 entry.loaded 未设、超时过短还是 name 不一致。** 下文给出**带注释的完整源码**、**行为流程**与**接手维护要点**。

## 一、waitLoaded(name, options) — 完整源码与注释（第 49–79 行）

```javascript
    // 异步等待指定依赖的 loaded 变为 true
    // 参数：name 依赖名（与 dependencyMap 的键一致）；options: { interval 默认50ms, timeout 默认5000ms }
    waitLoaded(name, options = {}) {
        const interval =
            typeof options.interval === "number" ? options.interval : 50;
        const timeout =
            typeof options.timeout === "number" ? options.timeout : 5000;
        KernelLogger.info("DependencyConfig", `等待加载: ${name}`);

        return new Promise((resolve, reject) => {
            // 【快速路径】若该条目已存在且 loaded 为 true，直接 resolve，不启动定时器
            const entry = this.dependencyMap.get(name);
            if (entry && entry.loaded) {
                KernelLogger.info("DependencyConfig", `等待完成: ${name}`);
                return resolve(true);
            }

            // 【轮询】未就绪则用 setInterval 每隔 interval ms 检查一次
            const start = Date.now();
            const timer = setInterval(() => {
                const e = this.dependencyMap.get(name);
                if (e && e.loaded) {
                    clearInterval(timer);
                    KernelLogger.info("DependencyConfig", `等待完成: ${name}`);
                    return resolve(true);
                }
                if (Date.now() - start >= timeout) {
                    clearInterval(timer);
                    KernelLogger.error("DependencyConfig", `等待超时: ${name} 加载失败`);
                    return reject(new Error(`waitLoaded: timeout waiting for "${name}"`));
                }
            }, interval);
        });
    }
```

### 行为流程（单次 waitLoaded 调用）

1. 解析 interval、timeout；打日志“等待加载: name”。
2. 若 `this.dependencyMap.get(name)` 存在且 `entry.loaded === true` → 打日志“等待完成”并 resolve(true)，结束。
3. 否则 start = Date.now()，设 setInterval 每 interval ms 执行：  
   - 再次 get(name)，若 entry 存在且 loaded 为 true → clearInterval，resolve(true)。  
   - 若已超过 timeout → clearInterval，打错误日志，reject(new Error(...))。  
4. 只 resolve 或 reject 一次；clearInterval 在两条分支中都会执行，避免重复回调。

### 为何用轮询而非事件

当前实现依赖“模块主动 publishSignal”，即 dependencyMap 中条目由事件回调更新。若改为“事件驱动等待”：需在 dependencyLoaded 上注册一次性 listener 并在 detail.name === name 时 resolve。轮询实现简单、与现有“依赖 map 状态”一致；轮询间隔 50ms 可减少 CPU 占用，又不会让等待方等得过久。

### 接手维护注意

- 若希望“某模块就绪后立刻 resolve、不浪费 50ms”：可在事件回调里维护“等待该 name 的 Promise 列表”，在设 loaded 时逐个 resolve；当前实现未做此优化。
- 修改超时时间时注意：RandomSecurity 可能涉及网络，用 15000ms；普通模块 2000ms 未就绪则 catch 继续，避免整层卡死。

## 二、waitLoadedSync(name, options) — 完整源码与注释（第 86–120 行）

```javascript
    // 同步等待：阻塞主线程直到 loaded 为 true 或超时
    // 返回 boolean：true 表示已加载，false 表示超时
    waitLoadedSync(name, options = {}) {
        const interval = typeof options.interval === "number" ? options.interval : 10;
        const timeout = typeof options.timeout === "number" ? options.timeout : 5000;

        KernelLogger.info("DependencyConfig", `同步等待加载: ${name}`);

        const entry = this.dependencyMap.get(name);
        if (entry && entry.loaded) {
            KernelLogger.info("DependencyConfig", `同步等待完成: ${name}`);
            return true;
        }

        const start = Date.now();
        while (true) {
            const e = this.dependencyMap.get(name);
            if (e && e.loaded) {
                KernelLogger.info("DependencyConfig", `同步等待完成: ${name}`);
                return true;
            }
            if (Date.now() - start >= timeout) {
                KernelLogger.error("DependencyConfig", `同步等待超时: ${name} 加载失败`);
                return false;
            }
            // 短暂阻塞，避免空转占满 CPU；注意会阻塞主线程，仅用于关键、短时等待
            const endTime = Date.now() + interval;
            while (Date.now() < endTime) {
                // busy-wait
            }
        }
    }
```

### 行为流程

1. 若已 loaded → 直接返回 true。  
2. 否则 while(true)：检查 loaded → 超时则返回 false；否则 busy-wait interval ms 再检查。  

**为何用 busy-wait**：浏览器环境没有“同步 sleep”的通用 API（Atomics.wait 需 SharedArrayBuffer）；用空循环占满 interval ms 实现“同步等待”。**副作用**：主线程阻塞，UI 卡顿，故只用于关键、短时等待；BootLoader 主要用异步 waitLoaded。

### 接手维护注意

- 不要在长超时下对非关键模块使用 waitLoadedSync；若必须同步等待，尽量短 timeout 与短 interval。
- window.waitDependencySync 会从 POOL 取 Dependency 再调 waitLoadedSync；若 POOL 未就绪会 new 临时 DependencyConfig 实例再调，此时 dependencyMap 可能为空，易超时返回 false。

## 三、BootLoader 中的调用位置与参数选择

| 调用点 | 参数 | 原因 |
|--------|------|------|
| RandomSecurity 加载后 | waitLoaded(RANDOM_SECURITY_MODULE, { timeout: 15000 }) | 安全校验可能涉及网络（如 JWT），耗时长；且必须等其 loaded 后再 loadModules，否则后续模块可能依赖未就绪的安全环境 |
| 每模块 loadScript 后 | waitLoaded(module, { interval: 10, timeout: 2000 }) | 给 2 秒让模块执行 IIFE 并 publishSignal；超时 catch 后继续，不阻塞整层；interval 较小以便更快感知就绪 |

---

## 四、本节小结

- **waitLoaded**：Promise 式轮询 entry.loaded，超时 reject；快速路径已 loaded 则直接 resolve。
- **waitLoadedSync**：同步 while+busy-wait 轮询，超时返回 false；会阻塞主线程，仅用于关键、短时等待。
- BootLoader 对 RandomSecurity 长超时、对普通模块短超时并 catch，兼顾安全与兼容性；模块需被等待时必须在就绪后 publishSignal(name)，且 name 与 waitLoaded(name) 一致。
