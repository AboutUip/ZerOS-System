# 2.2.3 dependencyMap 状态机与 dependencyLoaded 事件链路

## 本节导读（阅读目标）

本节使读者**完完全全参透** DependencyConfig 的**状态机**：每个模块在 dependencyMap 中的条目如何从“不存在”经 **linked → inited → loaded** 变化，以及 **dependencyLoaded** 事件在 document.body 上的派发与监听如何驱动 loaded 置位。学完后能画出完整的状态转换图、说出 BootLoader 与模块脚本各自在何时改写哪一字段、并能排查“waitLoaded 一直不 resolve”的根因。源码文件：`kernel/core/signal/dependencyConfig.js`。

---

## 一、状态机定义：三个布尔字段的含义

dependencyMap 中每个键（模块路径）对应一个**条目对象**，由 `DependencyConfig.generate(name)` 生成，结构如下（源码约 33–42 行）：

```javascript
    static generate(name) {
        return {
            linked: false,   // 是否已被“链接”：BootLoader 在 loadScript 后将该模块登记进 dependencyMap 并设为 true
            inited: false,   // 是否已初始化：脚本执行后由 dependencyLoaded 事件回调置为 true
            loaded: false,   // 是否完全加载：与 inited 在事件回调中同时置为 true，waitLoaded 只检查此字段
            expansion: {
                name: name,
                linktime: undefined,  // 可选，link 时记录
                inittime: undefined,  // 可选，事件回调时记录
                inde: undefined,
            },
        };
    }
```

**语义**：

- **linked**：该模块是否已被 BootLoader“登记”。在 loadModules 内，每次 loadScript(module) 成功后，会从 POOL 取 Dependency，若 dependencyMap 中无该 module 则 `set(module, generate(module))` 并设 `entry.linked = true`。表示“脚本已加载并执行过”的登记动作已完成。
- **inited**：该模块的脚本是否已执行到“初始化完成”并主动通知。只有模块内部调用 `DependencyConfig.publishSignal(本模块路径)` 后，事件回调才会把该条目设为 inited = true。
- **loaded**：与 inited 在**同一次事件回调**中被设为 true，是 waitLoaded 轮询检查的唯一字段。因此“loaded 为 true”等价于“该模块已 publishSignal”。

**状态转换**（按时间顺序）：

1. **条目不存在** → BootLoader 在 loadScript(module) 后若 dependencyMap 无 module，则 set(module, generate(module)) 并 linked = true → **linked=true, inited=false, loaded=false**。
2. 模块脚本执行到末尾，调用 `DependencyConfig.publishSignal(module)` → document.body 派发 CustomEvent("dependencyLoaded", { detail: { name: module } }) → DependencyConfig 实例的 eventHandler 被调用 → 若 dependencyMap 无该 name 则先 set(name, generate(name)) 并 linked=true，再 entry.inited = true; entry.loaded = true → **linked=true, inited=true, loaded=true**。
3. waitLoaded(name) 轮询检查 entry.loaded，为 true 则 resolve。

因此，**若模块从未调用 publishSignal**，则 loaded 永远为 false，waitLoaded 会一直轮询直到超时 reject。

## 二、dependencyLoaded 事件的派发与监听（源码 124–215 行）

### 2.1 派发：publishSignal(name)

```javascript
    static publishSignal(name) {
        document.body.dispatchEvent(
            new CustomEvent("dependencyLoaded", {
                detail: { name: name },
            })
        );
        KernelLogger.info("DependencyConfig", `${name} 已初始化`);
    }
```

**要点**：事件在 **document.body** 上派发，detail.name 为模块路径字符串。所有已注册的 "dependencyLoaded" 监听器都会收到该事件；ZerOS 中只有 DependencyConfig 的实例在 constructor 里注册了监听器，且每个实例的 dependencyMap 是各自独立的，但 **POOL 中注册的 Dependency 是 start_init 里 new 出来的那一个**，BootLoader 在 loadModules 中用的是 POOL 里的该实例，因此模块 publishSignal 后，**该实例**的 dependencyMap 会被更新。

### 2.2 监听：constructor 中的 eventHandler（约 179–215 行）

```javascript
    constructor() {
        this.dependencies = [];
        this.dependencyMap = new Map();
        this.RootElement = document.body;

        const eventHandler = (event) => {
            const name = event.detail.name;
            if (!this.dependencyMap.has(name)) {
                this.dependencyMap.set(name, DependencyConfig.generate(name));
                this.dependencyMap.get(name).linked = true;
            }
            const entry = this.dependencyMap.get(name);
            entry.inited = true;
            entry.loaded = true;
            entry.expansion.inittime = new Date().getTime();
            KernelLogger.info("DependencyConfig", `标记已初始化: ${name}`, { inittime: entry.expansion.inittime });
        };
        document.body.addEventListener("dependencyLoaded", eventHandler);
        this._dependencyLoadedHandler = eventHandler;
    }
```

**行为**：任意模块调用 publishSignal(name) 后，**所有** DependencyConfig 实例的 eventHandler 都会执行（因为都监听的是 document.body）。对**当前实例**的 dependencyMap：若没有 name 则先 create 并 linked=true，再统一 inited=true、loaded=true。因此若 BootLoader 用的是实例 A，只有 A.dependencyMap 被更新；若某处 new 了实例 B 且从未对 B 做过 addDependency/link 操作，B.dependencyMap 也可能因“先 publish 后 visit”而在事件回调中先被 create 再被设为 loaded。

## 三、完整事件链路（从模块执行到 waitLoaded resolve）

1. **loadScript(module)** 被调用，script 标签插入，脚本加载并执行。
2. 脚本内部（通常 IIFE 末尾）执行 **DependencyConfig.publishSignal(module)**（或相对路径，需与 BootLoader 中使用的 module 字符串一致）。
3. document.body 派发 **dependencyLoaded**，detail.name = module。
4. **DependencyConfig 实例**（start_init 中创建并放入 POOL 的）的 eventHandler 执行：dependencyMap.get(name) 或 set(name, generate(name)) 后，entry.loaded = true。
5. 此时 **waitLoaded(module)** 若正在轮询，下一次 setInterval 回调中 get(name).loaded 为 true，clearInterval，resolve(true)。

**常见问题**：若模块使用的 publishSignal 参数与 BootLoader 中 MODULE_DEPENDENCIES 的键（或 loadScript 传入的路径）不一致，则 dependencyMap 中会有两个不同键的条目，waitLoaded(module) 等待的是 BootLoader 侧的键，而模块更新的是另一键，导致 loaded 永远不置位、超时。

## 四、与 addDependency、linkerAll 的关系（历史与当前用法）

- **addDependency(name)**（约 148–151 行）：仅将 name 推入 this.dependencies 数组，**不**创建 dependencyMap 条目。BootLoader 当前用 `Object.keys(MODULE_DEPENDENCIES).forEach(module => Dependency.addDependency(module))` 填充 dependencies，但**真正创建 dependencyMap 条目的是 loadModules 内的“若 !dependencyMap.has(module) 则 set(module, generate(module)); entry.linked = true”**，不是 addDependency。
- **linkerAll()**（约 154–177 行）：遍历 this.dependencies，对每个 name 生成条目、**直接**在 body 上 append script 标签加载、并设 linked=true。这是**旧式“由 DependencyConfig 自己插 script”**的用法；当前 ZerOS 引导改用 **Starter 的 loadScript + 拓扑序**，不再在引导路径中调用 linkerAll，但保留该方法不影响现有流程。

---

## 五、本节小结与维护要点

- **状态机**：linked 表示“已被登记”，inited/loaded 表示“已 publishSignal”；waitLoaded 只认 loaded。
- **事件链路**：publishSignal(name) → body.dispatchEvent("dependencyLoaded") → 各实例 eventHandler → 当前实例 dependencyMap 中 name 对应条目 loaded=true。
- **排查 waitLoaded 不 resolve**：① 确认模块是否调用了 publishSignal；② 确认 publishSignal 的 name 与 waitLoaded(name) 的 name **字符串完全一致**（含相对路径、是否带 .js）；③ 确认等待的是 POOL 中注册的 Dependency 实例，而非临时 new 的实例（临时实例的 dependencyMap 可能未被 loadModules 填充 linked，但若先 publish 后 wait，事件回调会创建条目并 loaded=true，仍可 resolve）。
