# 2.2.1 DependencyConfig 职责与状态

## 本节导读（阅读目标）

本节使读者能够：**① 完全理解 DependencyConfig 的职责及其与 KernelLogger、POOL 的依赖关系；② 明确 dependencyMap 的结构、generate 的返回值、以及 linked/inited/loaded 三态在代码中的含义与更新时机；③ 理解构造函数中 dependencyLoaded 事件监听如何将“模块已初始化”转化为 loaded 标记；④ 在修改引导顺序或新增“等待某模块就绪”的逻辑时，能正确使用 dependencyMap 与 publishSignal。** 下文给出**带注释的完整源码**、**行为流程**与**接手维护要点**。

---

## 一、文件头与前置依赖（dependencyConfig.js 第 1–12 行）

```javascript
// DependencyConfig: 依赖管理器
// 依赖: KernelLogger（在 HTML 中已加载）
// 自成一体，可在 HTML 中直接加载

(function() {
    'use strict';

    // 【必须】KernelLogger 在 HTML 中先于本文件加载；本模块内所有日志与错误都依赖它。
    // 若未定义说明加载顺序错误，直接抛错便于在开发阶段发现。
    if (typeof KernelLogger === 'undefined') {
        throw new Error("KernelLogger is required for DependencyConfig");
    }
```

**行为**：IIFE 执行时若 KernelLogger 未定义则抛错，引导终止。**维护**：不要将 DependencyConfig 放在 KernelLogger 之前加载。

## 二、状态对象：generate 与 dependencyMap 的值（第 18–44 行）

```javascript
    /*
     * 依赖映射对象（dependencyMap 中每个 key 对应的 value 结构）
     * value = {
     *     linked : [bool]    是否被 link（脚本已加载并在 map 中登记）
     *     inited : [bool]    是否已执行初始化逻辑
     *     loaded : [bool]    是否完全加载（可供其他模块使用）；waitLoaded 等待的就是此项
     *     expansion : {
     *         linktime, inittime, inde, name 等扩展信息
     *     }
     * }
     */

    // 【静态方法】生成统一的状态模板，供 BootLoader 或事件回调在“首次登记某模块”时使用
    static generate(name) {
        return {
            linked: false,
            inited: false,
            loaded: false,
            expansion: {
                name: name,
            },
        };
    }
```

**行为**：任何需要往 dependencyMap 里放新条目时，都应使用 `DependencyConfig.generate(模块路径)`，保证字段一致。**linked** 由 BootLoader 在 loadScript 后设为 true；**inited / loaded** 由 dependencyLoaded 事件回调统一设为 true（见构造函数）。**维护**：若将来要区分“已执行初始化”与“已注册到 POOL 可供使用”，可在事件回调中先设 inited，再在另一时机设 loaded。

## 三、构造函数与 dependencyLoaded 事件（第 183–211 行）

```javascript
    constructor() {
        KernelLogger.info("DependencyConfig", "初始化开始");
        this.dependencies = [];           // 历史用法：addDependency 的列表，BootLoader 会批量 add
        this.dependencyMap = new Map();   // 核心：模块名/路径 -> 状态对象
        this.RootElement = document.body; // linkerAll 等可能用到的根元素

        // 【核心】监听自定义事件 "dependencyLoaded"；任意模块调用 publishSignal(name) 会派发该事件
        const eventHandler = (event) => {
            const name = event.detail.name;
            // 若 map 中尚无该 name（例如动态加载的模块先发事件、BootLoader 尚未登记），则先创建条目并设 linked=true
            if (!this.dependencyMap.has(name)) {
                this.dependencyMap.set(name, DependencyConfig.generate(name));
                this.dependencyMap.get(name).linked = true;
            }
            const entry = this.dependencyMap.get(name);
            entry.inited = true;
            entry.loaded = true;   // waitLoaded 轮询的就是 entry.loaded，这里设为 true 后等待方即 resolve
            const inittimer = new Date().getTime();
            entry.expansion.inittime = inittimer;
            KernelLogger.info("DependencyConfig", `标记已初始化: ${name}`, { inittime: inittimer });
        };
        document.body.addEventListener("dependencyLoaded", eventHandler);
        this._dependencyLoadedHandler = eventHandler;

        KernelLogger.info("DependencyConfig", "初始化完成");
    }
```

**行为流程**：  
1. 创建 dependencies 数组与 dependencyMap。  
2. 注册 dependencyLoaded 的监听器：收到事件时用 detail.name 取 name；若 map 无 name 则 generate 并设 linked=true；然后将该条目的 inited 与 loaded 设为 true，并记录 inittime。  
3. 因此**任意模块在适当时机调用 `DependencyConfig.publishSignal(本模块路径)`**，就会触发上述逻辑，使 waitLoaded(name) 的轮询发现 entry.loaded === true 并 resolve。

**为何支持“先发事件再登记”**：BootLoader 按层加载时，可能先 loadScript(module) 再在下一行才往 dependencyMap 里 set(module, generate(module))；而 module 的脚本可能在执行时立即 publishSignal。事件回调里若发现 map 尚无该 name 就先 create 并设 linked，避免漏标 loaded。

**维护**：新增模块若希望被 waitLoaded 等待，必须在 IIFE 末尾或初始化完成后调用 `DependencyConfig.publishSignal(本模块路径)`，且路径需与 MODULE_DEPENDENCIES 中的键一致（BootLoader 用该键做 waitLoaded(module)）。

## 四、publishSignal 静态方法（第 123–132 行）

```javascript
    static publishSignal(name) {
        // 向 document.body 派发自定义事件，detail 中携带模块名，供构造函数里注册的 eventHandler 消费
        document.body.dispatchEvent(
            new CustomEvent("dependencyLoaded", {
                detail: {
                    name: name,
                },
            })
        );
        KernelLogger.info("DependencyConfig", `${name} 已初始化`);
    }
```

**行为**：派发 dependencyLoaded 后，所有已注册的 listener（包括 Dependency 实例的 eventHandler）会执行，将 dependencyMap 中对应条目的 loaded 设为 true。**注意**：若 document.body 尚未就绪，dispatchEvent 可能无效；文件末尾有“body 就绪后再 publishSignal(dependencyConfig.js 自身)”的逻辑，保证自身也会被标记。

---

## 五、addDependency、checkDependency、linkerAll 简述

- **addDependency(name)**（第 147–150 行）：`this.dependencies.push(name)` 并打日志。BootLoader 用其批量登记 MODULE_DEPENDENCIES 的键，与 linkerAll 等历史逻辑兼容。
- **checkDependency(name)**（第 135–144 行）：同步查询 dependencyMap.get(name)，若不存在返回 false，否则返回 entry.loaded。用于“不等待、只查一次”的场景。
- **linkerAll**（第 154–176 行）：遍历 this.dependencies，对每项 generate、插入 script 标签、设 linked 与 linktime。当前 ZerOS 正式加载由 Starter 的 loadScript 完成，linkerAll 可能仅在特殊路径使用；若你改引导流程，需注意与 loadScript 的职责划分。

## 六、文件末尾：自身 publishSignal 与 POOL 注册（第 264–294 行）

```javascript
// 本脚本加载完成后，若 document.body 已存在则立即发布“本模块已初始化”；
// 否则在 DOMContentLoaded 或 setTimeout 中延迟发布，确保 DependencyConfig 自身也会被标记为 loaded
if (typeof document !== 'undefined' && document.body) {
    DependencyConfig.publishSignal("../kernel/core/signal/dependencyConfig.js");
} else {
    if (document.readyState === 'loading') {
        document.addEventListener('DOMContentLoaded', () => {
            DependencyConfig.publishSignal("../kernel/core/signal/dependencyConfig.js");
        });
    } else {
        setTimeout(() => {
            if (document.body) {
                DependencyConfig.publishSignal("../kernel/core/signal/dependencyConfig.js");
            }
        }, 0);
    }
}

// 将 DependencyConfig 类挂到 POOL（若 POOL 已加载），供 BootLoader 获取并 new DependencyConfig()
if (typeof POOL !== 'undefined' && typeof POOL.__ADD__ === 'function') {
    try {
        if (!POOL.__HAS__("KERNEL_GLOBAL_POOL")) {
            POOL.__INIT__("KERNEL_GLOBAL_POOL");
        }
        POOL.__ADD__("KERNEL_GLOBAL_POOL", "DependencyConfig", DependencyConfig);
    } catch (e) {
        window.DependencyConfig = DependencyConfig;
    }
} else {
    window.DependencyConfig = DependencyConfig;
}
```

**行为**：保证 DependencyConfig 自身也会进入 dependencyMap 并标记 loaded（路径为 "../kernel/core/signal/dependencyConfig.js"）；并将类注册到 POOL 或 window，供 start_init 中 `new DependencyConfig()` 使用。

## 七、接手维护要点

1. **新增“等待某模块就绪”**：调用方使用 `Dependency.waitLoaded(模块路径, options)`；被等待的模块必须在就绪时调用 `DependencyConfig.publishSignal(模块路径)`，路径需与 MODULE_DEPENDENCIES 的键一致。
2. **修改引导顺序**：BootLoader 在 loadScript(module) 后会 set(module, generate(module)) 并 linked=true；若你改为“先 publish 再 loadScript”，事件回调里已支持“无条目则先创建”，无需改 DependencyConfig。
3. **排查“waitLoaded 一直不 resolve”**：检查该模块是否调用了 publishSignal、name 是否与 waitLoaded(name) 完全一致（含路径）；检查 document.body 是否已存在（否则 dispatchEvent 无效）。

---

## 八、本节小结

- DependencyConfig 依赖 KernelLogger，提供 dependencyMap（模块名→状态对象）、generate、waitLoaded/waitLoadedSync、publishSignal、构造函数中的 dependencyLoaded 监听。
- linked 由 BootLoader 或事件回调（动态模块先发事件时）设置；inited/loaded 由 dependencyLoaded 事件回调统一设为 true；waitLoaded 轮询 entry.loaded。
- 模块需被等待时必须在就绪后 publishSignal(本模块路径)；路径需与 MODULE_DEPENDENCIES 键一致。
