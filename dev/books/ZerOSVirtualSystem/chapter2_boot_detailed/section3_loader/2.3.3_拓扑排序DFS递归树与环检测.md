# 2.3.3 拓扑排序 DFS 递归树与环检测

## 本节导读（阅读目标）

本节让读者**完完全全参透**拓扑排序的**递归执行过程**：对任意给定的 MODULE_DEPENDENCIES，能在大脑中或纸上画出 **visit() 的递归调用树**、每个节点上 visiting/visited 的变化、以及**环是如何在递归栈上被检测到的**。学完后能解释“为什么必须用 visiting 而不能只用 visited”“为什么是后序而非前序”、并能对任意依赖图手推排序结果。源码位置：`bootloader/starter.js` 第 255–301 行。

---

## 一、DFS 后序与“被依赖者在前”的等价性

**拓扑序**的定义：若图中存在边 A → B（表示 B 依赖 A），则在排序结果中 **A 必须出现在 B 之前**。这样按序 loadScript 时，A 先执行，B 后执行，B 执行时 A 已就绪。

**DFS 后序**：对节点 u，先递归访问 u 的**所有后继**（即 u 依赖的节点），再在递归返回时“处理 u”（此处为将 u 加入 sorted）。因此若 A → B，则 B 依赖 A，在 visit(B) 中会先 visit(A)，A 先被加入 sorted，B 后被加入，满足“被依赖者在前”。

**递归树示例**：设依赖为 D: [B,C], B: [A], C: [A], A: []。allModules = {A,B,C,D}。

- 若从 D 开始：visit(D) → visiting={D}，deps=[B,C]，先 visit(B) → visiting={D,B}，deps=[A]，visit(A) → visiting={D,B,A}，deps=[]，A 出栈入 visited，sorted=[A]；B 出栈入 visited，sorted=[A,B]；再 visit(C) → visiting={D,C}，visit(A) 时 A 已在 visited 直接 return；C 出栈，sorted=[A,B,C]；D 出栈，sorted=[A,B,C,D]。结果：A,B,C,D。
- 若从 A 开始：visit(A) → sorted=[A]；然后 allModules.forEach 会再对 B,C,D 调用 visit，因 B 的 deps 含 A 且 A 已在 visited，B 直接出栈，sorted=[A,B]；同理 C→[A,B,C]，D→[A,B,C,D]。**结论**：无论从哪个节点开始 DFS，只要所有节点都被 visit 到，最终 sorted 的拓扑序一致（因为后序保证依赖一定先入栈）。

---

## 二、环检测：为什么必须用 visiting

**环**：存在路径 u → … → v → … → u（同一节点在递归栈上出现两次）。

**若只用 visited**：visited 只表示“该节点已在某次 DFS 中处理完”。例如图 A→B→C→A，从 A 开始：visit(A)，visiting 无，visited 无，visiting.add(A)，visit(B)，visiting.add(B)，visit(C)，visiting.add(C)，visit(A)——此时若只查 visited，A 尚未被加入 visited（要等 A 的递归全部返回才 add），所以会继续递归，形成 visit(A)→visit(B)→visit(C)→visit(A)→… 无限递归。**因此 visited 无法在“当前路径”上区分“已处理完”与“正在栈上”**。

**用 visiting**：进入节点时 visiting.add(module)，离开时 visiting.delete(module)。若 visit(u) 在执行过程中调用了 visit(v)，而 v 又在某次递归中回到 u，则当再次进入 visit(u) 时，u 仍在 visiting 中（尚未 delete），此时立刻 throw 循环依赖。这样**栈上节点集合 = visiting**，若当前要访问的节点已在栈上，说明存在 u→…→u 的环。

**手推环例**：A→B，B→C，C→A。visit(A)：visiting={A}，visit(B)：visiting={A,B}，visit(C)：visiting={A,B,C}，visit(A)：A 在 visiting 中 → throw "循环依赖 detected: A"。

## 三、递归树与 visiting/visited 的逐步变化（无环例）

设依赖图：**G: { A:[], B:[A], C:[A], D:[B,C] }**，allModules = {A,B,C,D}。假设 allModules.forEach 的顺序为 A,B,C,D（实际为 Set 迭代顺序，可能不同，不影响最终拓扑序）。

- **visit(A)**：visiting.add(A)={A}，deps=[]，无递归；visiting.delete(A)={}，visited.add(A)={A}，dependencies.hasOwnProperty(A) 为 true → sorted=[A]。
- **visit(B)**：visiting={B}，deps=[A]，visit(A)；A 已在 visited → return；visiting.delete(B)，visited.add(B)，sorted=[A,B]。
- **visit(C)**：visiting={C}，visit(A) return；sorted=[A,B,C]。
- **visit(D)**：visiting={D}，deps=[B,C]，visit(B) 与 visit(C) 均 return；sorted=[A,B,C,D]。

每一时刻 **visiting** 恰好是当前递归栈上的节点集合，**visited** 是已完全处理完的节点集合。

---

## 四、hasOwnProperty(module) 与“仅键入 sorted”的再次说明

若某路径 **只出现在值中、未作为键**，例如 MODULE_DEPENDENCIES = { B: ["A"], C: ["A"] }，且 "A" 不是键。则 allModules = {A,B,C}（A 从值中收集）。visit(A) 时，A 会入栈、出栈、visited.add(A)，但 **dependencies.hasOwnProperty("A") 为 false**，故 A 不会 push 到 sorted。sorted 中只有 B,C，且 B、C 的依赖 A 已先被 visit，顺序为 B,C 或 C,B（取决于 forEach 顺序）。这样 **A 参与排序、保证 B/C 在 A 之后，但 A 本身不会被 loadScript**，适合“A 已由 HTML 加载”的场景。

---

## 五、本节小结与维护要点

- **后序**：先递归所有依赖再 push 自身，保证被依赖者一定在 sorted 中排前面。
- **visiting**：当前 DFS 栈上的节点，用于环检测；再次进入栈上节点即抛错。
- **visited**：已完全处理完的节点，避免重复遍历与重复 push（且只有键中的节点会 push）。
- 手推时可按“递归树 + 每步 visiting/visited/sorted”列表化，即可完全复现算法行为。
