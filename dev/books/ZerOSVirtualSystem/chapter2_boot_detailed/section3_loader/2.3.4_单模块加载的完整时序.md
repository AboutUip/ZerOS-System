# 2.3.4 单模块加载的完整时序

## 本节导读（阅读目标）

本节让读者**完完全全参透**“单个模块”从被 loadModules 选中到 **loadScript 执行完毕、dependencyMap 更新、waitLoaded 结束**的**完整时间线**：每一步在谁（BootLoader/浏览器/模块脚本）中执行、以什么顺序、以及为何这样设计能保证依赖语义。学完后能画出单模块的时序图、并能解释“先 Promise.all(deps) 再 loadScript(module)”与“waitLoaded 超时继续”对整体顺序的影响。源码：`bootloader/starter.js` loadModules 内单次 `layer.map(async (module) => { ... })`。

---

## 一、单模块在 loadModules 中的代码路径（starter.js 约 347–416 行）

对**当前层**的每一个 **module**，以下步骤**严格顺序**执行（同一层内多个 module 之间由 Promise.all 并行，但单个 module 内是串行）：

```text
1. deps = dependencies[module] || []
2. await Promise.all(deps.map(dep => loadedModules.has(dep) ? Promise.resolve() : loadScript(dep)))
3. await loadScript(module)
4. loadedModules.add(module)
5. 从 POOL 取 Dependency，若 dependencyMap 无 module 则 set(module, generate(module)); entry.linked = true
6. await Dependency.waitLoaded(module, { interval: 10, timeout: 2000 })  // 可选，超时 catch 后继续
```

---

## 二、时间线详解（单模块 module）

| 时刻 | 执行者 | 动作 | 说明 |
|------|--------|------|------|
| T0 | BootLoader | 进入该 module 的 async 回调 | 当前层 Promise.all(layer.map(...)) 中轮到本 module |
| T1 | BootLoader | Promise.all(deps.map(...)) | 若某 dep 未在 loadedModules 中，则 loadScript(dep)；否则 resolve。保证本 module 的依赖在本步之后都已执行过 loadScript 且 resolve |
| T2 | BootLoader | loadScript(module) | 创建 script 标签、src=module、appendChild(head)；返回 Promise |
| T3 | 浏览器 | 请求并执行 module 脚本 | 脚本执行期间可能调用 publishSignal(module) |
| T4 | 模块脚本 | 执行 IIFE、可能 publishSignal(module) | document.body 派发 dependencyLoaded，Dependency 的 eventHandler 将 dependencyMap 中 module 条目 loaded=true |
| T5 | 浏览器 | script onload 触发 | loadScript 的 Promise resolve，T2 的 await 返回 |
| T6 | BootLoader | loadedModules.add(module) | 标记本模块已加载 |
| T7 | BootLoader | POOL.__GET__("KERNEL_GLOBAL_POOL", "Dependency")，dependencyMap 无则 set(module, generate(module)); linked=true | 若 loadModules 先于 publishSignal 执行到此处，则先 create 并 linked；若 publishSignal 已执行则可能已有条目，仅需确保 linked=true（或由事件回调已创建） |
| T8 | BootLoader | Dependency.waitLoaded(module, { timeout: 2000 }) | 轮询 dependencyMap.get(module).loaded；若 T4 已执行则很快 resolve；否则最多等 2 秒后 catch，继续 |
| T9 | BootLoader | 本 module 的 async 回调 return | 本层其他 module 若也完成，则 Promise.all  resolve，进入下一层 |

**关键点**：T3–T4 与 T5 的顺序由浏览器保证（脚本执行完才会 onload）；T7 在 T5 之后，因此 dependencyMap 的“创建条目、linked=true”一定在 loadScript resolve 之后；若模块在 T4 调用了 publishSignal，则 T8 的 waitLoaded 会很快看到 loaded=true 并 resolve。

---

## 三、“先 Promise.all(deps) 再 loadScript(module)”的必要性

若**不**先等 deps，而是直接 loadScript(module)，则可能出现：同层内 module1 依赖 module2，但 layer 中 module1 排在 module2 前面，Promise.all 中 module1 先执行 loadScript(module1)，module1 的脚本执行时 module2 尚未加载，若 module1 内部有对 module2 的同步引用会报错。先 `await Promise.all(deps.map(...))` 保证**本 module 的所有依赖**要么已在之前层加载过（loadedModules.has(dep)），要么在本层内作为 dep 被 loadScript 并 resolve，从而本 module 执行时依赖一定已就绪。

---

## 四、waitLoaded 超时后继续的影响

若模块**未**调用 publishSignal，则 T8 会轮询 2 秒后 reject，被 catch 后不打 throw，本 module 的 async 回调仍正常 return，下一层照常进行。影响是：**依赖该模块“就绪”的后继逻辑**（若有）可能在该模块实际未就绪时就被执行，需由模块设计保证“要么 publishSignal，要么不依赖 waitLoaded”。若希望严格就绪再继续，应在模块末尾统一 publishSignal(本模块路径)。

---

## 五、本节小结与维护要点

- 单模块时序：等依赖 → loadScript(module) → 脚本执行（含可选 publishSignal）→ onload → 登记 linked → waitLoaded（超时可选继续）→ 回调结束。
- 先 Promise.all(deps) 再 loadScript(module) 保证依赖先就绪；waitLoaded 超时继续保证鲁棒性，但模块应尽量 publishSignal 以便依赖方可靠等待。
- 排查“某模块执行时依赖未定义”：确认该依赖在 MODULE_DEPENDENCIES 中已声明且在 sorted 中排在本模块前；确认层号与 deps 的 loadScript 顺序。
