# 2.3.1 MODULE_DEPENDENCIES 与拓扑排序

## 本节导读（阅读目标）

本节使读者在阅读后能够：**① 完全理解 ZerOS 如何根据 MODULE_DEPENDENCIES 得到模块加载顺序；② 明确 topologicalSort 中每一行代码的作用与执行时机；③ 清楚“何时会抛循环依赖、为何只加载键中的模块”；④ 在修改依赖图或排查加载顺序问题时，能准确预测行为并安全地做增量修改或修漏洞。** 下文给出**带逐行/逐块中文注释的完整源码**、**行为流程**、**设计原因**与**接手维护要点**。

## 一、MODULE_DEPENDENCIES 的数据结构（源码位置：starter.js 第 11–193 行）

依赖图以**对象**形式定义：**键 = 需要被 BootLoader 加载的模块路径**（字符串），**值 = 该模块所依赖的模块路径数组**（若为空数组则表示无依赖）。例如：

```javascript
// 示例：processManager 依赖 memoryManager 与 kernelMemory，故 memoryManager 必须先于 processManager 加载
"../kernel/process/processManager.js": [
    "../kernel/memory/memoryManager.js",
    "../kernel/memory/kernelMemory.js",
    "../kernel/process/applicationAssetManager.js"
],
"../kernel/memory/memoryManager.js": [
    "../kernel/core/typePool/logLevel.js",
    "../kernel/memory/heap.js",
    "../kernel/memory/shed.js"
],
```

**要点**：值中出现的路径可能并不在键中（例如仅被其他模块依赖的“叶子”模块）；拓扑排序会先把**键与值中出现的所有路径**收集到 `allModules`，但**只有键中的模块**会被加入最终 `sorted` 并参与后续 loadScript。这样设计是为了支持“仅参与排序、不参与动态加载”的节点（如占位或由 HTML 已加载的模块）。

## 二、拓扑排序完整源码与逐行/逐块注释（starter.js 第 255–301 行）

以下为 `topologicalSort(dependencies)` 的**完整实现**，每段后附注释说明**该段在做什么、为何这样写、执行顺序如何**。

```javascript
function topologicalSort(dependencies) {
    // ---------- 初始化：结果数组与 DFS 状态 ----------
    const sorted = [];           // 最终输出的拓扑序列表，按“被依赖者在前、依赖者在后”
    const visited = new Set();  // 已完全处理完的节点（已出递归栈），避免重复遍历
    const visiting = new Set(); // 当前 DFS 栈上的节点，用于检测环：若递归中再次进入栈上节点则存在环
    const allModules = new Set(Object.keys(dependencies));  // 先放入所有“键”中的模块

    // ---------- 收集“值”中出现的模块，保证图完整 ----------
    // 有些模块只作为依赖项出现在值里、不在键里，若不加入 allModules 则 visit 不会遍历到它们，
    // 可能导致排序结果中缺少依赖关系。加入后 visit(dep) 会执行，但只有键中的模块会 push 到 sorted。
    Object.values(dependencies).forEach(deps => {
        deps.forEach(dep => allModules.add(dep));
    });

    // ---------- 核心递归：对单节点做 DFS 后序 ----------
    function visit(module) {
        // 【环检测】若当前节点已在“当前路径”上，说明存在从该节点出发又回到该节点的环，必须报错终止引导
        if (visiting.has(module)) {
            throw new Error(`循环依赖 detected: ${module}`);
        }
        // 【已访问】若该节点已在之前某次 DFS 中处理完，直接返回，不重复加入 sorted
        if (visited.has(module)) {
            return;
        }

        visiting.add(module);   // 进入当前路径，标记为“栈上”

        // 先递归处理所有依赖（后继），保证依赖一定在本节点之前被 push 到 sorted
        const deps = dependencies[module] || [];
        deps.forEach(dep => {
            if (allModules.has(dep)) {
                visit(dep);
            }
        });

        visiting.delete(module);  // 离开当前路径
        visited.add(module);      // 标记为已处理完毕

        // 只把“出现在依赖图键中”的模块加入 sorted，值中独有的节点不参与 loadScript，只参与排序
        if (dependencies.hasOwnProperty(module)) {
            sorted.push(module);
        }
    }

    // ---------- 对图中所有未访问节点执行 DFS ----------
    allModules.forEach(module => {
        if (!visited.has(module)) {
            visit(module);
        }
    });

    return sorted;
}
```

### 注释要点汇总

| 代码位置 | 作用 | 为何这样写 |
|----------|------|------------|
| `visiting` | 记录当前 DFS 栈上的节点 | 若递归中再次进入栈上节点，说明存在环，必须 throw，否则排序无意义 |
| `visited` | 记录已完全处理完的节点 | 避免同一节点被多次加入 sorted，且避免重复递归 |
| `allModules` 包含键+值 | 保证“被依赖但不在键中”的节点也被遍历 | 这样依赖关系正确；但只有键中的节点会 push 到 sorted，不会对不存在的路径 loadScript |
| `dependencies.hasOwnProperty(module)` | 仅键中的模块进入 sorted | 值中独有的路径可能不对应实际脚本或由 HTML 加载，不应由 Starter 动态加载 |
| 先递归 deps 再 push(module) | DFS 后序 | 保证任意依赖都在其依赖者之前被 push，得到的就是拓扑序 |

## 三、行为流程（执行顺序与数据变化）

1. **输入**：`dependencies` 对象（键 = 要加载的模块路径，值 = 依赖路径数组）。
2. **初始化**：`sorted = []`，`visited = new Set()`，`visiting = new Set()`，`allModules = new Set(keys)`，再遍历所有值把依赖路径加入 `allModules`。
3. **遍历**：对 `allModules` 中每个未在 `visited` 中的 `module` 调用 `visit(module)`。
4. **visit(module) 内**：
   - 若 `visiting.has(module)` → 抛错「循环依赖 detected: module」。
   - 若 `visited.has(module)` → return。
   - `visiting.add(module)`。
   - 对 `dependencies[module]` 中每个在 `allModules` 中的 `dep` 调用 `visit(dep)`。
   - `visiting.delete(module)`，`visited.add(module)`。
   - 若 `dependencies.hasOwnProperty(module)` 则 `sorted.push(module)`。
5. **输出**：`sorted` 即拓扑序，保证对任意边 A→B，B 在 sorted 中一定排在 A 前面。

**递归时 visiting/visited 的变化**：进入某节点时加入 visiting，离开时从 visiting 删除并加入 visited。若在递归栈上再次进入同一节点（visiting 中已存在），则判定为环。

## 四、示例：小型依赖图走查

设 `dependencies = { A: [], B: ['A'], C: ['A'], D: ['B','C'] }`，则 `allModules = {A,B,C,D}`。

- 第一次调用 `visit(A)`：visiting={A}，deps 为空，递归不执行，A 出栈入 visited，A 在键中 → sorted=[A]。
- `visit(B)`：visiting={B}，visit(A) 时 A 已在 visited 直接 return；B 出栈入 visited → sorted=[A,B]。
- `visit(C)`：同理 → sorted=[A,B,C]。
- `visit(D)`：先 visit(B)、visit(C)，均已在 visited；D 出栈入 visited → sorted=[A,B,C,D]。  
加载顺序即 A→B→C→D，满足所有依赖。

若存在环，例如 B 依赖 D、D 依赖 B：从 B 进入会 visit(D)→visit(B)，此时 B 仍在 visiting 中，触发「循环依赖 detected: B」。

## 五、调用链示例：从 start_init 到 loadModules 到 topologicalSort

读者可沿下列调用链在源码中对照行号，完整走通“引导 → 排序 → 按层加载”的路径：

1. **starter.js 末尾（约 1699–1704 行）**：`document.readyState === 'loading'` 时 `document.addEventListener('DOMContentLoaded', start_init)`，否则直接 `start_init().catch(...)`。  
2. **start_init（约 1114 行起）**：`await waitForCoreModules()` → `new DependencyConfig()` → `POOL.__INIT__("KERNEL_GLOBAL_POOL")` → 设置系统加载标志 → `POOL.__ADD__(..., "Dependency", Dependency)` → `Object.keys(MODULE_DEPENDENCIES).forEach(module => Dependency.addDependency(module))` → `await loadScript(SYSTEM_INFORMATION_MODULE)` → `await loadScript(RANDOM_SECURITY_MODULE)` → `await Dependency.waitLoaded(RANDOM_SECURITY_MODULE, { timeout: 15000 })` → **`await loadModules(MODULE_DEPENDENCIES)`**。  
3. **loadModules（约 308 行起）**：首行即 `const sorted = topologicalSort(dependencies)`，得到拓扑序；随后按层级分组（同层模块 deps 均已出现在 sorted 更前位置），对每层 `await Promise.all(layer.map(module => loadScript(module)))`，并在每层加载后通过 POOL 取 Dependency、标记 linked、可选 `waitLoaded(module)`。  
4. **topologicalSort**：如上节，输入 MODULE_DEPENDENCIES，输出 sorted 数组；loadScript 严格按 sorted 的“层”顺序执行，同一层内并行，层与层之间串行（上一层 Promise.all 完成后再进行下一层）。

因此，**任意模块的加载时机** = 其所在“层”的 Promise.all 被 await 的时刻；**其执行顺序** = 在 sorted 中首次出现的层内，与其他同层模块并行，且一定晚于其所有依赖所在层。

## 六、接手维护时注意（增量更新与修漏洞）

1. **新增模块**：在 MODULE_DEPENDENCIES 中增加键值对即可；若该模块依赖已有模块，值写依赖数组。拓扑排序会自动把新模块纳入 allModules 并排在依赖之后；**注意不要写成循环依赖**（A 依赖 B、B 依赖 A 或更长环）。
2. **新增“仅作依赖、不加载”的节点**：可只在某键的值中加入路径，不要将该路径作为键；这样 allModules 会有该路径、排序正确，但 sorted 中不会出现，loadScript 不会加载它（适合已由 HTML 加载或占位）。
3. **排查加载顺序问题**：先对 MODULE_DEPENDENCIES 跑一遍 topologicalSort，看 sorted 中目标模块的前后顺序是否符合预期；若不符合，检查依赖声明是否写反或遗漏。
4. **修循环依赖**：错误信息会指出「循环依赖 detected: xxx」，从 xxx 出发沿 dependencies 回溯即可找到环上节点，去掉环上一条边或拆分子模块即可。

### 常见错误与排查

| 现象 | 可能原因 | 排查与修复 |
|------|----------|------------|
| 控制台报「循环依赖 detected: xxx」 | MODULE_DEPENDENCIES 中存在环 | 从 xxx 沿 dependencies 找环，删除一条依赖边或拆模块 |
| 某模块未被执行 | 该路径只在值中出现、未作为键 | 若需加载，将其加入 MODULE_DEPENDENCIES 的键 |
| 某模块执行时依赖未定义 | 依赖写反或遗漏，或依赖路径拼写错误 | 核对键与值中的路径与文件实际路径一致；对 dependencies 跑 topologicalSort 看 sorted 中顺序 |
| 同层模块执行顺序不确定 | 同层内 Promise.all 并行，顺序未规定 | 若需严格顺序，通过“虚依赖”把顺序约束进图（如 A 依赖 B 则 A 在 B 后） |

## 七、本节小结

- MODULE_DEPENDENCIES 的键为要加载的模块，值为其依赖数组；拓扑排序用 DFS 后序得到 sorted，保证被依赖者在前。
- visiting 用于环检测，visited 用于去重；只有键中的模块会进入 sorted 并被后续 loadScript 加载。
- 修改依赖图时注意避免环；新增模块时按依赖关系填写值即可；排查顺序时可直接对 dependencies 跑 topologicalSort 观察结果。
- 从 start_init → loadModules → topologicalSort 的调用链决定了“层”与“并行/串行”的语义；同层内并行、层间串行，任意模块的加载时机由其所在层决定。
