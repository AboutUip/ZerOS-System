# 2.3.2 按层加载与 loadScript

## 本节导读（阅读目标）

本节使读者能够：**① 完全理解 loadScript 的缓存、DOM 检查、动态插入与错误处理，以及为何 async=false；② 完全理解 loadModules 的层级计算方式、同层并行的含义、以及每步与 DependencyConfig/POOL 的衔接；③ 在修改加载逻辑、增加新模块或排查“某模块未就绪”时，能准确判断执行顺序与等待点。** 下文给出**带逐行/逐块注释的 loadScript 与 loadModules 源码**、**行为流程**、**设计原因**与**接手维护要点**。

## 一、loadScript 完整源码与逐行/逐块注释（starter.js 第 204–252 行）

```javascript
function loadScript(src) {
    // 【缓存】同一路径多次调用返回同一 Promise，避免重复插入 script、重复请求与执行
    if (scriptPromises.has(src)) {
        return scriptPromises.get(src);
    }

    // 【已存在检查】若 HTML 中已有该 src 的 script 标签（例如 KernelLogger 等已在入口 HTML 中），
    // 不再动态插入，直接返回已 resolve 的 Promise 并写入缓存，与静态加载兼容
    const existingScript = document.querySelector(`script[src="${src}"]`);
    if (existingScript) {
        const promise = Promise.resolve();
        scriptPromises.set(src, promise);
        return promise;
    }

    // 【创建加载 Promise】通过动态插入 script 触发浏览器加载并执行
    const promise = new Promise((resolve, reject) => {
        const script = document.createElement('script');
        script.src = src;
        // 【关键】async=false：浏览器会按“插入顺序/加载完成顺序”依次执行，保证依赖语义；
        // 若为 true 则执行顺序不可控，可能依赖者先于被依赖者执行
        script.async = false;

        script.onload = () => {
            if (typeof KernelLogger !== 'undefined') {
                KernelLogger.info("BootLoader", `脚本加载完成: ${src}`);
            } else {
                console.log(`[内核][BootLoader] 脚本加载完成: ${src}`);
            }
            resolve();  // 仅表示“脚本已加载并执行完毕”，不表示模块已 publishSignal(loaded)
        };

        script.onerror = () => {
            const error = new Error(`Failed to load script: ${src}`);
            if (typeof KernelLogger !== 'undefined') {
                KernelLogger.error("BootLoader", `脚本加载失败: ${src}`, error);
            } else {
                console.error(`[内核][BootLoader] 脚本加载失败: ${src}`, error);
            }
            reject(error);  // 上层 catch 后可终止引导或报错
        };

        document.head.appendChild(script);  // 插入后浏览器开始请求并执行
    });

    scriptPromises.set(src, promise);
    return promise;
}
```

### 行为流程（loadScript 单次调用）

1. 若 `scriptPromises.has(src)` → 直接返回已有 Promise，不创建新 script。
2. 若 DOM 中已有 `script[src=src]` → 返回 Promise.resolve() 并缓存。
3. 否则：创建 `<script src=src async=false>`，挂 onload/onerror，appendChild 到 head；onload 时 resolve，onerror 时 reject；将 Promise 存入 scriptPromises 并返回。

### 为何 async=false

同层多个模块可能并行调用 loadScript(A)、loadScript(B)；若 async=true，A、B 的执行顺序由网络与浏览器调度决定，可能 B 先于 A 执行，若 B 依赖 A 就会报错。async=false 时，脚本会按“加载完成”顺序依次执行，再结合“层”的保证（本层依赖都在前层已加载），可保证执行顺序满足依赖。

### 接手维护注意

- 不要改为 async=true，否则依赖顺序可能错乱。
- 若某路径在 HTML 与 MODULE_DEPENDENCIES 中重复出现，loadScript 会因 existingScript 或缓存而不会重复执行，属预期。
- 修改脚本路径时注意与 test/index.html 或部署路径一致，否则 404 会触发 onerror 并 reject。

### 调用链中 loadScript 的调用点

- **start_init 内**：`await loadScript(SYSTEM_INFORMATION_MODULE)`（约 1156 行）、`await loadScript(RANDOM_SECURITY_MODULE)`（约 1164 行）为串行；随后 `loadModules(MODULE_DEPENDENCIES)` 内对每一层的每个模块调用 `loadScript(module)`（约 368 行），同层内通过 `Promise.all(layer.map(...))` 并行。
- 因此同一 src 在整次引导中最多被 loadScript 一次（缓存）；若某模块既是“键”又在某键的“值”中作为依赖，会先在其作为依赖被 loadScript 时加载，后续作为键时从 scriptPromises 取到已 resolve 的 Promise，不会重复插入 script。

## 二、loadModules 完整源码与逐行/逐块注释（starter.js 第 308–429 行）

```javascript
async function loadModules(dependencies) {
    // ---------- 第一步：得到拓扑序 ----------
    const sortedModules = topologicalSort(dependencies);

    if (typeof KernelLogger !== 'undefined') {
        KernelLogger.info("BootLoader", `开始加载 ${sortedModules.length} 个模块`, { modules: sortedModules });
    } else {
        console.log(`[内核][BootLoader] 开始加载 ${sortedModules.length} 个模块`);
    }

    // ---------- 第二步：按“层”分组，同层可并行 ----------
    const moduleLayers = [];   // moduleLayers[i] = 第 i 层的模块路径数组
    const loadedModules = new Set();  // 已执行过 loadScript 且成功的模块，避免重复加载

    for (const module of sortedModules) {
        const deps = dependencies[module] || [];
        // 层号计算：无依赖则 0；否则取“各依赖所在层的下标+1”的最大值，保证本模块一定在所有依赖之后
        const layerIndex = deps.length === 0 ? 0 :
            Math.max(...deps.map(dep => {
                const depIndex = sortedModules.indexOf(dep);
                // 找到 dep 所在层：在 moduleLayers 中找第一个包含 dep 的层，其下标+1 即为本模块至少所在的层
                return depIndex >= 0 ? moduleLayers.findIndex(layer => layer.includes(dep)) + 1 : 0;
            }), 0);

        if (!moduleLayers[layerIndex]) {
            moduleLayers[layerIndex] = [];
        }
        moduleLayers[layerIndex].push(module);
    }

    // ---------- 第三步：逐层加载，层内并行 ----------
    for (let layerIndex = 0; layerIndex < moduleLayers.length; layerIndex++) {
        const layer = moduleLayers[layerIndex];

        if (typeof KernelLogger !== 'undefined') {
            KernelLogger.debug("BootLoader", `加载第 ${layerIndex + 1} 层模块 (${layer.length} 个)`, { modules: layer });
        }

        // 对当前层每个 module 启动一个 async 任务，Promise.all 等待本层全部完成后再进入下一层
        await Promise.all(layer.map(async (module) => {
            const deps = dependencies[module] || [];

            // 【先等依赖】若某依赖尚未在 loadedModules 中，则 loadScript(dep)，否则 resolve；
            // 这样即使层号计算有边界情况，也能保证依赖先于当前模块加载
            try {
                await Promise.all(deps.map(dep => {
                    if (!loadedModules.has(dep)) {
                        return loadScript(dep);
                    }
                    return Promise.resolve();
                }));
            } catch (error) {
                const errorMsg = `依赖加载失败: ${module} 的依赖 ${deps.join(', ')} 加载失败: ${error.message}`;
                if (typeof KernelLogger !== 'undefined') {
                    KernelLogger.error("BootLoader", errorMsg, { module, deps, error: error.message });
                }
                throw new Error(errorMsg);
            }

            // 【加载当前模块】
            try {
                await loadScript(module);
                loadedModules.add(module);

                // 【在 DependencyConfig 中登记】从 POOL 取 Dependency（DependencyConfig 实例），
                // 若 dependencyMap 中尚无该 module，则用 DependencyConfig.generate(module) 创建条目并设 linked=true；
                // 供后续 waitLoaded(module) 与模块自身 publishSignal 使用
                if (typeof POOL !== 'undefined' && POOL.__GET__) {
                    try {
                        const Dependency = POOL.__GET__("KERNEL_GLOBAL_POOL", "Dependency");
                        if (Dependency && Dependency.dependencyMap) {
                            if (!Dependency.dependencyMap.has(module)) {
                                Dependency.dependencyMap.set(module, DependencyConfig.generate(module));
                                Dependency.dependencyMap.get(module).linked = true;
                            }
                        }
                    } catch (e) {
                        // POOL 或 Dependency 尚未就绪时忽略，避免引导中断
                    }
                }

                // 【可选：等待模块标记 loaded】给模块 2 秒时间执行 IIFE 并 publishSignal；
                // 若模块未发布则 waitLoaded 超时，catch 后继续，不阻塞整层
                if (typeof POOL !== 'undefined' && POOL.__GET__) {
                    try {
                        const Dependency = POOL.__GET__("KERNEL_GLOBAL_POOL", "Dependency");
                        if (Dependency && typeof Dependency.waitLoaded === 'function') {
                            try {
                                await Dependency.waitLoaded(module, { interval: 10, timeout: 2000 });
                            } catch (e) {
                                if (typeof KernelLogger !== 'undefined') {
                                    KernelLogger.debug("BootLoader", `模块 ${module} 可能未发布信号，继续执行`);
                                }
                            }
                        }
                    } catch (e) {
                        if (typeof KernelLogger !== 'undefined') {
                            KernelLogger.debug("BootLoader", `跳过依赖等待: ${e.message}`);
                        }
                    }
                } else {
                    await new Promise(resolve => setTimeout(resolve, 10));
                }
            } catch (error) {
                const errorMsg = `模块加载失败: ${module} - ${error.message}`;
                if (typeof KernelLogger !== 'undefined') {
                    KernelLogger.error("BootLoader", errorMsg, { module, error: error.message });
                }
                throw new Error(errorMsg);
            }
        }));
    }

    if (typeof KernelLogger !== 'undefined') {
        KernelLogger.info("BootLoader", "所有模块加载完成");
    } else {
        console.log("[内核][BootLoader] 所有模块加载完成");
    }
}
```

### 行为流程（loadModules 一次调用）

1. **拓扑排序**：sortedModules = topologicalSort(dependencies)。
2. **分层**：遍历 sortedModules，对每个 module 根据其 deps 所在层计算 layerIndex，放入 moduleLayers[layerIndex]。
3. **逐层**：for layerIndex 从 0 到 moduleLayers.length-1：
   - 取 layer = moduleLayers[layerIndex]。
   - Promise.all(layer.map(async (module) => { ... }))：
     - 先 Promise.all(deps.map(dep => loadScript(dep) 或 resolve))，保证本模块依赖已加载；
     - await loadScript(module)，loadedModules.add(module)；
     - 从 POOL 取 Dependency，若 dependencyMap 无 module 则 generate 并设 linked=true；
     - 可选 await Dependency.waitLoaded(module, { timeout: 2000 })；超时 catch 后继续；
   - 本层全部完成后进入下一层。
4. **结束**：打日志“所有模块加载完成”。

### 为何先 Promise.all(deps) 再 loadScript(module)

层号是根据“依赖所在层+1”算的，理论上本层依赖应已在前层加载；但若层号计算有误或依赖在 sorted 中但尚未被 loadScript（例如同层另一分支未执行），显式先等 deps 再 load 当前模块可保证**绝对顺序**，避免“模块已执行但依赖未执行”的竞态。

### 为何 waitLoaded 超时后继续

部分模块可能不调用 publishSignal（历史或第三方）；若一直等待会卡死整层。2 秒超时后 catch 并继续，既给正常模块时间就绪，又不因个别模块未适配而阻塞引导。若你新增模块且希望被 waitLoaded 等待，应在模块 IIFE 末尾或初始化完成后调用 DependencyConfig.publishSignal(本模块路径)。

### 层级计算详解（layerIndex 公式）

对每个 `module`，`deps = dependencies[module] || []`。若 `deps.length === 0`，则 `layerIndex = 0`（无依赖，放第 0 层）。否则：

- 对每个 `dep`，在 `sortedModules` 中找 `dep` 的下标 `depIndex`；在已构建的 `moduleLayers` 中找**第一个包含 dep 的层**的下标，记为 `k`，则“本模块至少应在第 `k+1` 层”。
- 取所有依赖对应的 `k+1` 的**最大值**作为 `layerIndex`，保证本模块在所有依赖之后。
- 因为遍历顺序是 sortedModules（拓扑序），当处理到 module 时，其所有 dep 若在键中则已出现在 sorted 更前位置，且已按同样规则被放入某一层，故 `moduleLayers.findIndex(layer => layer.includes(dep))` 一定能找到（dep 已在前面的 module 时被 push 进某层）。

因此层与层之间**严格满足依赖关系**：第 i 层的任意模块的依赖一定在第 0～i-1 层的某一层。

### 常见错误与排查

| 现象 | 可能原因 | 排查与修复 |
|------|----------|------------|
| 某层报「依赖加载失败」 | 依赖路径 404 或 loadScript(dep) reject | 检查 MODULE_DEPENDENCIES 中 dep 路径是否正确、文件是否存在 |
| 某模块执行时其依赖未定义 | 依赖未在 deps 中声明，或 dep 未作为键导致未加载 | 在 dependencies[module] 中补全依赖；若 dep 仅作依赖、不单独加载，需保证 dep 作为某键的依赖已被前层 loadScript |
| Dependency 或 POOL 为 undefined | loadModules 在 start_init 中早于 POOL.__ADD__("Dependency", ...) | 不会发生：start_init 先注册 Dependency 再 loadModules；若在其它入口调用 loadModules，需先确保 POOL 与 Dependency 已就绪 |
| 模块“未就绪”就被使用 | 该模块未 publishSignal 或依赖方未 waitLoaded | 模块末尾调用 DependencyConfig.publishSignal(本模块路径)；依赖方在用到前 await Dependency.waitLoaded(module) |

### 接手维护注意

- 新增模块时在 MODULE_DEPENDENCIES 中写好依赖即可，无需改 loadModules 逻辑；层与顺序由拓扑与 layerIndex 自动得到。
- 若出现“某模块拿到的 Dependency 为 undefined”：检查 POOL 中 "Dependency" 是否在 start_init 中已注册、是否在 loadModules 之前执行。
- 若出现“某模块未就绪就被使用”：确认该模块是否在 IIFE 末尾调用了 publishSignal，或依赖方是否在 waitLoaded 之后才使用。

## 三、本节小结

- **loadScript**：缓存与 DOM 检查避免重复；async=false 保证执行顺序；onload/onerror 决定 resolve/reject。
- **loadModules**：拓扑排序 → 按层分组 → 逐层 Promise.all；层内先等依赖再 loadScript 当前模块，再登记 Dependency、可选 waitLoaded；超时继续以保证鲁棒性。
- 修改加载逻辑时注意：不要改 async；新增模块只改 MODULE_DEPENDENCIES；需要“就绪后再用”的模块应 publishSignal，或依赖方使用 waitLoaded。
