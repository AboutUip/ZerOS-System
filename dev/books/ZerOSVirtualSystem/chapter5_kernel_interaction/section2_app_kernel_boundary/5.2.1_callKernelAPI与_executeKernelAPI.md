# 5.2.1 callKernelAPI 与 _executeKernelAPI

## 本节导读（阅读目标）

本节使读者能够：**① 说出应用访问内核的唯一入口是 callKernelAPI(pid, apiName, args)；② 理解 _callKernelAPICore 中进程存在性、Exploit PID 严格校验、调用栈与 PID 一致性、权限检查、状态允许 API 的先后顺序与含义；③ 理解 _executeKernelAPI(apiName, args, pid) 仅做路由与执行，不负责校验；④ 能根据调用链排查“API 调用被拒绝”类问题。** 源码：`kernel/process/processManager.js`。

---

## 一、唯一入口：callKernelAPI

### 1.1 设计动机

内核提供的能力（文件读写、本地存储、进程自退、异常上报、多线程状态等）若直接暴露给应用层（例如全局可访问的 FileSystem.read），则无法统一做**权限校验**、**调用者身份校验**与**审计日志**。因此 ZerOS 规定：所有**应用层**（及部分系统层）对内核能力的访问，**必须**通过进程管理器提供的**唯一入口**：

```js
// 应用或系统脚本中
const result = await ProcessManager.callKernelAPI(pid, apiName, args);
```

这样：

- **权限**：在入口处统一调用 PermissionManager.checkAndRequestPermission，未授权则拒绝；
- **调用者身份**：通过传入的 pid 与调用栈解析结果（_getCallerPidsFromStack）比对，防止伪造 pid；
- **审计**：每次调用在 _callKernelAPICore 中 _logProgramAction，任务管理器可展示“API 调用记录”。

### 1.2 参数含义

- **pid**：调用方进程 ID；必须与“当前执行上下文”对应，否则会被 _callKernelAPICore 中的调用栈校验拒绝（见下）。应用层通常传入“当前程序”的 pid（由启动时 ProcessManager 分配并注入）。
- **apiName**：字符串，如 `'FileSystem.read'`、`'LocalStorage.get'`、`'Process.requestSelfTermination'` 等；与 _executeKernelAPI 内的 **kernelAPIs** 对象的键一一对应，大小写与拼写必须一致。
- **args**：数组，对应该 API 的实现函数参数列表（如 `['C:/data/config.json']` 或 `['C:/data/config.json', true]` 表示 asBase64）。顺序必须与 kernelAPIs 中该 API 的 handler 参数顺序一致。

返回值：Promise，resolve 为 API 的返回值，reject 为权限被拒、pid 校验失败或 API 内部抛错。

## 二、调用链概览（自上而下）

```
callKernelAPI(pid, apiName, args)
  → _callKernelAPICore(pid, apiName, args, { skipCallerCheck: false })
      → 1. 进程存在性检查：PROCESS_TABLE.get(pid)，不存在则 throw
      → 2. Exploit PID 严格校验：若 processInfo.isExploit 且未 skipCallerCheck，
           则 _isStackFromApplication() 为 true 时 throw（禁止应用栈使用 EXPLOIT_PID）
      → 3. 调用栈与 PID 一致性：_getCallerPidsFromStack()；
           返回 null（系统调用者）时仅 pid === EXPLOIT_PID 放行；
           返回 Set 时必须 callerPids.has(pid)，否则 throw
      → 4. 进程状态允许：非 running 时仅允许 loadingAllowedAPIs 列表内 API，否则 throw
      → 5. 权限检查：_getRequiredPermission(apiName)；
           若需权限则 PermissionManager.checkAndRequestPermission(pid, requiredPermission)，未授权 throw
      → 6. _logProgramAction(pid, 'callKernelAPI', { apiName, args })
      → 7. return await _executeKernelAPI(apiName, args, pid)
  → 返回 API 结果（Promise）
```

**skipCallerCheck**：当 _internalCallKernelAPI 或“进程绑定 API”（如 Exploit 内通过绑定 pid 的封装）调用 _callKernelAPICore 时传入 `{ skipCallerCheck: true }`，跳过步骤 2、3，避免误杀合法系统调用。普通应用**不应**使用 skipCallerCheck。

---

## 三、_callKernelAPICore 中的关键逻辑（逐项说明）

### 3.1 进程存在性

- 代码：`const processInfo = ProcessManager.PROCESS_TABLE.get(pid); if (!processInfo) throw new Error(...)`。
- 含义：pid 必须在进程表中存在，否则视为非法调用（例如 pid 已退出、或伪造 pid）。不通过则不进行后续任何校验，直接抛错。

### 3.2 Exploit 程序（isExploit）与严格校验

- 条件：`processInfo.isExploit === true`（即 pid 为 EXPLOIT_PID，固定 10000）。
- 逻辑：Exploit 是“系统进程”，拥有内核级权限；若**应用层脚本**（如 D/application/xxx）通过某种方式拿到并传入 EXPLOIT_PID 调用 callKernelAPI，则相当于**提权**。因此当 isExploit 时，若**未** skipCallerCheck，会调用 **ProcessManager._isStackFromApplication()**：若调用栈中任一层来自应用目录（如 application/、temp://），则视为“应用层在用 Exploit 的 pid”，**抛错拒绝**。
- 放行情况：skipCallerCheck 为 true（如系统内部 _internalCallKernelAPI），或 _isStackFromApplication() 为 false（栈上无应用路径），则 Exploit 的调用被允许，并记录日志后执行 _executeKernelAPI。

### 3.3 调用栈与 PID 一致性（CVS_ZEROS_009 等防护）

- **ProcessManager._getCallerPidsFromStack()**：从 `new Error().stack` 解析调用栈；跳过 processManager.js、kernel/process 等内核自身栈帧；若某帧匹配 **application/ProgramName** 或 **temp://ProgramName.js**，则用 ProgramName 去进程表中查对应 pid，返回这些 pid 的 Set；若某帧匹配 **system/ui**、**system/expansion** 等，则视为“系统调用者”，返回 **null**。
- 校验规则：
  - 若 **callerPids === null**：表示当前栈是系统/内核代码在调用；此时仅当 **pid === ProcessManager.EXPLOIT_PID** 才放行（系统调用必须用系统进程 pid），否则认为“系统代码却传了普通程序 pid”，抛错。
  - 若 **callerPids** 为 Set：表示栈上能解析出“来自某应用”；此时必须 **callerPids.has(pid)**，即传入的 pid 必须属于该应用（支持多实例时 Set 可能含多个 pid），否则认为“伪造 pid”，抛错。

### 3.4 进程状态（loading/starting）与允许的 API

- 非 **running** 状态的进程（如 loading、starting）原则上不允许调用大多数内核 API，避免在未完全就绪时产生副作用。但**卸载、清理**场景需要：例如程序在 __init__ 中请求自退、删除文件、删除定时任务等。因此维护了一个 **loadingAllowedAPIs** 白名单，例如：
  - `Process.requestSelfTermination`
  - `FileSystem.read`、`FileSystem.delete`
  - `ScheduleTask.getAll`、`ScheduleTask.delete`
- 若 processInfo.status 不是 running 且 apiName 不在该白名单中，则抛错。

### 3.5 权限检查

- **ProcessManager._getRequiredPermission(apiName)**：根据 apiName 返回所需权限名（如 KERNEL_DISK_READ），若该 API 不需要权限则返回 null。
- 若 requiredPermission 存在：调用 **PermissionManager.checkAndRequestPermission(pid, requiredPermission)**；若用户未授权或拒绝，则抛错，**不继续执行** API。
- 特殊：少数 API（如 ScheduleTask.create）需要在**内部**做更细的权限逻辑，因此在 _callKernelAPICore 中对该 apiName 做 **skipDefaultPermissionCheck**，不在这里做默认权限检查，由 API 内部自行调用 PermissionManager。

### 3.6 记录程序行为与执行

- **ProcessManager._logProgramAction(pid, 'callKernelAPI', { apiName, args })**：将该次调用写入该进程的“程序行为”列表（如 actions 数组），供任务管理器「API 调用记录」展示。
- 最后：**return await ProcessManager._executeKernelAPI(apiName, args, pid)**。_executeKernelAPI 内部**不再**做权限或调用者校验，仅做 apiName/args 校验与 kernelAPIs 路由；因此所有“安全与一致性”逻辑都集中在 _callKernelAPICore。

---

## 四、_executeKernelAPI 的职责（仅路由与执行）

- **参数校验**：apiName 非空字符串，args 为数组，否则 throw。
- **路由**：从 **kernelAPIs** 对象中取 `handler = kernelAPIs[apiName]`；若不存在则 throw“无效的 API 名称”。
- **执行**：`return await handler.apply(null, args)`；handler 的 this 不绑定，参数由 args 展开；若实现中需要 **pid**，由 _executeKernelAPI 的第三个参数 pid 通过**闭包**传入（见 5.2.2）。
- **不负责**：权限、调用栈、进程状态等校验均在 _callKernelAPICore 中完成；新增 API 时只需在 kernelAPIs 中注册 handler，记录由 _callKernelAPICore 统一完成。

## 五、常见错误与排查

| 现象 | 可能原因 | 排查与解决 |
|------|----------|------------|
| “Process X does not exist” | pid 不在 PROCESS_TABLE | 确认 pid 为当前程序有效 pid，且进程尚未退出 |
| “禁止应用层使用 Exploit 进程 PID” | 应用代码传入 EXPLOIT_PID(10000) 且栈上有应用路径 | 应用必须使用自身 pid，不得使用 10000 |
| “PID 与调用栈不一致” | 传入的 pid 与 _getCallerPidsFromStack 解析出的不一致 | 确认 callKernelAPI 的 pid 来自当前程序（如启动时保存的 this.pid） |
| “Process X is not running (status: loading)” | 非 running 且 API 不在 loadingAllowedAPIs | 将 API 加入白名单，或延后到 running 后再调用 |
| “没有权限调用 XXX” | PermissionManager 未授权该 pid 的所需权限 | 检查 _getRequiredPermission 映射与用户授权状态 |
| “无效的 API 名称” | apiName 拼写错误或未在 kernelAPIs 中注册 | 对照 kernelAPIs 键名，或新增注册 |

---

## 六、本节小结

- 应用访问内核的**唯一入口**是 **callKernelAPI(pid, apiName, args)**；内部经 **_callKernelAPICore** 做进程存在性、Exploit 严格校验、调用栈与 PID 一致性、进程状态、权限与日志后，由 **_executeKernelAPI** 执行。
- _executeKernelAPI **只负责**路由与执行，不负责校验；新增 API 时在 kernelAPIs 中注册 handler 即可，记录在 _callKernelAPICore 中统一完成。排查“API 调用被拒绝”时按调用链顺序检查：进程存在 → Exploit 校验 → 栈与 PID → 状态 → 权限。
