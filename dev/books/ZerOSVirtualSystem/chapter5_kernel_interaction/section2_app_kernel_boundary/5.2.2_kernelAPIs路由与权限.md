# 5.2.2 kernelAPIs 路由与权限

## 本节导读（阅读目标）

本节使读者能够：**① 说出 _executeKernelAPI 内 kernelAPIs 对象是“apiName → 实现函数”的路由表；② 理解新增内核 API 的步骤：在 kernelAPIs 中加键值、在 _getRequiredPermission 的 apiPermissionMap 中配置所需权限（若需要）；③ 理解 API 实现函数签名为 (...args) 对应 args 数组，pid 由闭包从 _executeKernelAPI 的第三个参数传入；④ 能根据 apiPermissionMap 与权限枚举排查“需要权限”的 API。** 源码：`kernel/process/processManager.js`。

---

## 一、kernelAPIs 路由表的结构与作用

在 **_executeKernelAPI(apiName, args, pid)** 内部，所有可被 callKernelAPI 调用的 API 都在一个对象 **kernelAPIs** 中注册。该对象是**静态维护**的（在函数体内定义，每次调用 _executeKernelAPI 都会重建；实际实现中为一大块字面量），键为 **apiName** 字符串，值为**异步或同步函数**（handler）。执行逻辑可概括为：

```js
// 伪代码
const kernelAPIs = {
    'FileSystem.read': async (path, asBase64) => { /* 实现；需要 pid 时从闭包取 */ },
    'FileSystem.write': async (path, content, asBase64) => { ... },
    'FileSystem.list': async (path) => { ... },
    'LocalStorage.get': async (key) => { ... },
    'LocalStorage.set': async (key, value) => { ... },
    'Process.requestSelfTermination': async () => { /* 内部用 pid */ },
    'Exception.report': async (message, targetPid) => { ... },
    'Multithreading.getPoolStatus': async () => { ... },
    // ... 大量其它 API
};
const handler = kernelAPIs[apiName];
if (!handler) throw new Error('无效的 API 名称');
return await handler.apply(null, args);
```

- **键**：与 callKernelAPI 的 apiName **完全一致**（如 `'FileSystem.read'`），大小写敏感。
- **值**：函数，参数与 **args** 一一对应；若实现中需要 **pid**，由 _executeKernelAPI 的第三个参数 **pid** 通过**闭包**传入（见下）。
- **调用方式**：`handler.apply(null, args)`，因此 args 必须与 API 文档/实现参数顺序一致；返回值一般为 Promise，由 _executeKernelAPI 原样返回。

这样设计便于**集中维护**所有“应用可调用的内核能力”，新增或下架 API 只需增删 kernelAPIs 中的项；权限与调用者校验已在 _callKernelAPICore 中统一完成，此处不再重复。

---

## 二、实现函数与 pid 的传递

许多 API 需要“当前调用进程”的 pid（例如分配内存、创建会话、上报异常、请求自退）。callKernelAPI 的调用方已经传入了 pid，该 pid 在 _callKernelAPICore 校验通过后，作为第三个参数传入 _executeKernelAPI(apiName, args, pid)。由于 **handler 是在 _executeKernelAPI 函数体内定义的闭包**，可以访问参数 pid，因此实现中可以这样写：

```js
'Process.requestSelfTermination': async () => {
    if (!pid) throw new Error('Process.requestSelfTermination: 无法获取进程 ID');
    // 使用 pid 做后续逻辑（如查表、通知 MemoryManager/GUIManager 等）
},
'Exception.report': async (message, targetPid) => {
    const exceptionPid = targetPid !== undefined && targetPid !== null ? targetPid : pid;
    // 使用 exceptionPid 上报异常
},
```

应用层只需 `await ProcessManager.callKernelAPI(this.pid, 'Process.requestSelfTermination', [])`，**无需在 args 里再传 pid**；pid 由内核在入口处校验并注入到实现中。

## 三、权限映射 _getRequiredPermission 与 apiPermissionMap

在 _callKernelAPICore 中，会调用 **ProcessManager._getRequiredPermission(apiName)** 得到该 API 所需权限（如 `KERNEL_DISK_READ`）；若存在，则通过 **PermissionManager.checkAndRequestPermission(pid, requiredPermission)** 检查，未授权则拒绝调用。

** _getRequiredPermission** 内部维护一个 **apiPermissionMap** 对象：键为 apiName，值为 PermissionManager.PERMISSION 下的枚举（或 null 表示该 API 不需要权限）。节选如下（见 processManager.js 约 3357–3427 行）：

```js
// 节选：apiPermissionMap 部分项
const apiPermissionMap = {
    'FileSystem.read': PermissionManager.PERMISSION.KERNEL_DISK_READ,
    'FileSystem.write': PermissionManager.PERMISSION.KERNEL_DISK_WRITE,
    'FileSystem.delete': PermissionManager.PERMISSION.KERNEL_DISK_DELETE,
    'FileSystem.create': PermissionManager.PERMISSION.KERNEL_DISK_CREATE,
    'FileSystem.list': PermissionManager.PERMISSION.KERNEL_DISK_LIST,
    'Notification.create': PermissionManager.PERMISSION.SYSTEM_NOTIFICATION,
    'Notification.remove': PermissionManager.PERMISSION.SYSTEM_NOTIFICATION,
    'Network.request': PermissionManager.PERMISSION.NETWORK_ACCESS,
    'GUI.createWindow': PermissionManager.PERMISSION.GUI_WINDOW_CREATE,
    'GUI.manageWindow': PermissionManager.PERMISSION.GUI_WINDOW_MANAGE,
    'Storage.read': PermissionManager.PERMISSION.SYSTEM_STORAGE_READ,
    'Storage.write': PermissionManager.PERMISSION.SYSTEM_STORAGE_WRITE,
    'Environment.get': PermissionManager.PERMISSION.ENVIRONMENT_READ,
    'Environment.set': PermissionManager.PERMISSION.ENVIRONMENT_WRITE,
    'Theme.read': PermissionManager.PERMISSION.THEME_READ,
    'Theme.write': PermissionManager.PERMISSION.THEME_WRITE,
    'Desktop.manage': PermissionManager.PERMISSION.DESKTOP_MANAGE,
    'Desktop.addShortcut': PermissionManager.PERMISSION.DESKTOP_SHORTCUT,
    'Taskbar.pinProgram': PermissionManager.PERMISSION.DESKTOP_MANAGE,
    'Event.register': PermissionManager.PERMISSION.EVENT_LISTENER,
    // ... 更多
};
return apiPermissionMap[apiName] || null;
```

- **新增需要权限的 API 时**：在 kernelAPIs 中增加实现；在 **_getRequiredPermission** 的 **apiPermissionMap** 中增加 `apiName → permission`；若某 API 需“内部特殊权限逻辑”（如 ScheduleTask.create），则在 _callKernelAPICore 中把该 apiName 加入 **skipDefaultPermissionCheck** 分支，在 API 内部自行调用 PermissionManager。
- **不需要权限的 API**：apiPermissionMap 中不写该 apiName，或显式写为 null；_getRequiredPermission 返回 null，_callKernelAPICore 中跳过权限检查。

---

## 四、新增内核 API 的完整步骤（清单）

1. **在 _executeKernelAPI 的 kernelAPIs 对象中**增加键值：`'Module.method': async (arg1, arg2, ...) => { ... }`；若实现需要 pid，在闭包内使用 _executeKernelAPI 的 pid 参数。
2. **若该 API 需要默认权限检查**：在 _getRequiredPermission 的 apiPermissionMap 中增加 `'Module.method': PermissionManager.PERMISSION.XXX`。
3. **若该 API 需在 loading/starting 状态可调**：在 _callKernelAPICore 的 loadingAllowedAPIs 数组中增加 `'Module.method'`。
4. **若该 API 需跳过默认权限、在内部自行检查**：在 _callKernelAPICore 中对 apiName 做 skipDefaultPermissionCheck 判断，并在实现内调用 PermissionManager。
5. **记录**：无需单独写 _logProgramAction；_callKernelAPICore 已对每次 callKernelAPI 统一记录。

## 五、常见错误与排查

| 现象 | 可能原因 | 排查与解决 |
|------|----------|------------|
| “无效的 API 名称” | apiName 拼写错误或未在 kernelAPIs 中注册 | 对照 kernelAPIs 键名，或按上述步骤新增注册 |
| 参数对不上（undefined/类型错误） | args 顺序或个数与 handler 参数不一致 | 确认 callKernelAPI 的 args 与 kernelAPIs 中该 API 的参数列表一致 |
| “无法获取进程 ID” | handler 内使用 pid 但 pid 为 null | 确保 callKernelAPI 传入有效 pid；Exploit 内部调用也会传 pid |
| 权限被拒 | apiPermissionMap 中该 API 需要权限但用户未授权 | 检查 PermissionManager 声明与用户授权；或该 API 改为内部权限逻辑并 skipDefaultPermissionCheck |

---

## 六、本节小结

- **_executeKernelAPI** 通过 **kernelAPIs** 路由到具体实现；新增 API 即在 kernelAPIs 中加键值，实现函数参数与 args 对应，**pid 由闭包传入**。
- 权限由 **_getRequiredPermission** 的 **apiPermissionMap** 配置；需要默认权限检查的 API 在此映射；特殊逻辑的 API 可跳过默认检查并在内部自行检查。新增 API 时按“完整步骤”清单操作即可。
