# 5.2.3 recordKernelModuleCall 与调用溯源

## 本节导读（阅读目标）

本节使读者能够：**① 区分“通过 callKernelAPI 调用”与“直接调用内核模块”的日志记录方式；② 说出 recordKernelModuleCall 的用途：供不经过 callKernelAPI 的内核模块在入口处写入程序行为日志，便于任务管理器展示与调用溯源；③ 知道哪些模块已接入 recordKernelModuleCall，新增可直接被程序调用的内核入口时应在入口处调用；④ 能根据任务管理器「API 调用记录」理解“谁在何时调用了什么”。** 源码：`kernel/process/processManager.js`、各内核模块。

---

## 一、两种调用路径与记录方式

### 1.1 路径一：应用通过 callKernelAPI

应用调用 `ProcessManager.callKernelAPI(pid, apiName, args)` → _callKernelAPICore → 在**执行 _executeKernelAPI 之前**已调用 **ProcessManager._logProgramAction(pid, 'callKernelAPI', { apiName, args })** → 再执行 _executeKernelAPI。

因此：**所有经 callKernelAPI 的调用**都会在 _callKernelAPICore 中**统一**写入一条「callKernelAPI」程序行为记录，任务管理器「API 调用记录」据此展示；**内核模块的实现函数内部无需再调用 recordKernelModuleCall**。这样避免重复记录，且 apiName 与 args 由入口处唯一确定。

### 1.2 路径二：程序或系统直接调用内核模块

某些能力并非通过 callKernelAPI 暴露，而是由**系统层或内核其他模块**直接调用。例如：

- 某处直接调用 **GUIManager.registerWindow(pid, ...)**、**GUIManager.unregisterWindow(pid)**；
- 某处直接调用 **MemoryManager.allocateMemory(pid, ...)**、**MemoryManager.freeMemory(pid)**；
- **PermissionManager.checkAndRequestPermission**、**PermissionManager.grant** 等由 _callKernelAPICore 内部调用，但若某路径是“程序触发”的（如用户点击授权），也需要在任务管理器中体现“该程序进行了权限相关操作”。

这类调用**不经过** callKernelAPI，因此 _callKernelAPICore 不会执行，也就不会自动写入「callKernelAPI」记录。若仍希望在任务管理器中看到“该进程调用了某内核能力”，则需要在**该内核模块的入口处**（在完成主要逻辑前或后）调用 **ProcessManager.recordKernelModuleCall(pid, '模块.方法', details)**，将本次调用写入该 pid 的“程序行为”列表。

注释中的说明（processManager.js）：  
> NodeTree、Disk、FileFramework、LStorage 等 kernel 层模块**仅由 _executeKernelAPI 在处理 callKernelAPI 时内部调用**，程序通过 callKernelAPI(pid, 'FileSystem.xxx'|'LocalStorage.xxx', ...) 访问，_callKernelAPICore 已统一记录为 callKernelAPI(apiName)，故这些 kernel 模块**无需再接入 recordKernelModuleCall**。  
> **新增可直接被程序调用的内核模块时，应在入口处调用 recordKernelModuleCall(pid, '模块.方法', details)。**

## 二、recordKernelModuleCall 的签名与含义

```js
/**
 * 供内核模块直接调用的记录接口：当程序不通过 callKernelAPI 而直接调用内核模块时，
 * 由该模块在入口处调用此方法以写入程序日志。
 * @param {number} pid 进程 ID（无效或系统调用时可不记录或传 null）
 * @param {string} moduleMethod 行为名称，如 'Process.killProgram'、'Memory.allocateMemory'
 * @param {Object} details 详细信息，如 { force }、{ heapSize, shedSize }、{ permission }
 */
static recordKernelModuleCall(pid, moduleMethod, details = {}) {
    ProcessManager._logProgramAction(pid, moduleMethod, details);
}
```

- **pid**：发起该次调用的进程 ID。若为系统内部调用、无法对应到具体程序，可传 null 或 -1，此时仍可能写入日志但可能不影响“按 pid 筛选”的展示逻辑（视 _logProgramAction 实现而定）。
- **moduleMethod**：字符串，建议格式为 **「模块.方法」**，如 `'Process.killProgram'`、`'Memory.allocateMemory'`、`'Permission.checkAndRequest'`。用于在任务管理器「API 调用记录」中展示“哪个模块的哪次调用”，便于溯源与审计。
- **details**：对象，记录该次调用的关键参数或结果摘要，如 `{ force: true }`、`{ heapSize, shedSize }`、`{ permission: 'KERNEL_DISK_READ' }`。便于排查与审计，不必记录敏感内容。

内部实现即调用 **ProcessManager._logProgramAction(pid, moduleMethod, details)**，与 _callKernelAPICore 中记录 callKernelAPI 使用同一套“程序行为”存储（如 actions 数组），因此任务管理器可统一展示。

## 三、已接入的模块（示例）

根据源码注释与 grep 结果，以下模块已在**直接对外入口**处调用 recordKernelModuleCall：

| 模块 | 调用的 moduleMethod（示例） | 说明 |
|------|-----------------------------|------|
| ProcessManager 自身 | Process.killProgram、Process.requestSelfTermination、Process.setBackground、Process.registerBackgroundTrayClick、Process.registerBackgroundTrayContextMenu | 这些既可能是 callKernelAPI 入口，也可能内部再调 recordKernelModuleCall 以区分“程序行为”粒度 |
| MemoryManager | Memory.allocateMemory、Memory.freeMemory、Memory.checkMemory | 分配/释放/检查内存时若由某 pid 触发，记录该 pid |
| PermissionManager | Permission.checkAndRequest、Permission.grant、Permission.revoke | 权限请求、授予、撤销时记录发起方 pid（若可解析） |

**GUIManager**、**NotificationManager** 等若存在“被程序或系统直接调用且需在任务管理器中展示”的入口，也应在入口处调用 recordKernelModuleCall，以便“API 调用记录”完整反映该进程对内核的访问。

## 四、何时接入 recordKernelModuleCall

- **仅通过 callKernelAPI 暴露的能力**：实现写在 _executeKernelAPI 的 kernelAPIs 中，**不需要**在实现内再调 recordKernelModuleCall；记录已在 _callKernelAPICore 中统一完成。
- **存在“直接调用”入口的内核模块**：若该入口可能由“某程序（pid）”触发（例如系统层代表某程序调用 GUIManager.registerWindow(pid, ...)），则在该入口处**传入该 pid** 并调用 **recordKernelModuleCall(pid, '模块.方法', details)**，便于任务管理器与审计。

---

## 五、常见错误与排查

| 现象 | 可能原因 | 排查与解决 |
|------|----------|------------|
| 任务管理器中看不到某次“直接调用” | 该内核入口未调用 recordKernelModuleCall | 在入口处增加 recordKernelModuleCall(pid, 'Module.method', details) |
| 重复出现同一次调用 | 既经 callKernelAPI 又在内核实现内调用了 recordKernelModuleCall | 经 callKernelAPI 的路径不要在内核实现内再记；仅“直接调用”路径记 |
| moduleMethod 展示不统一 | 各模块自拟字符串格式不一致 | 建议统一为「模块.方法」，如 Memory.allocateMemory、Permission.grant |

---

## 六、本节小结

- **经 callKernelAPI** 的调用由 _callKernelAPICore **统一记录**，内核实现**不必**再记。
- **直接调用内核模块**时，该模块应在入口处调用 **recordKernelModuleCall(pid, '模块.方法', details)**，以便调用溯源与任务管理器展示；新增可直接被程序调用的内核入口时需遵循此约定。已接入示例：ProcessManager、MemoryManager、PermissionManager；GUIManager、NotificationManager 等可按需接入。
