# 5.4.1 应用读取文件的完整调用链

## 本节导读（阅读目标）

本节以**应用层调用 FileSystem.read 读取一个文件**为例，从应用脚本到内核、再到 Disk/NodeTree 或 PHP 后端，**完整走一遍调用链**。读者可据此理解：callKernelAPI 如何进入 _callKernelAPICore、权限与 pid 校验、_executeKernelAPI 如何路由到 FileSystem.read、FileSystem.read 内部如何取 Disk、NodeTree、以及何时走 PHP 直读。涉及 5.1（POOL/KernelMemory）、5.2（callKernelAPI/kernelAPIs）、5.3（ProcessManager 与各模块协作）。

---

## 一、应用侧入口

假设应用脚本（如 D/application/Terminal/main.js）中需要读取 `C:/data/config.json`，则调用：

```js
const content = await ProcessManager.callKernelAPI(this.pid, 'FileSystem.read', ['C:/data/config.json']);
```

- **this.pid**：该程序启动时由 ProcessManager 分配并注入的进程 ID。
- **'FileSystem.read'**：与 kernelAPIs 中的键一致。
- **['C:/data/config.json']**：对应 handler 的第一个参数 path；若需 base64 可传 `['C:/data/config.json', true]`。

---

## 二、ProcessManager 内部：callKernelAPI → _callKernelAPICore

1. **callKernelAPI(pid, apiName, args)** 调用 **_callKernelAPICore(pid, apiName, args, { skipCallerCheck: false })**。

2. **_callKernelAPICore** 依次执行：
   - **进程存在性**：PROCESS_TABLE.get(pid) 存在，否则 throw。
   - **Exploit 校验**：若 pid 为 EXPLOIT_PID 且 _isStackFromApplication() 为 true，throw；本例为普通应用 pid，跳过。
   - **调用栈与 PID**：_getCallerPidsFromStack() 解析栈，匹配到 application/Terminal 或类似路径，返回包含 this.pid 的 Set；callerPids.has(pid) 为 true，通过。
   - **进程状态**：status 为 running（或允许的 loading 白名单），通过。
   - **权限**：_getRequiredPermission('FileSystem.read') 返回 KERNEL_DISK_READ；PermissionManager.checkAndRequestPermission(pid, KERNEL_DISK_READ)；若用户已授权或本次授权通过，继续；否则 throw。
   - **_logProgramAction(pid, 'callKernelAPI', { apiName: 'FileSystem.read', args })**。
   - **return await _executeKernelAPI('FileSystem.read', ['C:/data/config.json'], pid)**。

---

## 三、_executeKernelAPI：路由到 FileSystem.read

1. **_executeKernelAPI(apiName, args, pid)** 内：
   - 校验 apiName 非空、args 为数组。
   - **handler = kernelAPIs['FileSystem.read']**，存在。
   - **return await handler(path, asBase64)**，其中 path = 'C:/data/config.json'，asBase64 = args[1]（未传则为 undefined）。handler 为闭包，可访问 pid（若实现需要）。

2. **FileSystem.read** 的实现（在 processManager.js 的 kernelAPIs 中）大致逻辑：
   - 解析 path：盘符 + 路径 + 文件名；如 parts = ['C:', 'data', 'config.json']，diskName = 'C:'，dirPath = 'C:/data'，fileName = 'config.json'。
   - **Disk.diskSeparateMap** / **Disk.diskSeparateSize**：检查 diskName 分区是否存在；若不存在 throw。
   - **nodeTree = diskMap.get(diskName)**：从 POOL 或 Disk 内部映射取该分区的 NodeTreeCollection；若不存在或未初始化，可能尝试 **NodeTreeCollection** 新建并 **POOL.__ADD__("KERNEL_GLOBAL_POOL", diskName, nodeTree)**，再 **nodeTree._rebuildFromPHP()**；若仍不可用则走“从 PHP 服务直接读取”路径。
   - **若 nodeTree 存在且 initialized**：通过 NodeTree/FileFramework 按 dirPath + fileName 读取文件内容（可能再请求 PHP 或本地缓存）。
   - **若 nodeTree 不存在或未初始化**：构造 PHP 服务 URL（如 SystemInformation.buildServiceUrlObject、action=read_file、path、fileName），**fetch** 该 URL，返回响应内容（或 base64）。
   - 返回内容给上层，最终返回到应用。

---

## 四、涉及 POOL、KernelMemory、协作

- **POOL**：Disk/文件系统 init 或 FileSystem.read 内可能将 **diskName（如 "C:"）→ NodeTreeCollection** 注册到 POOL；FileSystem.read 通过 **Disk.diskSeparateMap** 或等价方式取到 NodeTree（可能来自 POOL 或 Disk 内部缓存）。
- **KernelMemory**：FileSystem.read 不直接读写 KernelMemory；但 **Disk** 可能从 KernelMemory 的 **DISK_SEPARATE_MAP** 等 key 读分区列表；ProcessManager 的 PROCESS_TABLE 来自 KernelMemory，用于 _callKernelAPICore 的进程存在性检查。
- **权限**：FileSystem.read 需要 KERNEL_DISK_READ，在 _callKernelAPICore 中已检查；LStorage 不参与本条链。

---

## 五、本节小结

- 应用 **callKernelAPI(pid, 'FileSystem.read', [path])** → **_callKernelAPICore**（进程存在、Exploit/栈校验、状态、权限、记录）→ **_executeKernelAPI** → **kernelAPIs['FileSystem.read'](path, asBase64)** → 解析 path、取 Disk/NodeTree、读文件或走 PHP 直读 → 返回内容。
- 整条链体现了“唯一入口、权限与 pid 校验、内核实现与 POOL/Disk 协作”；若遇“读取失败”或“权限被拒”，可按链逐段排查：pid 是否正确、权限是否授权、分区与 NodeTree 是否就绪、PHP 服务是否可用。
