# 5.4.2 进程退出与资源回收的完整调用链

## 本节导读（阅读目标）

本节以**进程退出**（kill 或 requestSelfTermination）为例，从 ProcessManager 的退出入口到 **PROCESS_TABLE 更新、MemoryManager.freeMemory、GUIManager 注销窗口、EventManager 清理监听**的**完整顺序**做文字描述。读者可据此理解 5.3 中“典型协作模式”在一条链上的具体体现，并在修改退出逻辑时保持顺序一致。

---

## 一、退出入口

- **ProcessManager.kill(pid, force)** 或 **Process.requestSelfTermination(pid)**（后者可能由应用通过 callKernelAPI(pid, 'Process.requestSelfTermination', []) 触发）。
- 内部会进入统一的“进程退出”处理逻辑：更新进程状态、执行清理、从 PROCESS_TABLE 移除或标记。

---

## 二、退出流程中的协作顺序（典型）

以下顺序为逻辑顺序；实际代码可能合并或异步，但**语义上**应保证：

1. **更新进程状态**  
   ProcessManager 将 PROCESS_TABLE 中该 pid 的状态更新为“退出中”或类似，避免后续再以该 pid 调用 callKernelAPI 被误认为有效进程。

2. **释放内存**  
   调用 **MemoryManager.freeMemory(pid)**：
   - MemoryManager 根据 APPLICATION_SOP 找到该 pid 的 Heap/Shed 分区，执行释放；
   - 从 APPLICATION_SOP 中删除该 pid 的条目；
   - 可选 recordKernelModuleCall(pid, 'Memory.freeMemory', {})。

3. **注销窗口**  
   调用 **GUIManager** 的“按 pid 注销窗口”接口（如 unregisterWindow 逐窗、或按 pid 批量清理），将该 pid 下的所有窗口从任务栏、窗口列表移除，并做 DOM 清理。

4. **清理事件监听**  
   调用 **EventManager** 的“按 pid 移除监听”接口，将该 pid 注册的全局/局部监听器移除，避免悬空引用与后续误派发。

5. **最终移除进程表条目**  
   ProcessManager 从 PROCESS_TABLE 中删除该 pid（或标记为已退出），并持久化到 KernelMemory（若实现如此）。

6. **其他清理**  
   若有“按 pid 注册”的其它资源（如通知、定时任务、后台托盘等），在同一退出流程中一并清理（参见第 3 章 3.2.4 与 processManager.js 中的退出实现）。

---

## 三、为何顺序重要

- **先释放内存、再清窗口/事件**：避免窗口或事件回调中仍访问“已释放”的 pid 分区。
- **先更新状态/再释放**：避免在释放过程中其他逻辑仍把该 pid 当作有效进程分配新资源。
- **GUIManager 与 EventManager 的顺序**：视实现而定，通常先窗口后事件，或并行；只要保证“使用 pid 的资源”都在 ProcessManager 驱动下按 pid 清理即可。

---

## 四、本节小结

- 进程退出时 ProcessManager **依次**：更新 PROCESS_TABLE 状态 → **MemoryManager.freeMemory(pid)** → **GUIManager 按 pid 注销窗口** → **EventManager 按 pid 清理监听** → 最终移除 PROCESS_TABLE 条目及它资源。
- 整条链体现 5.3 的协作模式：ProcessManager 为驱动方，MemoryManager、GUIManager、EventManager 为被调方；修改退出逻辑时保持上述顺序与 5.3.1、5.3.2 的约定一致。
