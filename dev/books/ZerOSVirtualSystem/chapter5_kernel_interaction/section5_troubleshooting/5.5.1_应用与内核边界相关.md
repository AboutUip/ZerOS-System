# 5.5.1 应用与内核边界相关

## 本节导读（阅读目标）

本节汇总与 **callKernelAPI、_callKernelAPICore、权限、kernelAPIs、recordKernelModuleCall** 相关的常见错误与排查思路，便于快速定位“API 调用被拒绝”“无效的 API 名称”“权限被拒”等问题。

---

## 一、callKernelAPI 与 pid/栈校验

| 现象 | 可能原因 | 排查与解决 |
|------|----------|------------|
| “Process X does not exist” | pid 不在 PROCESS_TABLE | 确认 pid 为当前程序有效 pid，且进程尚未退出；应用应使用启动时注入的 this.pid |
| “禁止应用层使用 Exploit 进程 PID” | 应用代码传入 EXPLOIT_PID(10000) 且栈上有 application 等路径 | 应用必须使用自身 pid，不得使用 10000；检查传参是否误写死 10000 |
| “PID 与调用栈不一致” | 传入的 pid 与 _getCallerPidsFromStack 解析出的不一致 | 确认 callKernelAPI 的 pid 来自当前程序（如 this.pid）；多实例时 pid 应对应当前实例 |
| “调用栈显示为系统代码，但传入的 PID 不是系统进程” | 系统/内核代码调用 callKernelAPI 时传了普通程序 pid | 系统调用应传 EXPLOIT_PID，或使用 _internalCallKernelAPI / skipCallerCheck |

---

## 二、进程状态与 loadingAllowedAPIs

| 现象 | 可能原因 | 排查与解决 |
|------|----------|------------|
| “Process X is not running (status: loading)” | 非 running 且调用的 API 不在 loadingAllowedAPIs | 将所需 API 加入 loadingAllowedAPIs 白名单，或延后到 status 为 running 后再调用 |

---

## 三、权限

| 现象 | 可能原因 | 排查与解决 |
|------|----------|------------|
| “没有权限调用 XXX（需要权限: YYY）” | PermissionManager 未授权该 pid 的所需权限 | 检查 _getRequiredPermission 的 apiPermissionMap 中该 API 对应权限；确认用户已授权或 checkAndRequestPermission 流程完成 |
| 某 API 需要特殊权限逻辑 | 默认权限检查不适用 | 在 _callKernelAPICore 中对该 apiName 做 skipDefaultPermissionCheck，在 API 内部自行调用 PermissionManager |

---

## 四、kernelAPIs 与参数

| 现象 | 可能原因 | 排查与解决 |
|------|----------|------------|
| “无效的 API 名称” | apiName 拼写错误或未在 kernelAPIs 中注册 | 对照 kernelAPIs 键名（大小写一致）；或按 5.2.2 新增注册 |
| 参数对不上（undefined/类型错误） | args 顺序或个数与 handler 参数不一致 | 确认 callKernelAPI 的 args 与 kernelAPIs 中该 API 的参数列表一致 |
| “无法获取进程 ID” | handler 内使用 pid 但 pid 为 null | 确保 callKernelAPI 传入有效 pid |

---

## 五、recordKernelModuleCall

| 现象 | 可能原因 | 排查与解决 |
|------|----------|------------|
| 任务管理器中看不到某次“直接调用” | 该内核入口未调用 recordKernelModuleCall | 在直接调用入口处增加 recordKernelModuleCall(pid, 'Module.method', details) |
| 同一次调用重复出现 | 既经 callKernelAPI 又在内核实现内调用了 recordKernelModuleCall | 经 callKernelAPI 的路径不要在内核实现内再记 |
