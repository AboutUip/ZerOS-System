# 5.1.4 通信机制小结与选型

## 本节导读（阅读目标）

本节对 5.1 的三种通信机制做**归纳与选型指南**：在“模块间要传递什么、何时需要”的前提下，如何选择 POOL、KernelMemory 或事件；并给出**组合使用**的典型模式与一张总表，便于读者在开发或排查时快速决策。

---

## 一、三种机制回顾

- **POOL**：按**类别 + 名称**存贮**对象引用**；生命周期与当前会话一致；用于**模块发现**与“按名取引用”。接口：__ADD__、__GET__、__HAS__、__INIT__、__UPDATE__ 等（见第 2 章 2.4）。
- **KernelMemory**：按 **key** 存贮**可序列化数据**；数据在 Exploit 的 Heap/Shed 中，可持久化；用于**跨模块、跨会话的共享状态**。接口：loadData(key)、saveData(key, data)；与 MemoryManager.APPLICATION_SOP、_ensureMemory 配合（见第 3 章 3.5）。
- **事件**：在 **document.body** 上派发 CustomEvent，监听方 addEventListener；用于**“某时刻发生了某件事”**的**解耦通知**，不存业务状态。典型：dependencyLoaded、主题/语言变更。

---

## 二、选型总表

| 需求 | 推荐机制 | 说明 |
|------|----------|------|
| 需要拿到某模块暴露的**对象/单例/类** | POOL | 按名取引用，会话内有效 |
| 需要**持久化**且多模块共享的**数据** | KernelMemory | 按 key 读写，负责方单写、读通过 API 或 loadData |
| 需要**在某一时刻通知多方**（就绪、主题/语言变更） | 事件 | 派发 + 监听，不存状态 |
| 需要“数据变更时通知” | KernelMemory + 事件 | 数据仍存 KernelMemory；负责方在变更后派发事件，或提供订阅 API |
| 需要**跨会话**且为**对象引用** | 不可行 | 对象引用不能序列化；需改为“存数据 + 启动时重建对象” |

---

## 三、组合使用典型模式

- **引导阶段**：BootLoader 依赖 DependencyConfig；DependencyConfig 通过 **dependencyLoaded 事件** 更新 dependencyMap；BootLoader 通过 **POOL** 注册 Dependency、startKernel、WORK_SPACE，供后续 **waitForCoreModules** 等使用。这里“就绪”用事件，“发现”用 POOL。
- **进程与内存**：ProcessManager 维护 PROCESS_TABLE，写入 **KernelMemory**；MemoryManager 维护 APPLICATION_SOP，也写入 KernelMemory。其他模块**不直接** loadData('PROCESS_TABLE')，而是通过 **ProcessManager 的 API** 访问；ProcessManager 内部再读 KernelMemory。这里“共享状态”用 KernelMemory，“封装”用负责方 API。
- **系统 UI 与内核**：TaskbarManager 通过 **POOL** 取 GUIManager，再调用其方法；ThemeManager 切换主题后**派发事件**，GUIManager、TaskbarManager 监听并刷新。这里“发现”用 POOL，“通知”用事件。

---

## 四、本节小结

- POOL、KernelMemory、事件三者分工明确：**发现用 POOL、持久化共享用 KernelMemory、通知用事件**。
- 选型时根据“要取引用 / 要存数据 / 要通知发生”及是否跨会话，对照上表选择；组合使用时注意“负责方”与封装，避免多处直接写同一 key 或散落事件类型。
