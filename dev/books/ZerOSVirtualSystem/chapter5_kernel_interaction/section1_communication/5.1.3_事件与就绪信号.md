# 5.1.3 事件与就绪信号

## 本节导读（阅读目标）

本节使读者能够：**① 明确“事件”在模块间通信中的角色：解耦的“就绪通知”或“状态变更通知”；② 说出 dependencyLoaded、主题/风格变更等事件的派发方与监听方；③ 理解与 POOL/KernelMemory 的差异：事件是“一次性或订阅式”的通信，不存状态；④ 能根据需求在合适场景选用“事件”而非 POOL 或 KernelMemory。** 与第 2 章 2.2.3、第 4 章 4.1 互补。

---

## 一、事件作为解耦通知

### 1.1 设计动机

除 POOL（发现）与 KernelMemory（共享状态）外，ZerOS 还需要一种**“某件事发生了，通知关心方”**的机制：例如“某模块脚本已执行完毕”“主题已切换”“语言已变更”。若用 POOL，只能“取引用”，无法表达“刚刚发生”的时机；若用 KernelMemory，需要调用方轮询 key 的变化，耦合高且易遗漏。因此采用 **DOM CustomEvent** 做**解耦通知**：

- **派发方**：某模块在“某件事完成”时执行：  
  `document.body.dispatchEvent(new CustomEvent(type, { detail: {...} }))`。
- **监听方**：其他模块在 document.body 上 `addEventListener(type, handler)`，在 handler 中根据 `detail` 做后续动作。

这样**派发方不需要知道“谁在听”**；**监听方不需要直接引用派发方**，只需约定事件类型与 detail 结构。适用于“就绪信号”“主题/语言变更”等**事件驱动**的协作。

### 1.2 典型用法

- 就绪信号：模块 A 执行完后派发 `dependencyLoaded`（或内部等价事件），模块 B（如 DependencyConfig）监听后更新依赖图状态，使 waitLoaded 能 resolve。
- 主题/风格变更：ThemeManager 在用户切换主题后派发自定义事件，GUIManager、TaskbarManager 等监听并刷新样式。
- 语言切换：LanguagesExpansion 或相关模块派发语言变更事件，TaskbarManager、NotificationManager、LockScreen 等监听并刷新多语言文案。

---

## 二、典型事件与流向

| 事件类型 | 派发方 | 监听方 | 含义 |
|----------|--------|--------|------|
| dependencyLoaded | 各模块（通过 DependencyConfig.publishSignal） | DependencyConfig 实例（constructor 内注册） | 模块已执行并“就绪”，用于 waitLoaded |
| ThemeManager 风格/主题变更 | ThemeManager | GUIManager、TaskbarManager 等 | 更新窗口样式、任务栏图标等 |
| 语言切换 | LanguagesExpansion 或相关 | TaskbarManager、NotificationManager、LockScreen | 刷新多语言文案 |

**dependencyLoaded**：在第 2 章 2.2.3 中已详述。各模块脚本末尾调用 `DependencyConfig.publishSignal(模块路径)`，DependencyConfig 的 constructor 内注册的 handler 将 dependencyMap 中对应条目标记为 loaded，从而使 waitLoaded 的轮询能发现“所有依赖已 loaded”并 resolve。注意：waitLoaded 内部是**轮询** dependencyMap 的 loaded 状态，而 loaded 的置位是由 **dependencyLoaded 事件**驱动的，因此事件在这里起到“通知 DependencyConfig 更新状态”的作用。

## 三、事件与 POOL/KernelMemory 的对比

| 维度 | POOL | KernelMemory | 事件 |
|------|------|--------------|------|
| 主要语义 | 按名取引用 | 按 key 读写数据 | 某时刻“发生了一件事” |
| 调用方式 | 同步 __GET__ | 同步/异步 loadData/saveData | 派发 + 监听，异步收到 |
| 是否存状态 | 存对象引用（非持久） | 存可序列化数据（持久） | 不存业务状态，仅传递 detail |
| 典型场景 | 模块发现、获取单例 | 进程表、内存元数据等 | 就绪信号、主题/语言变更 |

- **POOL**：同步“取引用”；无“通知”语义；谁需要谁去 __GET__。
- **KernelMemory**：同步或异步“读/写 key”；表达的是“共享状态”，不是“事件发生”。
- **事件**：异步“通知”；表达的是“某时刻发生了某件事”；监听方订阅后被动收到，不主动轮询（waitLoaded 内部虽为轮询，但轮询的目标状态是由事件驱动更新的）。

---

## 四、选型建议：何时用事件

- 需要**“在某一时刻通知多方”**且**不需要持久化**：用事件（如就绪、主题/语言变更）。
- 需要**拿到某个对象引用**且在会话内有效：用 POOL。
- 需要**读写可序列化、需持久化的数据**：用 KernelMemory；若需“数据变更时通知”，可在负责该 key 的模块内派发自定义事件，或由监听方轮询/通过 API 订阅。

---

## 五、本节小结

- 事件用于**解耦的“就绪”或“状态变更”通知**；典型如 dependencyLoaded、主题/语言变更；派发在 document.body，监听方 addEventListener。
- 与 POOL（发现）、KernelMemory（共享状态）并列，**事件是“通知式”通信，不存状态**；选型时根据“要取引用 / 要存数据 / 要通知发生”选择对应机制。
