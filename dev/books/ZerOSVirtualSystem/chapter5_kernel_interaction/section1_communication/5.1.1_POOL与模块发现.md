# 5.1.1 POOL 与模块发现

## 本节导读（阅读目标）

本节使读者能够：**① 明确 POOL 在“模块间通信”中的角色：不是消息总线，而是“按类别+名称取引用”的注册表；② 说出引导层、内核层、系统层中哪些模块会向 POOL 注册、哪些会从 POOL 获取；③ 理解为何“发现”用 POOL 而“持久化状态”用 KernelMemory；④ 能根据源码在 POOL 中正确注册与获取，并避免“过早获取”“类别写错”等常见错误。** 与第 2 章 2.4 互补：2.4 讲 POOL 的接口与实现，本节讲其在**关联与交互**中的用法与设计动机。

---

## 一、POOL 的角色：按名发现

### 1.1 设计动机

在 ZerOS 中，Boot、Kernel、System 各层由多个脚本文件组成，模块之间经常需要**拿到对方提供的对象**（例如单例、类、工具函数）。若在模块 B 中直接写“从某路径 import 或依赖某全局变量 A”，会带来：

- **加载顺序强耦合**：B 所在脚本必须晚于 A 所在脚本执行，否则 A 未定义；
- **循环依赖风险**：A 若又依赖 B，容易出现未初始化即被访问；
- **可测试性差**：难以在单测中替换 A 为 Mock。

因此引入 **POOL**：一个**全局的“类别 + 名称 → 对象”注册表**。模块 A 在**自己初始化完成后**，把要暴露的对象以某个**名称**注册到某个**类别**下；模块 B 在**需要时**用同一类别和名称去取，得到的是 A 注册的引用。这样：

- 谁先注册、谁后取用，由 **MODULE_DEPENDENCIES** 与加载顺序保证（见第 2 章）；取用方不关心对象来自哪个脚本；
- “按名发现”统一走 POOL，避免在源码中散落对全局变量或路径的硬编码。

**POOL**（尤其是 `KERNEL_GLOBAL_POOL`）的职责可以概括为：**存贮“名称 → 对象引用”**，供其他模块在运行时**按名称获取**，而不需要直接依赖该对象的模块路径或全局变量名。

### 1.2 典型用法

- 模块 A 在初始化时执行：`POOL.__ADD__("KERNEL_GLOBAL_POOL", "GUIManager", GUIManager)`；
- 模块 B 在需要时执行：`const GUIManager = POOL.__GET__("KERNEL_GLOBAL_POOL", "GUIManager")`，即可拿到 A 注册的引用。

**注意**：依赖由 MODULE_DEPENDENCIES 与加载顺序保证，但“拿到引用”这一动作统一通过 POOL 完成，不在 B 的源码中写死对 A 的依赖路径。

因此 POOL 是**发现/注册表**：谁先注册、谁后取用；取用时只认“类别 + 名称”，不关心对象来自哪个脚本文件。它**不是**消息总线（不负责事件派发）、也不是共享状态存储（不替代 KernelMemory）。

## 二、POOL 接口在关联与交互中的使用方式

### 2.1 类别与名称

- **类别（type）**：在本书上下文中常用字符串 `"KERNEL_GLOBAL_POOL"`，表示“内核全局池”；POOL 实现中也支持传入**伪枚举对象**，此时会将该枚举中的各值分别作为类别键（见 pool.js 的 `__extractEnumValues__`）。同一类别下可挂多个**名称**。
- **名称（name）**：字符串，如 `"GUIManager"`、`"Dependency"`、`"C:"`；同一类别下名称唯一，后注册的会覆盖先前的（若实现允许覆盖）。

获取时使用**完全相同的**类别与名称，否则取到的是 undefined 或“未初始化”占位对象。

### 2.2 注册时机与获取时机

- **注册**：发生在各模块的 **init 或首次使用前**。例如 GUIManager 在自身 `init` 中注册；BootLoader 在 `start_init` 中注册 Dependency、startKernel、WORK_SPACE 等。注册前应确保该对象已就绪（否则其他模块取到后调用会出错）。
- **获取**：发生在“需要调用该能力”时。可能是模块初始化阶段（如 TaskbarManager 初始化时取 GUIManager），也可能是运行时（如用户点击某按钮后，事件处理中再取 GUIManager）。若获取时 POOL 中尚无该名称，则 `__GET__` 可能返回 undefined 或 `{ isInit: false }`，调用方需做**降级或等待**（例如延迟重试、或依赖 dependencyLoaded 后再取）。

### 2.3 与第 2 章 2.4 的衔接

第 2 章 2.4 已说明：`__INIT__`/`__UPDATE__` 用于确保类别存在；`__ADD__` 添加命名元素；`__GET__` 按类别+名称获取；`__HAS__` 判断是否存在；`__GET_ALL__`、`__CLEAR__` 的语义与使用场景。本节不重复接口细节，而是强调：在**模块关联与交互**场景下，**谁在什么时机注册、谁在什么时机获取**，以及**为何用 POOL 而不是 KernelMemory 或事件**。

## 三、典型注册与获取（按层）

下表按**引导层、内核层、系统层**归纳“谁注册、谁获取、用途”。便于读者在阅读或修改代码时快速定位 POOL 的使用点。

| 层级 | 注册方 | 名称 | 获取方 | 用途 |
|------|--------|------|--------|------|
| 引导层 | BootLoader（start_init） | Dependency | loadModules、waitForCoreModules | 依赖状态与 waitLoaded |
| 引导层 | BootLoader（start_init） | startKernel | 外部或测试 | 重新触发引导 |
| 引导层 | BootLoader（start_init） | WORK_SPACE | 多处 | 工作区根路径（如 "C:"） |
| 引导层 | dependencyConfig.js 末尾 | DependencyConfig | BootLoader、waitDependencySync | 类引用 |
| 引导层 | pool.js 末尾 | （自身 publishSignal） | — | 依赖信号 |
| 系统层 | GUIManager.init | GUIManager | TaskbarManager、Desktop、应用通过内核 API | 窗口注册/焦点/预览 |
| 内核层 | Disk / 文件系统 init | 分区名（如 "C:", "D:"） | Disk._getDiskSeparateMap、NodeTree 相关 | NodeTreeCollection 引用 |
| 内核层 | LStorage 等 | LStorage | PermissionManager、ThemeManager、应用通过 API | 存储读写 |

**要点**：

- 注册发生在各模块 **init 或首次使用前**；获取发生在“需要调用该能力”时。
- 若获取时 POOL 中尚无该名称，则 `__GET__` 返回 undefined 或 `{ isInit: true }`（空占位），调用方需做降级或等待。
- 分区名（如 "C:", "D:"）作为名称注册的是**该分区对应的 NodeTreeCollection 实例**，便于 FileSystem 等按盘符取到正确的树结构。

## 四、为何“发现”用 POOL 而“持久化”用 KernelMemory

这是架构上的明确分工，避免误用：

- **POOL**：
  - 存的是**运行时对象引用**（函数、类、单例、DOM 相关等），**不能序列化**；
  - 生命周期与**当前页面/会话**一致，刷新即清空；
  - 用于**当前会话内**的模块发现与调用。
- **KernelMemory**：
  - 存的是**可序列化的数据**（进程表、APPLICATION_SOP 元数据、分区名列表等），需要刷新后恢复；
  - 用于**跨会话**的共享状态。

因此：**“谁提供什么能力”（对象引用）** → 用 POOL 按名取；**“谁存了什么数据”（可序列化状态）** → 用 KernelMemory 按 key 读写。二者配合示例：ProcessManager 从 KernelMemory 读 PROCESS_TABLE，不从 POOL 取进程表；GUIManager 不往 KernelMemory 写窗口列表，只通过 POOL 暴露自身供别人调用。

## 五、源码片段导读（pool.js 中的 __ADD__ 与 __GET__）

以下仅摘录与“注册/获取”相关的逻辑，便于对照实现理解“类别+名称”的存储方式。完整实现见 `kernel/core/signal/pool.js`。

```js
// pool.js 中 __ADD__ 的核心逻辑（节选）
// 若 name 为空将打印警告并忽略
__ADD__(type, name, elem) {
    if (typeof name === "undefined" || name === null || name === "") {
        KernelLogger.warn("POOL", "__ADD__: name 不能为空或空字符串", { type, name });
        return;
    }
    // 若 type 为伪枚举对象且 name 对应其某字段，则用该字段的值作为真实类别
    let realType = type;
    if (this.__isObject__(type) && typeof name === "string" &&
        Object.prototype.hasOwnProperty.call(type, name)) {
        realType = type[name];
    }
    const key = this.__normalizeKey__(realType);
    if (!this.__KEY_POOL__.has(key)) this.__KEY_POOL__.set(key, { isInit: true });
    const pool = this.__KEY_POOL__.get(key);
    pool[name] = elem;  // 同名覆盖
}
```

```js
// __GET__ 的核心逻辑（节选）
// 按类别 key 找到池对象，再按 name 取元素；若不存在则返回 undefined
__GET__(type, name) {
    const key = this.__normalizeKey__(type);
    const pool = this.__KEY_POOL__.get(key);
    if (!pool || !this.__isObject__(pool)) return undefined;
    return pool[name];
}
```

理解要点：**类别**先被规范化成字符串 key，同一 key 对应一个“池对象”（普通对象）；**名称**是该池对象上的属性名；因此 `__GET__("KERNEL_GLOBAL_POOL", "GUIManager")` 实际是取 `__KEY_POOL__.get("KERNEL_GLOBAL_POOL")["GUIManager"]`。

## 六、常见错误与排查

| 现象 | 可能原因 | 排查与解决 |
|------|----------|------------|
| 取到 undefined | 尚未注册或类别/名称写错 | 确认注册方已执行且类别、名称与注册时完全一致（区分大小写）；必要时在获取前 waitForCoreModules 或等待 dependencyLoaded |
| 取到 { isInit: true } 且无业务对象 | 该类别已 __INIT__ 但尚未 __ADD__ 具体 name | 检查加载顺序，确保提供方模块先于使用方执行并完成 __ADD__ |
| 调用取到的对象时报错“不是函数” | 注册的是类而非实例，或注册错了引用 | 确认注册的是调用方期望的类型（单例实例 vs 类）；检查 __ADD__ 的第三个参数 |
| 多分区下取错 NodeTree | 分区名不一致（如 "C" vs "C:"） | 使用与 Disk 一致的规范化盘符（如 ProcessManager._normalizeDiskName），并在注册与获取时统一 |

---

## 七、本节小结

- POOL 是“按类别+名称取引用”的**注册表**，用于**模块发现**；不是消息总线，也不是持久化存储。
- 典型注册/获取按层见上表；注册在 init 或首次使用前，获取在需要时；取不到时需降级或等待。
- **发现用 POOL、持久化用 KernelMemory**；二者分工明确，共同支撑模块间通信与状态共享。
- 实现上类别对应内部 Map 的 key，名称对应池对象的属性名；新增模块时注意注册时机与名称一致性，并参考常见错误表排查。
