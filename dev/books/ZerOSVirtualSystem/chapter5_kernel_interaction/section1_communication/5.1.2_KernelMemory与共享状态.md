# 5.1.2 KernelMemory 与共享状态

## 本节导读（阅读目标）

本节使读者能够：**① 明确 KernelMemory 在“模块间共享状态”中的角色：多模块读写同一批 key（PROCESS_TABLE、APPLICATION_SOP、DISK_SEPARATE_MAP 等），实现跨模块、跨会话的共享；② 说出哪些模块写谁、哪些模块读谁；③ 理解“共享”体现在“同一 key 被多个模块依赖”，而非“POOL 式单例引用”；④ 理解 loadData/saveData 与 Exploit 内存、_ensureMemory 的关系，以及为何对外应通过“负责该 key 的模块”的 API 访问。** 与第 3 章 3.1.2、3.5 互补。

---

## 一、KernelMemory 的角色：键值持久化与共享

### 1.1 设计动机

ZerOS 中除了“按名发现对象”（POOL）外，还需要**跨模块、跨会话**的**数据共享**：例如进程表要在 ProcessManager 与持久化之间同步、内存分区元数据要供 MemoryManager 与 KernelMemory 共同使用。这类数据特点：

- **可序列化**：能 JSON 序列化或按约定格式存贮；
- **需要持久化**：刷新页面或重启后需恢复；
- **多模块依赖**：可能由一个模块“负责写入”，多个模块“只读”或“通过负责方 API 访问”。

若把这些数据放在 POOL，则刷新后 POOL 清空，无法恢复；若各模块各自维护一份副本，则一致性难以保证。因此引入 **KernelMemory**：以 **key 为逻辑名**，在 **Exploit 进程的 Heap/Shed** 中存贮序列化后的数据（见第 3 章 3.5）；底层由 KernelMemory._ensureMemory 与 loadData/saveData 完成地址映射与读写。

多个模块可以：

- **写入同一 key**：通常由“负责该语义”的模块**唯一写入**（如 ProcessManager 写 PROCESS_TABLE，MemoryManager 写 APPLICATION_SOP），避免多写冲突。
- **读取同一 key**：任意有权调用 KernelMemory 的模块在需要时 loadData(key)，得到的是**同一份逻辑数据**（反序列化后的副本或结构），从而实现“共享状态”。

因此 KernelMemory 是**共享持久化状态**：谁有 key 的写权由设计约定；读权对所有能调用 KernelMemory 的代码开放（实际多为内核/系统层）；**对外暴露**则建议通过“拥有该 key 的模块”的公开 API，以保持封装与一致性。

### 1.2 与 POOL 的对比（重申）

| 维度 | POOL | KernelMemory |
|------|------|--------------|
| 存贮内容 | 运行时对象引用（函数、类、单例等） | 可序列化数据（对象、数组、Map 等） |
| 生命周期 | 当前会话，刷新即清空 | 持久化在 Exploit 内存，刷新后可恢复 |
| 典型用途 | 模块发现、按名取引用 | 进程表、内存元数据、权限快照等 |
| 访问方式 | __GET__(type, name) | loadData(key) / saveData(key, data) |

## 二、典型 key 与读写方

下表列出内核/系统层常用的 KernelMemory key、写入方、读取方与含义。便于在阅读或修改代码时明确“谁负责写、谁可以读”。

| key | 写入方 | 读取方 | 含义 |
|-----|--------|--------|------|
| PROCESS_TABLE | ProcessManager | ProcessManager、TaskbarManager 等（建议经 ProcessManager API） | 进程表序列化 |
| APPLICATION_SOP | MemoryManager | MemoryManager、KernelMemory（_ensureMemory） | 各 pid 内存分区元数据（Heap/Shed 分配信息） |
| PROGRAM_NAMES | MemoryManager | MemoryManager、展示/日志 | pid → 程序名映射 |
| DISK_SEPARATE_MAP | Disk（或文件系统 init） | Disk | 分区名列表或分区相关元数据 |
| permissionManager.permissions | PermissionManager | PermissionManager | 按程序名保存的权限集合 |

**要点**：

- 读写方可能同一模块（如 ProcessManager 既读又写 PROCESS_TABLE），也可能不同（如 TaskbarManager 通过 ProcessManager 的 getter 或 getProcessList 访问进程表，而不是直接 loadData('PROCESS_TABLE')）。
- “共享”体现在**多个模块依赖同一 key 所表示的逻辑状态**；物理上数据在 Exploit 的 Heap/Shed 中，由 KernelMemory 做 key → 地址的映射（见 3.5.2）。

---

## 三、loadData / saveData 的语义与调用链简述

- **loadData(key)**：根据 key 在 Exploit 内存中定位对应存储区域，读取并反序列化后返回。若 key 不存在或未初始化，可能返回 undefined 或默认结构。
- **saveData(key, data)**：将 data 序列化后写入 Exploit 内存中该 key 对应的区域；若该 key 尚未分配空间，会通过 _ensureMemory 与内部分配算法预留空间（见 3.5.2）。

调用链上：**KernelMemory.loadData/saveData** 内部会依赖 **MemoryManager.APPLICATION_SOP**（用于 Exploit 分区的元数据）和 **_ensureMemory**（确保 Exploit 的 Heap/Shed 已分配）。因此 KernelMemory 与 MemoryManager 存在协作关系：MemoryManager 维护 APPLICATION_SOP，KernelMemory 使用它并可能触发 MemoryManager 的分配逻辑。

---

## 四、与 POOL 的配合及封装建议

- **POOL**：ProcessManager、GUIManager、LStorage 等**对象本身**由各模块注册；其他模块通过 POOL 拿到**引用**再调用其方法。
- **KernelMemory**：ProcessManager 内部通过 KernelMemory 存 PROCESS_TABLE；其他模块若需“进程列表”或“某进程是否存在”，应通过 **ProcessManager 的公开 API**（如 PROCESS_TABLE getter、getProcessList、getProcessInfo 等）访问，而**不直接** loadData('PROCESS_TABLE')。这样做的原因：
  - **单一数据源**：进程表的格式与一致性由 ProcessManager 统一维护；
  - **封装**：将来若进程表拆成多个 key 或增加缓存，调用方无需改动；
  - **权限与校验**：若将来在读取时增加校验，只需在 ProcessManager 的 API 内实现。

因此“共享状态”往往通过**“负责该 key 的模块”暴露出的接口**访问，KernelMemory 是底层存储，不是唯一对外通道。

## 五、源码片段导读（KernelMemory 常量与 _ensureMemory 要点）

以下节选 `kernel/memory/kernelMemory.js` 中与“角色”相关的常量与 _ensureMemory 的入口逻辑，便于理解 Exploit 内存与 APPLICATION_SOP 的配合。

```js
// kernel/memory/kernelMemory.js（节选）
class KernelMemory {
    static EXPLOIT_PID = 10000;
    static EXPLOIT_HEAP_ID = 1;
    static EXPLOIT_SHED_ID = 1;
    static EXPLOIT_HEAP_SIZE = 2 * 1024 * 1024; // 2MB

    static _ensureMemory() {
        // 防止递归调用
        if (KernelMemory._ensuringMemory) {
            if (KernelMemory._memoryCache) return KernelMemory._memoryCache;
            return null;
        }
        // ...
        const sop = MemoryManager.APPLICATION_SOP;  // 依赖 MemoryManager 的 APPLICATION_SOP
        let appSpace = sop.get(KernelMemory.EXPLOIT_PID);
        if (!appSpace) {
            appSpace = { heaps: new Map(), sheds: new Map(), nextHeapId: 1, nextShedId: 1 };
            sop.set(KernelMemory.EXPLOIT_PID, appSpace);
        }
        // 后续：确保 heaps/sheds 中有 Exploit 的 Heap 与 Shed，并写入 _memoryCache
    }
}
```

理解要点：KernelMemory 使用**固定 PID（EXPLOIT_PID）**与**固定 Heap/Shed ID** 表示 Exploit 的内核数据区；APPLICATION_SOP 由 MemoryManager 维护，KernelMemory 通过 sop.get(EXPLOIT_PID) 取得或创建 Exploit 的“分区元数据”，再在此基础上做 loadData/saveData 的地址分配。因此“共享状态”的物理载体是 Exploit 的 Heap/Shed，逻辑载体是 key；读写 key 即读写该区域中的某段。

## 六、常见错误与排查

| 现象 | 可能原因 | 排查与解决 |
|------|----------|------------|
| loadData 返回 undefined | key 从未 saveData，或 key 拼写不一致 | 确认写入方已调用 saveData(key, data)；检查 key 字符串是否与写入方完全一致 |
| saveData 后刷新丢失 | 数据未真正写入 Exploit 持久化区域，或 Exploit 内存未正确初始化 | 确认 _ensureMemory 已成功、MemoryManager 已就绪；检查 APPLICATION_SOP 中 EXPLOIT_PID 分区是否存在 |
| 多模块写同一 key 导致覆盖 | 违反“单写方”约定 | 约定每个 key 仅由一个模块写入；其他模块只读或通过负责方 API 访问 |
| 直接 loadData('PROCESS_TABLE') 导致格式依赖 | 进程表结构变更时调用方易出错 | 改为通过 ProcessManager 的公开 API 访问进程表，避免依赖内部序列化格式 |

---

## 七、本节小结

- KernelMemory 提供**跨模块、跨会话**的键值共享；数据存于 Exploit 的 Heap/Shed，通过 loadData/saveData 按 key 读写。
- 典型 key 与读写方见上表；**共享**体现在多模块依赖同一 key 的逻辑状态；**写权**建议由单一模块拥有，**读**可通过负责方 API 封装。
- 与 POOL 配合：POOL 管“对象引用”，KernelMemory 管“可序列化状态”；对外访问共享状态时优先使用负责该 key 的模块的 API，KernelMemory 为底层存储。
