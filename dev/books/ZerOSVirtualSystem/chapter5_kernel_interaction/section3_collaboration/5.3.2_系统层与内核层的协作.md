# 5.3.2 系统层与内核层的协作

## 本节导读（阅读目标）

本节使读者能够：**① 说出 GUIManager 与 EventManager 在“按 pid 注册/注销窗口与事件”上的协作；② 说出 PermissionManager 与 LStorage 在敏感键与权限检查上的配合；③ 说出 BootLoader 与 DependencyConfig/POOL 在引导顺序与模块发现上的关系；④ 能画出“系统层 → 内核层”的调用方向与“进程退出时多模块清理”的顺序。** 与第 2 章、第 4 章各节互补。

---

## 一、GUIManager 与 EventManager

### 1.1 职责划分

- **GUIManager**（内核/系统层）：负责窗口的创建、注册、焦点、最小化、关闭等；每个窗口与 **pid** 关联（registerWindow(pid, ...)）。进程退出时，必须**按 pid 注销**该进程下的所有窗口（unregisterWindow 或 showWindowsForPid 等批量清理），否则会出现“已退出程序仍占任务栏/窗口列表”或 DOM 悬空引用。
- **EventManager**（系统层）：负责全局事件监听与按 pid 派发；进程退出时需**按 pid 移除**该进程注册的监听器，避免悬空引用与误派发（将事件派发到已销毁的上下文）。

### 1.2 协作方式

**ProcessManager** 在进程退出流程中，**依次**（或按实现规定的顺序）调用：

1. **GUIManager** 的“按 pid 注销窗口”接口（如 unregisterWindow 逐窗、或 cleanupProgramNotifications / showWindowsForPid 等按 pid 批量清理）；
2. **EventManager** 的“按 pid 清理监听”接口（移除该 pid 注册的所有 listener）。

这样保证**窗口与事件生命周期与进程一致**：进程存在则窗口与监听存在，进程退出则一并清理。具体调用链与函数名见第 3 章 3.2.4（进程退出与资源回收）。

**系统层使用内核层**：TaskbarManager、Desktop 等系统层 UI 通过 **POOL.__GET__("KERNEL_GLOBAL_POOL", "GUIManager")** 获取 GUIManager 引用，再调用其方法（如获取窗口列表、焦点窗口、最小化/还原等）。这是“系统层 → 内核层”的典型方向：**不通过 callKernelAPI**，而是**直接调用**内核暴露的对象（通过 POOL 发现），因为调用方是系统可信代码。

## 二、PermissionManager 与 LStorage

### 2.1 职责划分

- **LStorage**：提供按 **key** 的存储（底层通过 callKernelAPI('LocalStorage.get/set', ...) 或等价实现）；部分 key 被设计为**敏感键**（如与用户隐私、系统配置相关），需要**特定权限**才能访问。
- **PermissionManager**：维护权限声明、用户授权与 **hasPermission(pid, permission)**；在 LStorage 的 get/set 路径上，对**敏感键**会先调用 PermissionManager 检查当前调用进程（pid）是否具备对应权限（见第 4 章 4.3.3）。

### 2.2 协作方式

- **LStorage** 在读写**敏感键**前：解析“当前调用方 pid”（如通过 ProcessManager._getCallerPidsFromStack 或传入的 pid）；调用 **PermissionManager.hasPermission(pid, permission)** 或 **checkAndRequestPermission**；未通过则拒绝本次 get/set。
- **权限数据**可能持久化（如 permissionManager.permissions 存于 KernelMemory），与 LStorage 的“按 key 存储”**分离**：**权限是元数据，LStorage 是数据**；二者通过“敏感键 ↔ 所需权限”的**配置**关联（如在 LStorage 或 PermissionManager 中维护敏感键列表及所需权限名）。

这样既保证“谁能读哪些 key”由权限控制，又保证存储实现与权限实现解耦：LStorage 只负责存贮与敏感键判断，PermissionManager 只负责权限状态与检查。

## 三、BootLoader 与 DependencyConfig / POOL

### 3.1 职责划分

- **BootLoader**：负责**启动顺序**；在 start_init 中加载 DependencyConfig、通过 **waitForCoreModules** 等待核心模块就绪（依赖 dependencyLoaded 事件与 Dependency 状态），然后注册 **Dependency**、**startKernel**、**WORK_SPACE** 等到 **POOL**，再启动内核与系统层。
- **DependencyConfig**：维护 MODULE_DEPENDENCIES 与 dependencyMap；各模块脚本执行末尾 **publishSignal(模块路径)** 触发 dependencyLoaded，DependencyConfig 将对应条目标记为 loaded；**waitLoaded** 轮询或等待这些条目，供 BootLoader 的 waitForCoreModules 使用。
- **POOL**：在核心模块加载完成后，由各模块在 init 中 **__ADD__** 自身或关键引用（如 GUIManager、LStorage）；BootLoader 或后续系统层通过 **__GET__** 按名发现，无需写死路径。

### 3.2 协作方式

- **引导顺序**：由 BootLoader + DependencyConfig + **MODULE_DEPENDENCIES 依赖图**决定；先 loadScript 依赖，再 waitLoaded，再执行后续 init 与 POOL 注册。
- **模块发现**：由 **POOL** 在运行时提供；谁先注册、谁后取用，由加载顺序保证。
- **就绪信号**：**dependencyLoaded** 事件把“脚本已执行”与“DependencyConfig 更新 dependencyMap”串起来；BootLoader 通过 waitForCoreModules（内部依赖 Dependency 的 waitLoaded）等待“所有核心模块 loaded”后再继续。

详见第 2 章 2.2（依赖配置）、2.4（POOL）。

## 四、协作关系小结表

| 协作对 | 方向 | 内容 |
|--------|------|------|
| ProcessManager ↔ MemoryManager | 双向（PM 调 MM） | 进程创建时 allocateMemory；进程退出时 freeMemory；PROCESS_TABLE 与 APPLICATION_SOP 通过 pid 关联 |
| ProcessManager ↔ GUIManager | PM 调 GUIManager | 进程退出时按 pid 注销窗口 |
| ProcessManager ↔ EventManager | PM 调 EventManager | 进程退出时按 pid 清理监听 |
| 系统层 ↔ GUIManager | 系统层调 GUIManager | 通过 POOL 取 GUIManager 引用，调用窗口/焦点等方法 |
| PermissionManager ↔ LStorage | LStorage 调 PermissionManager | 敏感键读写前 hasPermission / checkAndRequestPermission |
| BootLoader ↔ DependencyConfig | BootLoader 用 DependencyConfig | waitForCoreModules → waitLoaded；dependencyLoaded 驱动 loaded 状态 |
| BootLoader ↔ POOL | BootLoader 写 POOL，后续读 POOL | 注册 Dependency、startKernel、WORK_SPACE；各模块注册自身，系统层按名取用 |

---

## 五、本节小结

- **GUIManager ↔ EventManager**：按 pid 管理窗口与事件，进程退出时由 **ProcessManager** 驱动一并清理；系统层通过 **POOL** 取 GUIManager 直接调用。
- **PermissionManager ↔ LStorage**：敏感键读写前经 PermissionManager 检查；权限元数据与存储数据分离，通过“敏感键 ↔ 所需权限”配置关联。
- **BootLoader ↔ DependencyConfig / POOL**：引导顺序依赖 DependencyConfig 与 dependencyLoaded；运行时发现依赖 POOL；三者共同保证“先就绪、再注册、再使用”。
