# 5.3.1 ProcessManager 与 MemoryManager

## 本节导读（阅读目标）

本节使读者能够：**① 说出进程创建时 MemoryManager 如何为 pid 分配 Heap/Shed、如何写入 APPLICATION_SOP；② 说出进程退出时 ProcessManager 如何触发内存释放、MemoryManager 如何释放并清理 APPLICATION_SOP；③ 理解 PROCESS_TABLE 与 APPLICATION_SOP 的读写分工及与 KernelMemory 的关系；④ 能画出“进程创建/退出”与“内存分配/释放”的协作时序，并在修改时保持一致性。** 与第 3 章 3.2.3、3.2.4、3.5 互补。

---

## 一、进程创建时的协作

### 1.1 设计动机

进程在 ZerOS 中对应一个 **pid**，需要**独立的内存分区**（Heap/Shed）用于 loadData/saveData 等持久化与隔离。若由 ProcessManager 自行管理内存分配，会与 MemoryManager 的“统一内存视图”（APPLICATION_SOP）重复且易不一致。因此约定：**进程表与生命周期**由 ProcessManager 负责，**内存分区与 APPLICATION_SOP** 由 MemoryManager 负责；二者通过 **pid** 关联，在**进程创建时**由 ProcessManager 调用 MemoryManager 分配，在**进程退出时**由 ProcessManager 调用 MemoryManager 释放。

### 1.2 进程创建时的调用顺序

**ProcessManager** 在启动程序（如 _runProgram、startProgram）时：

1. **分配 PID**：通过 _allocatePid 等得到新 pid，并在 **PROCESS_TABLE**（内存中的 Map，并持久化到 KernelMemory 的 PROCESS_TABLE key）中写入进程信息：programName、status（如 loading → starting → running）、isExploit 等。
2. **分配内存**：需要为该进程提供 Heap/Shed 时，调用 **MemoryManager.allocateMemory(pid, heapSize, shedSize)**（或通过内部封装、或通过 callKernelAPI 转调，视实现而定）。

**MemoryManager.allocateMemory** 内：

1. 通过 **KernelMemory._ensureMemory** 等逻辑，在 **Exploit 的 Heap/Shed** 中为该 pid 预留或创建分区（见第 3 章 3.5）；若该 pid 已有分区则可能复用或扩展。
2. 将分区元数据（如 heapId、shedId、起始地址、大小等）写入 **APPLICATION_SOP**（由 MemoryManager 维护，通常也持久化到 KernelMemory 的 APPLICATION_SOP key），便于后续 **loadData/saveData** 按 pid 映射到正确地址。
3. 可选：调用 **ProcessManager.recordKernelModuleCall(pid, 'Memory.allocateMemory', { heapSize, shedSize })** 记录该次分配，供任务管理器展示。

因此：**进程表**由 ProcessManager 维护（PROCESS_TABLE）；**内存分区元数据**由 MemoryManager 维护（APPLICATION_SOP）；二者通过 **pid** 关联，进程“存在”与“有内存”在创建阶段保持一致。

### 1.3 时序简述（文字）

```
ProcessManager.startProgram / _runProgram
  → _allocatePid → PROCESS_TABLE.set(pid, { programName, status, ... })
  → （若需内存）MemoryManager.allocateMemory(pid, heapSize, shedSize)
      → KernelMemory._ensureMemory / 分区分配
      → APPLICATION_SOP 更新该 pid 的 heaps/sheds 等
      → （可选）recordKernelModuleCall(pid, 'Memory.allocateMemory', ...)
  → 后续：加载脚本、registerWindow 等
```

## 二、进程退出时的协作

### 2.1 设计动机

进程退出时，必须**释放该 pid 占用的内存**并**清理 APPLICATION_SOP 中该 pid 的条目**，否则会导致“僵尸分区”与后续 pid 复用时的混乱。同时，窗口、事件监听等也需按 pid 清理（见 5.3.2）。因此 ProcessManager 在退出流程中**统一驱动**：先更新或移除进程表，再调用 MemoryManager.freeMemory，再通知 GUIManager、EventManager 等清理。

### 2.2 进程退出时的调用顺序

**ProcessManager** 在进程退出（kill、requestSelfTermination、异常退出等）时：

1. **更新 PROCESS_TABLE**：将该 pid 的状态置为“退出”或从 PROCESS_TABLE 中移除条目；必要时持久化到 KernelMemory。
2. **释放内存**：调用 **MemoryManager.freeMemory(pid)**（或等效接口），释放该 pid 占用的 Heap/Shed，并从 **APPLICATION_SOP** 中移除该 pid 的元数据。
3. **清理窗口与事件**：通知 **GUIManager** 注销该 pid 的窗口（unregisterWindow 或按 pid 批量清理）、**EventManager** 按 pid 移除该进程注册的监听器（见 5.3.2）。

**MemoryManager.freeMemory** 内：

1. 根据 **APPLICATION_SOP** 找到该 pid 的分区（heaps、sheds），执行释放逻辑（如标记为可用、或从 Exploit 的分配表中移除）。
2. 更新或删除 **APPLICATION_SOP** 中该 pid 的条目，避免后续 loadData/saveData 仍按该 pid 寻址。
3. 可选：**recordKernelModuleCall(pid, 'Memory.freeMemory', {})**。

这样**进程生命周期**与**内存生命周期**一一对应：创建时分配、退出时释放，避免泄漏与悬空引用。

### 2.3 时序简述（文字）

```
ProcessManager.kill / requestSelfTermination / 异常退出处理
  → PROCESS_TABLE 更新或删除该 pid
  → MemoryManager.freeMemory(pid)
      → 根据 APPLICATION_SOP 释放该 pid 的 Heap/Shed
      → APPLICATION_SOP 删除或清空该 pid 的条目
      → （可选）recordKernelModuleCall(pid, 'Memory.freeMemory', {})
  → GUIManager 按 pid 注销窗口
  → EventManager 按 pid 清理监听
```

## 三、PROCESS_TABLE 与 APPLICATION_SOP 的分工

| 数据 | 维护方 | 存储位置（逻辑） | 用途 |
|------|--------|------------------|------|
| PROCESS_TABLE | ProcessManager | KernelMemory 持久化 + 内存中 Map | 进程是否存在、状态、程序名、isExploit 等 |
| APPLICATION_SOP | MemoryManager | KernelMemory（及内存缓存） | 各 pid 对应的 Heap/Shed 分区元数据，供 loadData/saveData 按 pid 寻址 |

- ProcessManager **只**读/写 PROCESS_TABLE；MemoryManager **只**读/写 APPLICATION_SOP。其他模块需要“进程列表”或“某进程是否存在”时，应通过 **ProcessManager 的公开 API**（如 getProcessList、getProcessInfo、PROCESS_TABLE getter）访问，**不要直接** loadData('PROCESS_TABLE')，以保持单一数据源与封装。
- 两表通过 **pid** 关联：同一 pid 在 PROCESS_TABLE 中有一条进程记录，在 APPLICATION_SOP 中有一条（或一组）分区元数据；进程退出后两处都应清理。

## 四、常见错误与排查

| 现象 | 可能原因 | 排查与解决 |
|------|----------|------------|
| 进程退出后仍能 loadData(pid, key) | freeMemory 未调用或 APPLICATION_SOP 未清理该 pid | 确认 ProcessManager 退出流程中调用了 MemoryManager.freeMemory(pid)，且 APPLICATION_SOP 已删除该 pid |
| 新进程复用 pid 后读到旧数据 | 释放时未清空分区或未从 APPLICATION_SOP 移除 | 确保 freeMemory 中既释放物理/逻辑分区，又删除 APPLICATION_SOP 中该 pid 的条目 |
| PROCESS_TABLE 与 APPLICATION_SOP 不一致 | 某处只更新了一方 | 创建时先写 PROCESS_TABLE 再 allocateMemory；退出时先更新 PROCESS_TABLE 再 freeMemory，顺序一致 |

---

## 五、本节小结

- 进程**创建**：ProcessManager 登记 PROCESS_TABLE，并调用 **MemoryManager.allocateMemory**；MemoryManager 更新 APPLICATION_SOP，并通过 KernelMemory 在 Exploit 中分配分区。
- 进程**退出**：ProcessManager 更新/移除 PROCESS_TABLE，并调用 **MemoryManager.freeMemory**；MemoryManager 释放分区并清理 APPLICATION_SOP；再配合 GUIManager、EventManager 清理窗口与事件。
- PROCESS_TABLE 与 APPLICATION_SOP 通过 pid 关联；对外通过 ProcessManager/MemoryManager 的 API 访问，不直接读写 KernelMemory key。修改退出或创建逻辑时，保持“先进程表、再内存、再窗口/事件”的顺序一致。
