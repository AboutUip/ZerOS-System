# 第6.1节：文件系统驱动 FSDirve

## 本节导读

本节使读者能够：**① 理解 FSDirve 在 ZerOS 架构中的位置与职责——作为后端核心服务，处理前端内核的所有文件操作请求；② 掌握 FSDirve 的整体架构设计——请求路由、路径规范化、JWT 鉴权、权限校验、操作执行、响应封装；③ 理解三种后端实现（PHP/Python/Java）的异同与兼容性设计。** 源码位置：`system/service/FSDirve.php`、`system/service/backend-python/FSDriver.py`。

---

## 一、FSDirve 在 ZerOS 架构中的位置

### 1.1 前后端分离架构

ZerOS 采用典型的前后端分离架构：

```
┌─────────────────────────────────────────────────────────────────┐
│                      前端 JavaScript 层                        │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────────────────┐ │
│  │ ProcessMgr  │  │  FileSystem │  │     NodeTree            │ │
│  │  进程管理    │  │  文件系统    │  │    虚拟文件节点树        │ │
│  └──────┬──────┘  └──────┬──────┘  └────────────┬────────────┘ │
│         │                 │                     │              │
│         └─────────────────┼─────────────────────┘              │
│                           ▼                                    │
│                  ┌─────────────────┐                           │
│                  │  NetworkManager │  ← 统一网络请求封装        │
│                  └────────┬────────┘                           │
└───────────────────────────┼────────────────────────────────────┘
                            │ HTTP 请求
                            ▼
┌───────────────────────────────────────────────────────────────────┐
│                      后端服务层 (PHP/Python/Java)                │
│  ┌─────────────────────────────────────────────────────────────┐ │
│  │                        FSDirve                              │ │
│  │    文件系统驱动：目录/文件 CRUD、权限校验、JWT 鉴权          │ │
│  └─────────────────────────────────────────────────────────────┘ │
│                              │                                   │
│                              ▼                                   │
│  ┌─────────────────────────────────────────────────────────────┐ │
│  │                    虚拟磁盘 DISK/                           │ │
│  │     A: B: C: D: ... (每个分区对应 service/DISK/分区字母/)   │ │
│  └─────────────────────────────────────────────────────────────┘ │
└───────────────────────────────────────────────────────────────────┘
```

前端内核的 `FileSystem` 模块不直接操作磁盘，而是通过 `NetworkManager` 发起 HTTP 请求到后端 FSDirve 服务。后端完成实际的文件 I/O 后返回结果，前端再更新虚拟文件节点树。

### 1.2 FSDirve 的核心职责

FSDirve 是 ZerOS 后端的核心服务，其职责包括：

1. **请求路由**：解析 HTTP 请求中的 `action` 参数，分发到对应的处理函数
2. **路径规范化**：将虚拟路径（如 `D:/folder/file.txt`）转换为物理路径
3. **JWT 鉴权**：验证请求是否携带有效的 JWT Token
4. **权限校验**：根据 upid（程序唯一标识）检查程序是否有权执行操作
5. **操作执行**：执行实际的文件系统操作（创建/读取/写入/删除/移动/复制）
6. **响应封装**：统一封装操作结果为 JSON 格式返回前端

## 二、FSDirve 整体架构详解

### 2.1 请求处理流程

```
HTTP 请求到达 (GET/POST)
         │
         ▼
┌────────────────────────┐
│  响应头设置            │  ← CORS、Content-Type 等
└──────────┬─────────────┘
           │
           ▼
┌────────────────────────┐
│  JWT 验证 (jwtVerify)  │  ← 检查 token 有效性
│  - requireJWTVerify()  │
└──────────┬─────────────┘
           │
           ▼
┌────────────────────────┐
│  路由分发               │  ← action 参数解析
│  - switch($action)     │
└──────────┬─────────────┘
           │
    ┌──────┴──────┐
    │              │
    ▼              ▼
┌───────┐    ┌────────┐
│read_  │    │write_  │
│file   │    │file    │
└───┬───┘    └───┬────┘
    │            │
    └──────┬─────┘
           │
           ▼
┌────────────────────────┐
│  权限校验 (upid)        │  ← upid 对应程序权限
│  - checkPermission()   │
└──────────┬─────────────┘
           │
           ▼
┌────────────────────────┐
│  执行文件系统操作        │
│  - file_put_contents   │

```

### 2.2 核心代码结构 (PHP 实现)

```php
<?php
// system/service/FSDirve.php

// 1. 响应头设置
header('Content-Type: application/json; charset=utf-8');
header('Access-Control-Allow-Origin: *');
header('Access-Control-Allow-Methods: GET, POST, OPTIONS');
header('Access-Control-Allow-Headers: Content-Type, Authorization, X-Auth-Token, X-JWT');

// 2. 引入 JWT 验证
require_once __DIR__ . '/jwtVerify.php';
requireJWTVerify('FSDirve');

// 3. 基础路径配置
define('DISK_BASE_PATH', __DIR__ . '/DISK');

// 4. 路由分发
$action = $_GET['action'] ?? $_POST['action'] ?? '';

switch ($action) {
    case 'read_file':
        handleReadFile();
        break;
    case 'write_file':
        handleWriteFile();
        break;
    case 'create_dir':
        handleCreateDir();
        break;
    case 'delete':
        handleDelete();
        break;
    case 'list_dir':
        handleListDir();
        break;
    // ... 其他操作
    default:
        sendResponse(false, '未知操作: ' . $action, null, 400);
}
```

### 2.3 三种后端实现对比

| 特性 | PHP 实现 | Python 实现 | Java 实现 |
|------|---------|------------|-----------|
| 框架 | 原生 PHP | FastAPI + Uvicorn | Spring Boot 3.2 |
| 端口 | 8089 | 8000 | 8080 |
| 文件操作 | file_put_contents | pathlib.Path | Files.readAllLines |
| 压缩支持 | ZipArchive | zipfile | Apache Commons Compress |
| JWT 库 | firebase/php-jwt | PyJWT | java-jwt |
| 部署方式 | Apache/Nginx CGI | uvicorn 进程 | Spring Boot JAR |

三种实现提供**完全相同的 API 接口**，前端可通过 `backend` 参数或 `SystemInformation.setBackendType()` 切换。

## 三、路径规范化的实现

### 3.1 虚拟路径到物理路径的映射

FSDirve 使用简单的路径替换策略：

```php
// PHP 实现
function virtualToPhysical($virtualPath) {
    // 提取盘符 (D: -> D)
    $drive = substr($virtualPath, 0, 1);
    
    // 去除盘符，获取相对路径
    $relativePath = substr($virtualPath, 3); // 跳过 "D:/"
    
    // 映射到物理路径
    return DISK_BASE_PATH . '/' . $drive . '/' . $relativePath;
}
```

**示例**：
- 虚拟路径 `D:/folder/file.txt` → 物理路径 `system/service/DISK/D/folder/file.txt`
- 虚拟路径 `C:/config.json` → 物理路径 `system/service/DISK/C/config.json`

### 3.2 路径安全校验

必须防止路径穿越攻击（如 `D:/../C:/secret.txt`）：

```php
function validatePath($virtualPath) {
    // 1. 格式校验：必须是 A-Z: 开头
    if (!preg_match('/^[A-Za-z]:/', $virtualPath)) {
        return false;
    }
    
    // 2. 禁止路径穿越
    $normalized = realpath($virtualPath);
    if ($normalized === false) {
        // 路径不存在，单独检查是否有 ..
        if (strpos($virtualPath, '..') !== false) {
            return false;
        }
    }
    
    // 3. 必须在 DISK 目录下
    $physicalPath = virtualToPhysical($virtualPath);
    $diskBase = realpath(DISK_BASE_PATH);
    
    return strpos($physicalPath, $diskBase) === 0;
}
```

## 四、与前端内核的协作

### 4.1 NetworkManager 的请求封装

前端通过 `NetworkManager` 发起文件操作请求：

```javascript
// kernel/drive/networkManager.js

async readFile(path) {
    return await this.request('FSDirve', {
        action: 'read_file',
        path: path,
        options: { encoding: 'utf-8' }
    });
}

async writeFile(path, content, options = {}) {
    return await this.request('FSDirve', {
        action: 'write_file',
        path: path,
        content: content,
        options: options
    });
}
```

### 4.2 JWT Token 的自动注入

`NetworkManager` 会自动在请求头中注入 JWT Token：

```javascript
// 请求拦截器
async request(serviceName, data) {
    const token = await LStorage.getSystemStorage('jwtToken');
    
    const response = await fetch(this.getServiceUrl(serviceName), {
        method: 'POST',
        headers: {
            'Content-Type': 'application/json',
            'X-JWT': token  // 自动注入 JWT
        },
        body: JSON.stringify(data)
    });
    
    return await response.json();
}
```

## 五、接手维护要点

### 5.1 新增操作类型

如果需要在 FSDirve 中新增文件操作（如 `copy_file`），步骤如下：

1. **在前端** `kernel/filesystem/` 中添加对应方法
2. **在 NetworkManager** 添加请求封装
3. **在后端** 添加路由 case 和处理函数
4. **在 jwtVerify.php** 添加服务的 upid 映射（如果需要权限控制）

### 5.2 安全审计 checklist

- [ ] 所有新增操作是否都有 upid 权限校验？
- [ ] 路径规范化是否正确处理了 `..` 和符号链接？
- [ ] 敏感文件（如 `LocalSData.json`）是否有额外的写入限制？
- [ ] JWT Token 过期时间是否合理？

## 本节小结

本节建立了对 FSDirve 的整体认知：

1. **架构位置**：FSDirve 是 ZerOS 后端的核心文件系统服务，承接前端所有文件操作请求
2. **核心职责**：请求路由、路径规范化、JWT 鉴权、权限校验、操作执行、响应封装
3. **三种实现**：PHP/Python/Java 提供相同的 API 接口，保证前端切换无感知
4. **路径安全**：路径穿越攻击是主要防御点，需要严格的规范化与校验
5. **前后端协作**：NetworkManager 发起请求 + JWT Token 自动注入 + 统一 JSON 响应
